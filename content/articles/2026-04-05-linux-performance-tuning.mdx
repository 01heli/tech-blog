## 性能问题的层次化思维

Linux 性能问题排查最怕的是"瞎猜"——看到一个 CPU 100% 就去排查 CPU，结果问题是磁盘 I/O 导致的 iowait；看到内存高就去加内存，结果问题是连接数过多导致的。

Brendan Gregg 提出了 **USE 方法论**——从三个维度审视每个资源：

- **Utilization（使用率）**：资源被使用的百分比
- **Saturation（饱和度）**：等待资源的任务队列长度
- **Errors（错误数）**：资源相关的错误事件

排查路径应该从宏观到微观，逐层深入：**确定瓶颈资源类型 → 定位到具体进程 → 深入分析函数级 → 代码修复**。

## 性能分析工具箱

| 资源维度 | 基础监控 | 深度分析 | 基准测试 |
|----------|----------|----------|----------|
| CPU | `top`, `mpstat`, `pidstat` | `perf`, 火焰图, `ftrace` | `stress-ng`, `sysbench` |
| 内存 | `free`, `vmstat`, `pmap` | `valgrind`, `heaptrack` | `stress-ng --vm` |
| 磁盘 I/O | `iostat`, `iotop` | `strace`, `blktrace` | `fio`, `dd` |
| 网络 | `ss`, `sar -n DEV`, `iftop` | `tcpdump`, `strace` | `iperf3`, `wrk` |

## CPU 性能分析

### 快速定位高负载

```bash
# 查看系统负载和 CPU 使用率
top -c

# 查看每个 CPU 核心的详细状态
mpstat -P ALL 1

# 找出 CPU 占用最高的进程
ps aux --sort=-%cpu | head -10

# 按线程级别查看
ps -eLo pid,tid,pcpu,comm --sort=-pcpu | head -10
```

重点关注几个指标：
- **Load Average**：除以 CPU 核心数，超过 1 说明有任务在排队
- **%us（用户态）**：应用代码的 CPU 消耗
- **%sy（内核态）**：系统调用和内核的 CPU 消耗，持续 >30% 说明内核开销过大
- **%wa（I/O 等待）**：CPU 在等待磁盘 I/O，此时 CPU 是空闲的，说明瓶颈在磁盘
- **上下文切换**：`vmstat 1` 的 `cs` 列，单核超过 10 万/秒需要关注

### perf：CPU 热点分析

`perf` 是 Linux 内核自带的性能分析工具，可以采样 CPU 的函数调用：

```bash
# 实时查看 CPU 热点函数（类似 top 的函数版）
perf top -p <pid>

# 采样 30 秒，记录调用链
perf record -F 99 -p <pid> -g --call-graph dwarf -- sleep 30
perf report --stdio

# 统计硬件事件
perf stat -e cycles,instructions,cache-misses,branches,branch-misses -p <pid> -- sleep 10
```

关键指标解读：
- **IPC（instructions per cycle）**：< 1 说明 CPU 没被充分利用（可能在等内存）
- **cache-misses**：缓存未命中率高说明数据局部性差
- **branch-misses**：分支预测失败率高说明代码分支模式不佳

将 perf 数据生成火焰图，可以直观地看到哪些函数占用了最多的 CPU：

```bash
perf record -F 99 -p <pid> -g -- sleep 30
perf script > out.perf
# 使用 Brendan Gregg 的 FlameGraph 工具
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl out.folded > flame.svg
```

### CPU 调优策略

```bash
# 设置性能调频策略（避免 CPU 降频影响性能）
cpupower frequency-set -g performance

# 进程绑定到指定 CPU 核心（减少缓存失效）
taskset -cp 0-3 <pid>

# 调整进程优先级
renice -n -10 -p <pid>

# 中断亲和性：将网卡中断分散到多个核心
echo f > /proc/irq/<irq_num>/smp_affinity
```

## 内存性能分析

### 快速诊断

```bash
# 内存概览
free -h

# 持续监控内存和 swap 变化
vmstat 1

# 查看进程内存详情
cat /proc/<pid>/status | grep -E "VmRSS|VmSize|VmSwap"

# 查看进程内存映射
pmap -x <pid>
```

关键理解：Linux 的"空闲内存"不等于 `free` 列。`available` 列才是真正可用的内存（包括可以释放的 buffer/cache）。

内存问题的三种类型：
1. **内存不足**：`available` 持续降低，OOM killer 被触发
2. **内存泄漏**：进程的 `VmRSS` 持续增长，不释放
3. **Swap 抖动**：大量 page-in/page-out，系统响应变慢

### 内存泄漏检测

```bash
# valgrind 检测（适合测试环境，有 10-20 倍性能损耗）
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./your_app

# heaptrack 图形化分析（性能影响较小）
heaptrack ./your_app
heaptrack_print heaptrack.your_app.xxx.gz | head -20
```

### 内存调优

```bash
# 降低 swap 倾向（0-100，默认 60，数据库场景建议设为 10）
sysctl -w vm.swappiness=10

# 禁用透明大页（数据库场景常用，减少内存碎片）
echo never > /sys/kernel/mm/transparent_hugepage/enabled

# 增加脏页比例，减少刷盘频率（有断电丢数据风险）
sysctl -w vm.dirty_ratio=20
sysctl -w vm.dirty_background_ratio=10

# 启用内存 overcommit（Redis 等依赖 fork 的场景）
sysctl -w vm.overcommit_memory=1
```

## 磁盘 I/O 分析

### 关键工具

```bash
# 查看磁盘 I/O 延迟和饱和度
iostat -x 1

# 查看哪个进程在大量读写
iotop -o

# 追踪进程的文件 I/O 系统调用
strace -e trace=open,openat,read,write -p <pid> -T
```

`iostat -x` 输出的关键指标：

| 指标 | 含义 | 危险阈值 |
|------|------|----------|
| `await` | I/O 平均等待时间（ms） | SSD > 10ms, HDD > 30ms |
| `avgqu-sz` | 平均队列深度 | 持续 > 1 说明设备饱和 |
| `%util` | 设备利用率 | 接近 100% 代表 I/O 瓶颈 |
| `r/s`, `w/s` | 每秒读写次数 | 超过设备规格需要关注 |
| `rkB/s`, `wkB/s` | 每秒读写数据量 | 对比设备带宽上限 |

### strace：系统调用级排查

`strace` 是排查应用层 I/O 问题的利器：

```bash
# 追踪进程的所有系统调用
strace -p <pid> -f -T

# 仅追踪文件 I/O
strace -e trace=openat,read,write,close -p <pid>

# 统计系统调用耗时分布
strace -c -p <pid> -f
```

曾经遇到一个案例：服务日志写入时延很高，`strace` 发现每次 `write()` 之后都跟着 `fsync()`，原来是日志框架开启了同步刷盘。关掉之后吞吐量提升了 5 倍。

### 磁盘 I/O 调优

```bash
# SSD 使用 mq-deadline 调度器
echo mq-deadline > /sys/block/sdX/queue/scheduler

# 禁用文件访问时间更新（减少写操作）
mount -o noatime,nodiratime /dev/sdX /mnt/data

# 限制进程 I/O 优先级
ionice -c 2 -n 7 -p <pid>    # best-effort 类，最低优先级
```

## 网络性能分析

### 快速诊断

```bash
# 查看网络连接统计
ss -s

# 查看所有 TCP 连接状态
ss -antp | awk '{print $1}' | sort | uniq -c

# 查看网络流量
sar -n DEV 1

# 查看网络连接实时流量
iftop -i eth0
```

判断网络瓶颈的几个信号：
- **TCP 重传率**：`netstat -s | grep retrans`，>1% 需要关注
- **连接队列溢出**：`netstat -s | grep -i "listen\|overflow"`
- **TIME_WAIT 过多**：`ss -ant | grep TIME-WAIT | wc -l`，过多说明短连接频繁创建

### tcpdump：深入协议层

```bash
# 抓取特定端口的流量
tcpdump -i eth0 -n -c 100 "port 8080"

# 查看 TCP 握手过程
tcpdump -i eth0 -n "tcp[tcpflags] & (tcp-syn|tcp-fin) != 0"

# 抓包写入文件，用 Wireshark 分析
tcpdump -i eth0 -w capture.pcap "host 10.0.0.1"
```

### 网络参数调优

```bash
# TCP 缓冲区（高带宽高延迟场景）
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.wmem_max=16777216
sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"

# 连接队列（高并发 Web 服务）
sysctl -w net.core.somaxconn=4096
sysctl -w net.ipv4.tcp_max_syn_backlog=4096

# 启用 BBR 拥塞控制（低延迟场景，替代 CUBIC）
sysctl -w net.core.default_qdisc=fq
sysctl -w net.ipv4.tcp_congestion_control=bbr

# TIME_WAIT 复用（高并发短连接场景）
sysctl -w net.ipv4.tcp_tw_reuse=1

# 启用 TCP Fast Open（减少握手 RTT）
sysctl -w net.ipv4.tcp_fastopen=3
```

## 实战案例：CPU 100% 但吞吐量极低

曾经遇到一个线上问题：Go 服务 CPU 100% 满载，但 QPS 很低。排查过程：

1. `top` 确认 CPU 100%，且全是 `%us`（用户态），排除 I/O 等待
2. `perf top` 发现大量 CPU 时间消耗在 `runtime.futex` 和 `sync.(*Mutex).Lock`
3. `go tool pprof mutex` 确认了高竞争的热点锁——一个 `sync.Mutex` 保护了整个请求处理函数
4. 将 mutex 拆细，关键路径改为 CAS 无锁操作
5. CPU 降至 20%，吞吐量提升 3 倍

这个案例的教训：**CPU 高不一定是计算密集型任务，也可能是锁竞争导致的忙等待。** 工具告诉你 CPU 在干什么，但根因需要结合应用逻辑分析。

## 性能排查的正确姿势

总结一套实用的排查 SOP：

```
1. 首先理解系统架构 —— 请求怎么到达的？经过了哪些组件？
2. 用 USE 法定位瓶颈层 —— CPU / 内存 / I/O / 网络，哪一个饱和了？
3. 用对应工具深入分析 —— perf / strace / tcpdump / valgrind
4. 形成假设并验证 —— "我认为是 X 导致的，改动 Y 后应该看到 Z"
5. 调优后回归测试 —— 确认改动有效，且没有引入新问题
```

最重要的原则：**用数据代替直觉。** 每一个性能优化决策背后，都应该有 perf 的火焰图、strace 的耗时分布、或者 tcpdump 的抓包分析作为支撑。猜出来的优化，十有八九是错的。
