## 缓存的本质

缓存是计算机科学中最伟大的发明之一——用空间换时间，将昂贵计算或 I/O 的结果暂存起来，下次直接返回。

Redis 作为最流行的分布式缓存方案，在实际业务中面临的挑战可以归结为三个核心问题：**怎么读写**（缓存策略）、**怎么保证一致**（数据同步）、**怎么防止雪崩**（异常防护）。

## 缓存读写策略

### Cache-Aside（旁路缓存）— 最通用

这是 90% 的业务场景应该使用的模式：

```
读流程：查缓存 → 命中就返回 → 未命中查数据库 → 写入缓存 → 返回
写流程：更新数据库 → 删除缓存（不是更新缓存）
```

**为什么是删缓存而不是更新缓存？**
- 避免无意义的写操作：某些数据写入后很久不被读取，更新缓存浪费资源
- 避免复杂的计算：缓存值可能是多表聚合的结果，更新时需要同样的计算
- 遵循延迟加载原则：只有被读取的数据才值得缓存

```python
def get_user(user_id: str) -> User | None:
    # 1. 先查缓存
    cached = redis.get(f"user:{user_id}")
    if cached:
        return json.loads(cached)

    # 2. 查数据库
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)
    if not user:
        return None

    # 3. 写入缓存，设置 TTL
    redis.setex(f"user:{user_id}", 3600, json.dumps(user))
    return user

def update_user(user_id: str, data: dict) -> None:
    # 1. 先更新数据库
    db.execute("UPDATE users SET ... WHERE id = ?", user_id, data)
    # 2. 再删除缓存
    redis.delete(f"user:{user_id}")
```

### Read-Through / Write-Through（读写穿透）

应用只和缓存交互，缓存层负责和数据库同步：

- **Read-Through**：缓存未命中时，缓存层自动查库并回填
- **Write-Through**：应用写入时，缓存层同步写入数据库

优点是对应用透明，缺点是写性能受限。适用于对数据一致性要求高的场景，但一般需要专门的缓存中间件支持。

### Write-Behind（异步写回）

应用只更新缓存就返回成功，缓存层后台异步批量写入数据库：

- **优点**：写性能极高，适合日志、统计计数等场景
- **缺点**：Redis 宕机会丢失未刷盘的数据，一致性最差

### 模式选择指南

| 模式 | 读性能 | 写性能 | 一致性 | 适用场景 |
|------|--------|--------|--------|----------|
| Cache-Aside | 高 | 高 | 中等 | 读多写少，通用场景 |
| Read/Write-Through | 高 | 低 | 高 | 高一致性需求 |
| Write-Behind | 高 | 极高 | 低 | 写密集型，可容忍少量丢失 |

## 缓存一致性问题

Cache-Aside 模式下，先更新数据库再删除缓存，在高并发时可能出现短暂不一致。经典场景：

```
时间线：   线程A（写）              线程B（读）
T1       更新数据库 X=1
T2                               读缓存 → 未命中
T3                               读数据库 → X=0（旧值）
T4       删除缓存
T5                               将 X=0 写入缓存
结果：缓存中是旧值，数据库是新值
```

**延时双删**是解决这个问题的经典方案：

```
1. 删除缓存（清除旧数据）
2. 更新数据库
3. 延迟 500ms ~ 2s 后再次删除缓存（异步执行）
4. 兜底：设置合理的缓存 TTL
```

其他保障手段：
- **设置 TTL**：最简单有效的兜底方案，确保不一致最终被修复
- **Canal + binlog 订阅**：监听数据库变更，异步刷新缓存，实现最终一致性
- **分布式锁**：强一致性场景下，对同一 Key 的读写加锁

## 缓存穿透

### 问题描述

查询一个**数据库和缓存中都不存在**的数据。由于缓存没有命中，请求每次都穿过缓存直接打到数据库。恶意攻击者可以通过遍历大量不存在的 ID 来击穿数据库。

### 解决方案

**布隆过滤器**是最经典的解法——在缓存前面加一层过滤器，用极小的内存快速判断一个 Key 是否存在：

```python
from pybloom_live import BloomFilter

bf = BloomFilter(capacity=1000000, error_rate=0.001)

# 初始化：将所有存在的 ID 加入布隆过滤器
for user_id in db.query("SELECT id FROM users"):
    bf.add(user_id)

def get_user(user_id: str) -> User | None:
    # 布隆过滤器说"不存在"→ 一定不存在，直接返回
    if user_id not in bf:
        return None

    # 布隆过滤器说"可能存在"→ 走正常缓存+数据库流程
    return cache_or_db(user_id)
```

布隆过滤器的特点：**不存在的一定不存在，存在的可能存在**（有误判率）。内存占用极小——1 亿个元素，1% 误判率，仅需约 120MB。

**空值缓存**也是常用手段——对查询结果为空的 Key 也缓存一个短 TTL 的空标记：

```python
def get_user(user_id: str) -> User | None:
    cached = redis.get(f"user:{user_id}")
    if cached == "NULL":
        return None  # 空值缓存命中
    if cached:
        return json.loads(cached)

    user = db.query(...)
    if user:
        redis.setex(f"user:{user_id}", 3600, json.dumps(user))
    else:
        redis.setex(f"user:{user_id}", 300, "NULL")  # 空值缓存 5 分钟
    return user
```

推荐组合：**布隆过滤器 + 空值缓存 + 接口参数校验 + 限流**。

## 缓存击穿

### 问题描述

某个**热点 Key** 在过期瞬间，大量并发请求同时穿透到数据库。这是高并发场景下最危险的时刻——流量尖峰瞬间打满数据库连接池。

热点 Key 的特征：访问频率极高、单 Key 承载大量流量（如首页推荐列表、秒杀商品信息）。

### 解决方案

**互斥锁**——缓存失效时，只让一个线程去查数据库重建缓存，其他线程等待或重试：

```python
import threading
import time

def get_hot_data(key: str):
    data = redis.get(key)
    if data is not None:
        return json.loads(data)

    # 尝试获取重建锁
    lock_key = f"lock:rebuild:{key}"
    if redis.setnx(lock_key, 1):
        try:
            redis.expire(lock_key, 10)  # 防止死锁
            # 双重检查：可能其他线程已经重建完成了
            data = redis.get(key)
            if data is not None:
                return json.loads(data)
            # 查库重建
            data = db.query(...)
            redis.setex(key, 60, json.dumps(data))
        finally:
            redis.delete(lock_key)
    else:
        # 没拿到锁，短暂等待后重试
        time.sleep(0.05)
        return get_hot_data(key)

    return data
```

**逻辑过期**是更适合高并发读场景的方案——Key 不设物理 TTL，在 Value 中嵌入一个逻辑过期时间戳。读取时如果发现逻辑过期，返回旧值的同时**异步**触发重建：

```python
def get_with_logical_expiry(key: str):
    raw = redis.get(key)
    if not raw:
        return rebuild_and_cache(key)

    data = json.loads(raw)
    if data["expire_at"] > time.time():
        return data["value"]  # 未过期，直接返回

    # 逻辑已过期：返回旧值，异步重建
    redis.setnx(f"lock:rebuild:{key}", 1)
    threading.Thread(target=rebuild_and_cache, args=(key,)).start()
    return data["value"]  # 返回旧值，不阻塞
```

| 维度 | 互斥锁 | 逻辑过期 |
|------|--------|----------|
| 一致性 | 好（返回最新数据） | 一般（可能短暂返回旧数据） |
| 性能体验 | 线程需等待 | 无等待，用户体验好 |
| 实现复杂度 | 简单 | 较高（需要异步重建机制） |
| 适用场景 | 更新频繁的热点 | 更新不频繁的热点 |

## 缓存雪崩

### 问题描述

两种情况会触发雪崩：
1. **大量 Key 同时过期**——缓存层在某一时刻大面积失效
2. **Redis 节点宕机**——整个缓存层不可用

无论哪种情况，结果都是所有请求瞬间涌向数据库，在极短时间内耗尽连接池，导致整个系统不可用。

### 解决方案

**随机化过期时间**——给每个 Key 的 TTL 加一个随机偏移，避免集中失效：

```python
import random
base_ttl = 3600              # 1 小时
ttl = base_ttl + random.randint(0, 600)  # 加 0-10 分钟随机偏移
redis.setex(key, ttl, value)
```

**多级缓存**——本地缓存（Caffeine / 进程内存）作为 Redis 的前置缓冲：

```
请求 → 本地缓存(L1) → Redis(L2) → 数据库(L3)
```

即使 Redis 完全宕机，本地缓存仍然能挡掉一部分读流量。

**Redis 高可用部署**：
- Redis Sentinel 实现主从自动切换
- Redis Cluster 分片，单节点故障只影响部分 Key
- 对核心数据不设 TTL，通过后台任务主动刷新

**服务降级熔断**——当数据库压力过大时，对非核心服务返回默认值或限流，保证核心链路可用。

## 三大问题对比总结

| 问题 | 核心原因 | 数据状态 | 影响范围 | 核心方案 |
|------|----------|----------|----------|----------|
| 穿透 | 查不存在的数据 | 缓存无 + DB 无 | 所有无效 Key | 布隆过滤器 + 空值缓存 |
| 击穿 | 热点 Key 过期 + 高并发 | 缓存无 + DB 有 | 单个热点 Key | 互斥锁 / 逻辑过期 |
| 雪崩 | 大量 Key 同时过期 / Redis 宕机 | 缓存大面积失效 | 全局影响 | 随机 TTL + 高可用 + 多级缓存 |

记忆口诀：**穿透布隆空值挡，击穿锁或逻辑抗，雪崩随机多级防。**

## 总结

缓存的难点不在于怎么存取数据，而在于**异常情况下的鲁棒性**。设计缓存方案时，永远要问三个问题：

1. 缓存失效后，数据库能不能扛住？→ 做好容量规划，设置限流熔断
2. 数据不一致能容忍多久？→ 设置 TTL 兜底，选择合适的更新策略
3. 热点数据怎么处理？→ 互斥锁或逻辑过期，避免击穿

记住：缓存不是银弹，它是**最终一致性的妥协**。理解了这一点，你就能在性能和一致性之间做出正确的取舍。
