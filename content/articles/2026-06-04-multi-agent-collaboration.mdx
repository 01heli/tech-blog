## 一、一个人的天花板

假设你有一个很能干的 AI 助手。你给它一个任务——"分析这份 200 页的合同，找出所有风险条款，写一份审核报告"。

它做得不错。但有几个问题：

1. 花了很多时间——它得读完 200 页、逐条分析、写报告，这三个步骤是串行的
2. 分析到第 150 页的时候，它似乎"忘了"前面看过的内容——上下文窗口已经快撑满了
3. 写报告的时候，它没办法同时检查自己有没有漏掉什么东西——因为"分析"和"审查"用的是同一个大脑

你试过让同一个 Agent 做得更好——优化 prompt、加更多 Few-Shot 示例、扩大上下文窗口。确实有改善，但到了一定程度就推不动了。不是你的问题，**是单 Agent 架构就到这个天花板了**。

这时候，一个自然的想法出现了：能不能不给一个人派任务，而是派一个团队？

这就是多智能体协作（Multi-Agent Collaboration）的出发点——**让多个 AI Agent 组成团队，各自负责最擅长的部分，最终协作完成一个人搞不定的事**。

## 二、单 Agent vs 多 Agent：什么时候该加人

在进入具体技术之前，先搞清楚一个关键问题：**你到底需不需要多 Agent？**

Anthropic 的工程师在 2026 年 4 月的一篇博客中写了一句很值得注意的话——"我们见过太多团队花几个月时间搭建复杂的多 Agent 架构，最后发现一个 prompt 写得更好的单 Agent 能拿到同样的效果。"

这不是说多 Agent 没用。而是说：**多 Agent 是一个"问题驱动的架构选择"，不是一个"潮流驱动的技术选型"。**

什么时候单 Agent 就够了，什么时候应该上多 Agent？三个明确信号：

### 信号一：上下文打架

每个 Agent 都有一个上下文窗口——它能同时"记住"的信息是有限的。当你塞给它 5 个不相关的任务、加上它们的输入数据和中间结果，模型就像一个人同时接 5 个电话、回 3 封邮件、还要写一份 PPT。

2026 年学术界做了一个测试：在一个单 Agent 的上下文窗口里塞进 N 个并行子任务，当 N=3 时准确率还能维持在 ~60%，N=10 时掉到 21%。不是因为模型变笨了，而是太多无关信息污染了它的判断——这叫**上下文污染（Context Pollution）**。

**信号：当你发现 Agent 在处理某个子任务时总被其他子任务的信息干扰，就该拆解了。**

### 信号二：任务可以并行

有些任务天生就是独立的。比如"研究 A 公司的市场表现"和"研究 B 公司的财务状况"——两个任务完全不依赖对方的结果。在单 Agent 模式下，只能一个一个做；多 Agent 可以同时并行，Google 内部的实测加速比为 **+81%**。

**信号：如果你能清楚地把大任务拆成独立子任务，多 Agent 的收益就能兑现。**

### 信号三：工具太多让 Agent 犯选择困难

当 Agent 同时面对超过 15-20 个工具时，它选工具的正确率会明显下降。这不是模型的能力问题——换你面对一个摆了 50 种工具的工台，你也要花时间选。解决方案是把工具按职责分配到不同的专业 Agent 身上——财务 Agent 只管财务相关的工具，法务 Agent 只管法务相关的工具。

**信号：当 Agent 开始频繁调错工具时，不是因为模型不够好，而是因为"工具菜单"太长。**

### 反过来，什么时候不该用多 Agent

- **任务本身是串行的，无法拆解**：拆解不了一个任务就不要强行拆。硬拆只会增加通信开销——每个子 Agent 把结果转给下一个的时候都会丢失信息，像传话游戏，转了 3 轮之后最初的意图已经面目全非
- **单 Agent 完全能搞定**：别为了"技术先进"而用多 Agent。实测表明一个 prompt 写得好的单 Agent 跟一个草率设计的多 Agent 系统效果差不多，但后者 token 消耗多了 3-10 倍

> **一个实用的原则：先用单 Agent 做到最好。在明确撞到天花板（上下文打满、串行太慢、工具选不准）之后，再考虑拆成多 Agent。**

## 三、五种协作模式

一旦确定需要多 Agent，下一个问题就是：**它们怎么协作？**

Anthropic 在 2026 年 4 月归纳了五种经生产环境验证的模式。按适用场景从简单到复杂排列：

### 3.1 生成-验证模式（Generator-Verifier）

```
┌────────────┐    产出     ┌────────────┐
│  生成者     │ ───────────→ │  验证者     │
│ Generator │              │ Verifier  │
└────────────┘              └───────────┘
                                   │
                              不通过 │ 通过
                              ┌────┴─────┐
                              │  返回修改  │    输出
                              └──────────┘
```

最基础、最安全的两 Agent 模式。生成者产出内容，验证者检查是否符合标准，不符合就打回去重做。像一个作者和一个编辑——作者负责写，编辑负责挑刺，说不明白就打回重写。

适用场景：合同审核、代码审查、内容校对，任何有明确质量标准的工作。Factory 公司 2026 年发布的文档显示，在它们的多 Agent 代码开发系统中，**37.2% 的总时间被分配给了验证环节**——写代码不是最花时间的，确保代码没问题才是。

### 3.2 编排者-子智能体模式（Orchestrator-Subagent）

```
                   ┌──────────────┐
                   │   编排者      │
                   │ Orchestrator │
                   └──────┬───────┘
                          │ 拆解任务、分派
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ 研究员    │   │ 分析师    │   │ 写手      │
   │Researcher│   │ Analyst  │   │ Writer   │
   └──────────┘   └──────────┘   └──────────┘
```

这是**目前生产环境中使用最广的模式**。编排者收到任务后，自己不动手，而是拆解任务、分派给专业化的子 Agent，最后汇总结果。

核心优势是**关注点分离**——每个子 Agent 有自己干净的上下文窗口，不会被其他人的工作信息污染。编排者的上下文只需要保留"任务调度信息"，子 Agent 的上下文只需要保留"执行所需信息"。互不干扰。

关键设计原则是**上下文驱动的拆分**，而不是问题驱动的拆分。什么叫问题驱动的拆分？"你写代码、你写测试、你审查"——看起来合理，但实际上每个角色都需要理解整个过程，上下文传递成本极高。上下文驱动的拆分则是"你负责认证模块（包括代码+测试+审查）、你负责支付模块"——按信息边界切，每个 Agent 拥有完成自己任务所需的全部上下文。

### 3.3 Agent 团队模式（Agent Teams）

```
┌──────────────────────────────────────────────┐
│                 共享工作空间                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ Agent A  │  │ Agent B  │  │ Agent C  │   │
│  │ (前端)   │  │ (后端)    │  │ (数据库)  │   │
│  └──────────┘  └──────────┘  └──────────┘   │
│        │              │              │        │
│        └──────────────┼──────────────┘        │
│                       ▼                       │
│              ┌─────────────────┐              │
│              │   共享状态/记忆   │              │
│              └─────────────────┘              │
└──────────────────────────────────────────────┘
```

与编排者模式不同，Agent 团队里的成员是长生命周期的——它们在多次任务之间保持自己的状态和记忆。像一支稳定的项目组，不是每次任务都临时组队。

适用场景：需要跨多次任务积累领域知识的长期项目。每个 Agent 在不断处理同类任务的过程中越来越熟练（因为它的记忆在累积相关经验）。

### 3.4 消息总线模式（Message Bus）

Agent 不再直接通信。它们订阅自己关心的"事件"，当某类事件发生时自动被触发。

```
Agent A 发布事件 → [消息总线] → 订阅了该事件的 Agent B/C/D 各自响应
```

适合"生态级"场景——Agent 数量在增长，谁跟谁协作是不确定的，经常会有新的 Agent 加入。消息总线让系统可以不断扩展而不需要重写协调逻辑。

### 3.5 共享状态模式（Shared State）

所有 Agent 共享一个持久化的"工作区"/"白板"——不做中心协调，各自读各自需要的信息，各自写各自的结果。适合需要多个 Agent 在同一个结果上不断叠加贡献的场景，比如协作式研究——你发现一个线索，我接着你的线索深挖。

### 如何选择

```
你需要哪种模式？
├── 输出质量是首要目标 → 生成-验证
├── 任务结构清晰，可分解为独立步骤 → 编排者-子智能体
├── 需要跨多次任务积累经验 → Agent 团队
├── Agent 生态在扩张，协作关系不确定 → 消息总线
└── 多个 Agent 在同一个成果上协作 → 共享状态
```

现实中最常见的做法是组合：**编排者做流程控制 + 子 Agent 内部用生成-验证保证质量**。

## 四、协议层：Agent 之间怎么"说话"

知道了协作模式，还需要解决一个基础设施问题：**Agent 之间怎么通信，Agent 怎么调用各自的工具？**

2026 年，这个领域已形成两个互补的开放标准：

### 4.1 MCP：Agent 和工具之间的协议

MCP（Model Context Protocol，模型上下文协议）解决的是 **Agent ↔ 工具/数据** 之间的连接。一个技术类比：MCP 之于 AI Agent，就像 USB-C 之于硬件设备——你不需要为每个设备配一个专用接口。

过去每接入一个外部工具（数据库、搜索、文件系统），你都得为 Agent 写一套工具描述和调用逻辑。MCP 让你一次写好，所有 Agent 共用。

### 4.2 A2A：Agent 和 Agent 之间的协议

A2A（Agent-to-Agent）解决的是 **Agent ↔ Agent** 之间的通信。核心机制是 Agent Card——每个 Agent 注册时发布一张"数字名片"，写清楚自己能做什么、输入输出格式、端点地址。

当一个 Agent 遇到自己做不了的事情，它去注册中心查——"谁擅长做这个？"——找到对的 Agent Card——发起任务委托——拿到结果继续。

2026 年 A2A 已有超过 150 家企业合作伙伴（包括 Salesforce、SAP、ServiceNow、Atlassian），由 Linux 基金会管理，和 MCP 形成互补：

```
A2A: Agent ↔ Agent（"谁擅长做这个？帮我做一下"）
MCP: Agent ↔ 工具（"帮我查数据库、调 API"）
```

两者的关系可以这样理解：**MCP 是 Agent 的手（伸向世界），A2A 是 Agent 的嘴（互相沟通）。**

## 五、纸上谈兵 vs 实际跑起来

篇幅有限，我们来看具体代码。这里以最常见的编排者-子智能体模式为例，展示两种主流框架的实现方式。

### 5.1 CrewAI：角色化团队

CrewAI 的核心抽象是"角色"——像给真人团队写岗位描述一样定义每个 Agent 的角色和职责。

```python
from crewai import Agent, Task, Crew, Process

# 定义三个专业 Agent——像写岗位 JD 一样写清楚角色和职责
researcher = Agent(
    role="行业研究员",
    goal="找出目标领域的最新趋势和关键数据，输出结构化的研究笔记",
    backstory="你曾在 McKinsey 做了 10 年行业研究，擅长在海量信息中发现结构性洞察。"
)

writer = Agent(
    role="技术写手",
    goal="把研究笔记写成一篇零基础读者也能读懂的文章",
    backstory="你是一个有 8 年经验的技术博主，最擅长把复杂的概念讲得人人都懂。"
)

reviewer = Agent(
    role="主编",
    goal="检查文章是否有事实错误、逻辑漏洞、表达不清的地方，确保符合发表标准",
    backstory="你是前出版社主编，标准高到你手下作者都说你是个'行走的退稿信'。"
)

# 定义任务
research_task = Task(
    description="调查 2026 年多智能体协作的技术趋势和主要玩家",
    expected_output="一份结构化研究笔记，包含至少 3 个关键趋势、2 个标杆公司案例",
    agent=researcher
)

write_task = Task(
    description="基于研究笔记，写一篇 3000 字的技术科普文章",
    expected_output="面向零基础读者的 Markdown 格式文章，包含代码示例",
    agent=writer
)

review_task = Task(
    description="审核文章草稿，检查事实准确性和表达清晰度",
    expected_output="审核意见（通过或需要修改，需要修改的话标注具体位置和原因）",
    agent=reviewer
)

# 组队——顺序执行：先研究 → 再写 → 最后审
crew = Crew(
    agents=[researcher, writer, reviewer],
    tasks=[research_task, write_task, review_task],
    process=Process.sequential
)

result = crew.kickoff(inputs={"topic": "多智能体协作"})
print(result)
```

关键细节：`Process.sequential` 意味着按任务列表的顺序串联执行，每个 Agent 等上一个做完再开始。你不需要手动管理数据传递——CrewAI 内部自动将上一环节的输出递交给下一环节。

### 5.2 LangGraph：状态图编排

LangGraph 的思路与 CrewAI 互补。如果说 CrewAI 是"把任务交给团队"，LangGraph 就是"精确控制流水线的每一步"。基于有向图（DAG），每个节点是一个 Agent，边定义状态转换条件。

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Optional
import operator

class CodeReviewState(TypedDict):
    # 全局状态——所有节点共用
    code: str
    review_notes: Optional[str]
    approved: bool
    retry_count: int

def code_generator(state: CodeReviewState) -> CodeReviewState:
    """生成代码的 Agent。"""
    # 调用 LLM 生成代码...
    return {
        **state,
        "code": generated_code,
        "retry_count": state.get("retry_count", 0)
    }

def code_reviewer(state: CodeReviewState) -> CodeReviewState:
    """审查代码的 Agent。"""
    # 调用 LLM 审查代码...
    if meets_standards:
        return {**state, "review_notes": feedback, "approved": True}
    else:
        return {**state, "review_notes": feedback, "approved": False}

def should_retry(state: CodeReviewState) -> str:
    """决定下一步做什么。"""
    if state["approved"]:
        return "end"
    elif state["retry_count"] >= 3:
        return "end"  # 最多重试 3 次
    else:
        return "coder"  # 打回重做

# 建图：定义节点和边
workflow = StateGraph(CodeReviewState)

workflow.add_node("coder", code_generator)
workflow.add_node("reviewer", code_reviewer)

workflow.set_entry_point("coder")
workflow.add_edge("coder", "reviewer")

# 关键：条件分支——通过就结束，不通过就回到 coder 重做
workflow.add_conditional_edges(
    "reviewer",
    should_retry,
    {
        "end": END,
        "coder": "coder"
    }
)

app = workflow.compile()
result = app.invoke({"code": initial_code, "approved": False, "retry_count": 0})
```

LangGraph 的图模式让你能做 CrewAI 难以精确控制的事——比如**循环重试**（不通过就回去重写，而不是一条路走到黑）和**状态检查点**（程序崩溃后可以从中断处恢复，不需要重头来）。

### 5.3 两者组合

2026 年的生产实践不是二选一，而是组合：**LangGraph 做外层流程控制（什么时候做、做几遍、按什么条件分叉），CrewAI 做内层任务执行（具体的角色分工和协作内容）。**

## 六、翻车记录：多 Agent 生产环境的四个坑

多 Agent 听起来像团队作战，但生产环境中翻车的方式也更多样。以下四个问题来自 2026 年多个团队的生产经验总结。

### 6.1 上下文污染——最隐蔽的坑

当一个编排者 Agent 同时管理 10 个子 Agent 时，所有人的返回结果都在编排者的上下文窗口里。研究数据表明，在这种情况下编排者做出正确路由决策的准确率会从 N=3 的 ~60% 掉到 N=10 的 ~21%。28-57% 的路由决策受到了"其他 Agent 的无关结果"的影响。

解决方案：**保持编排者的上下文干净**。不要让编排者读到子 Agent 的完整执行过程，子 Agent 只返回结果摘要。

### 6.2 通信开销吃掉并行收益

看起来拆成并行可以让速度翻倍，但实际测量发现一个残酷的事实：**子 Agent 花在"跟编排者交代自己做了什么"上的 token，经常比花在"真正干活"上的 token 还多**。UIUC 的研究显示多 Agent 系统的 token 消耗是单 Agent 的 4-220 倍——下限是"搞得好"的情况，上限是"翻车"的情况。

解决方案：按信息边界拆分，不是按角色拆分。让一个 Agent 负责一个完整的上下文块（比如某个功能模块的代码+测试+文档），而不是人为切割成"你写代码、他写测试"。

### 6.3 群体迷思——审查者变点头虫

在生成-验证模式中，验证 Agent 理论上应该"独立、严格、客观"。但当验证 Agent 看到生成 Agent 的推理过程时，它有时会**不自觉地跟随对方的思路**——尤其是当生成 Agent 的推理看起来很"自信"的时候。

更危险的是多审查 Agent 场景：当三个审查 Agent 中两个倾向于"通过"时，第三个经常放弃自己的异议而选择随大流。这削弱了"多数投票"的有效性。

解决方案：**审查 Agent 不应该看到生成 Agent 的中间推理过程，只给它看最终产出**。Factory 公司 2026 年的做法是引入两类验证者——审核者只审代码逻辑（blind review），用户测试者以黑盒方式操作产品（不知道内部实现），确保两条验证路径完全独立。

### 6.4 手递手任务中的信息衰减

类似传话游戏：编排者分解需求 → 传给子 Agent A → A 的结果摘要传回 → 编排者再传给子 Agent B → B 的结果传回。每传一次，原始信息就丢失一点。转了三个 Agent 之后，最初的意图可能已经完全变味。

这不是框架的问题——任何"层层传递"的架构都会面临信息衰减。有实际生产团队（包括微软 Azure SRE 团队）走了一条相反的路："**减少 Agent 数量，扩大每个 Agent 的工具集，需要什么知识让 Agent 自己去查**。"硬拆分不是目标，有效协作才是。

## 七、总结：你的行动指南

| 你的角色 | 优先关注 |
|---------|---------|
| **初学者** | 先用 CrewAI 搭一个三 Agent 流水线（研究员 → 写手 → 审稿员）跑通，理解角色定义和任务分派的基本概念。不用一上来学 LangGraph |
| **开发者** | 从单 Agent 做起，真正撞到天花板（上下文打满/工具太多/串行太慢）再拆。拆的时候按信息边界切，别按角色切 |
| **架构师** | MCP 和 A2A 是基础设施层面的投资——先上 MCP（更成熟、更容易部署），等 Agent 间出现了频繁的跨团队协作需求时再引入 A2A |
| **团队负责人** | 把评估体系建起来再谈架构升级。没有评估，多 Agent 对你来说只是"多个点会出错的地方" |

三个最重要的原则：

1. **单 Agent 优先，多 Agent 是解决问题的手段不是目的**。一个 prompt 写得好的单 Agent 可以走很远
2. **按信息边界拆分，不是按角色拆分**。让每个 Agent 拥有完成自己任务所需的全部上下文，而不是要求它们通过"传话"来拼接信息
3. **把验证当一等公民**。在生产系统中，验证可能要消耗 37% 以上的总时间——这不是浪费，是确保可靠性的必要成本
