## 从一个重复了 100 遍的代码片段说起

假设你正在写一个电商后端。每当你需要排查线上问题时，你都会临时加上几行日志：

```python
def calculate_discount(price, rate):
    print(f"[DEBUG] 调用 calculate_discount({price}, {rate})")  # 临时加的
    return price * rate

def create_order(user_id, items):
    print(f"[DEBUG] 调用 create_order({user_id}, {items})")     # 又加一遍
    ...

def process_payment(order_id, amount):
    print(f"[DEBUG] 调用 process_payment({order_id}, {amount})") # 又双加一遍
    ...
```

问题来了：当你要排查的函数有 50 个时，你在 50 个函数里复制粘贴了同样的 `print`。更糟糕的是，排查完了你还要一个一个删掉——漏删一个就会在生产日志里刷屏。

**有没有一种办法，在不修改原函数代码的情况下，统一给它们加上日志功能？**

这就是装饰器要解决的问题。这篇文章将从零开始，带你彻底理解 Python 装饰器的底层原理、语法演变、实战场景和类型标注。

## 第一部分：在理解装饰器之前，先弄懂三个基础

装饰器的本质并不复杂，但它建立在三个基础概念上。如果你这三个概念都熟悉，可以直接跳到第二部分。

### 1.1 函数是"一等公民"

在 Python 中，函数和整数、字符串一样，都是普通对象：

```python
# 1. 函数可以赋值给变量
def greet(name):
    return f"Hello, {name}"

say = greet              # 把函数对象赋给 say（注意没加括号）
print(say("Alice"))      # Hello, Alice

# 2. 函数可以作为参数传给另一个函数
def apply(func, value):
    return func(value)

print(apply(len, "hello"))  # 5 —— len 被当成参数传进去了

# 3. 函数可以定义在另一个函数内部，并作为返回值返回
def make_power(n):
    def power(x):
        return x ** n
    return power         # 返回 power 这个函数对象本身

square = make_power(2)
print(square(5))         # 25
```

第三点最关键——**函数里面可以定义函数，并且外层函数可以把内层函数当作返回值返回**。这是装饰器的"物理基础"。

### 1.2 闭包——"函数记住了它出生的地方"

```python
def make_counter():
    count = 0                    # count 是 make_counter 的局部变量
    def increment():
        nonlocal count           # 告诉 Python：我要用外层的 count
        count += 1
        return count
    return increment

counter1 = make_counter()
print(counter1())  # 1
print(counter1())  # 2
print(counter1())  # 3

counter2 = make_counter()
print(counter2())  # 1  ← 另一个独立的计数器，从 1 开始
```

你可能注意到一个问题：`make_counter()` 已经执行完毕了，按理说它的局部变量 `count` 应该随着函数返回而被销毁。但为什么 `counter1()` 还能访问并修改它？

答案就是**闭包（Closure）**：当内层函数引用了外层函数的变量，外层函数把这个内层函数返回后，**这个内层函数会把外层函数的变量"打包带在身边"**。这份被打包的变量叫做"自由变量（free variable）"，你可以通过 `__closure__` 属性看到它：

```python
print(counter1.__closure__[0].cell_contents)  # 3 —— 这就是那个活着的 count
```

用一个比喻来理解：**闭包就像你离家上大学时带上的行李箱——箱子里的东西（变量）本来属于你的家乡（外层函数），但你现在走到哪都能用到它们。**

装饰器的本质，就是把"被装饰的函数"当作行李箱里的那样东西——包在闭包里，在上面加一层新逻辑。

### 1.3 `*args` 和 `**kwargs`——万能参数转发

这是最后一个要用到的工具。当你要写一个"我不确定里面是什么函数，但要把所有参数原封不动传给它"的包装时，必须用到它俩：

```python
def wrapper(*args, **kwargs):
    # args = 所有位置参数组成的元组
    # kwargs = 所有关键字参数组成的字典
    result = original_function(*args, **kwargs)
    return result
```

`*args` 吞掉所有位置参数，`**kwargs` 吞掉所有关键字参数。然后你用 `*` 和 `**` 把它们再"拆开"传给原始函数——原封不动，不多不少。

好，三个基础知识都齐了。接下来把它们拼成装饰器。

## 第二部分：装饰器的诞生——从一个手动包装到 @ 语法糖

### 2.1 最原始的装饰器

回到开头的日志需求。用上第一节的知识，可以这样解决：

```python
def add_logging(func):                     # 1. 接收"被装饰的函数"
    def wrapper(*args, **kwargs):          # 2. 定义一个包装函数
        print(f"[DEBUG] 调用 {func.__name__}({args}, {kwargs})")
        result = func(*args, **kwargs)     # 3. 调用原函数
        print(f"[DEBUG] {func.__name__} 返回 {result}")
        return result                      # 4. 返回原函数的结果
    return wrapper                         # 5. 返回包装函数

# 使用
def calculate_discount(price, rate):
    return price * rate

# 手动包装
calculate_discount = add_logging(calculate_discount)

# 现在调用 calculate_discount 就会自动打印日志
calculate_discount(100, 0.8)
# 输出：
# [DEBUG] 调用 calculate_discount((100, 0.8), {})
# [DEBUG] calculate_discount 返回 80.0
```

整个过程的图示：

```
原函数 calculate_discount
        │
        ▼
    add_logging(func)
        │
        │  func = calculate_discount
        │  在 wrapper 里调用 func，前后加 print
        │
        ▼
    返回 wrapper（新的函数对象，包含了旧函数 + 日志功能）
        │
        ▼
calculate_discount = wrapper  ← 名字没变，但已经"升级"了
```

这就是装饰器的全部原理。下面的一切——@语法、@wraps、带参数装饰器——都只是在这个基础模型上的改进和扩展。

### 2.2 @ 语法糖——让代码不再啰嗦

每次都要写 `calculate_discount = add_logging(calculate_discount)` 太丑了。Python 提供了 `@` 语法：

```python
@add_logging
def calculate_discount(price, rate):
    return price * rate

# ↑ 完全等价于 ↓
# calculate_discount = add_logging(calculate_discount)
```

`@add_logging` 的含义就是：**把下一行定义的函数作为参数传给 `add_logging`，然后用它返回的新函数替换原函数。**

语法糖并不改变功能——它只是让代码更好看。但它是理解装饰器的关键一步：看到 `@xxx`，脑子里就自动翻译成 `func = xxx(func)`。

### 2.3 堆叠装饰器——多个装饰器怎么执行？

```python
@decorator_a
@decorator_b
def greet():
    print("你好")

# 等价于：
# greet = decorator_a(decorator_b(greet))
#
# 执行顺序：先 decorator_b 包装，再 decorator_a 包装（由内向外）
# 调用顺序：先执行 decorator_a 的前置逻辑，再执行 decorator_b 的前置逻辑
#           → 原函数 → decorator_b 的后置逻辑 → decorator_a 的后置逻辑
```

用一个更形象的例子：

```python
def bold(func):
    def wrapper():
        return "<b>" + func() + "</b>"
    return wrapper

def italic(func):
    def wrapper():
        return "<i>" + func() + "</i>"
    return wrapper

@bold
@italic
def hello():
    return "Hello"

print(hello())  # <b><i>Hello</i></b>
# 先 italic 包（内层），再 bold 包（外层）
```

**规则：越靠近函数定义的装饰器越先执行。** 就像穿衣服——先穿内衣（italic），再穿外套（bold）。

## 第三部分：修复装饰器的"副作用"——让被装饰函数还是它自己

### 3.1 一个潜伏的 Bug

如果你在第二部分的基础上再加一行这个：

```python
@add_logging
def calculate_discount(price, rate):
    """根据原价和折扣率计算折后价"""
    return price * rate

print(calculate_discount.__name__)  # wrapper  ← 不是 calculate_discount！
print(calculate_discount.__doc__)   # None      ← 文档字符串丢了！
help(calculate_discount)           # 显示的是 wrapper 的文档，不是原函数的
```

这会造成三个实际问题：
1. **调试困难**——你在日志里看到 `wrapper` 而不是 `calculate_discount`，完全不知道是哪个函数报的错
2. **文档丢失**——`help()` 和自动生成的 API 文档都不对
3. **类型信息丢失**——类型检查器（mypy/pyright）失去了原函数的签名信息

### 3.2 一行代码修复：`@functools.wraps`

```python
from functools import wraps

def add_logging(func):
    @wraps(func)                       # ← 这一行解决所有问题
    def wrapper(*args, **kwargs):
        print(f"[DEBUG] 调用 {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@add_logging
def calculate_discount(price, rate):
    """根据原价和折扣率计算折后价"""
    return price * rate

print(calculate_discount.__name__)  # calculate_discount ✅
print(calculate_discount.__doc__)   # 根据原价和折扣率计算折后价 ✅
```

`@wraps(func)` 做的事情很简单：**把原函数 `func` 的元信息（`__name__`、`__doc__`、`__module__` 等）复制到 `wrapper` 上**。这样 wrapper 在外人看来就是原来的函数——但它已经悄悄披了一层外衣。

> **铁律：写装饰器时永远加上 `@wraps(func)`。** 即使现在看起来没什么影响，将来某天在调试时你会感谢当初的自己。

## 第四部分：如何把原函数的返回值正确传递

### 4.1 一个容易被忽视的 Bug

假设你写了这样一个装饰器：

```python
def log_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")
        func(*args, **kwargs)    # ← 这里有问题！
    return wrapper

@log_call
def add(a, b):
    return a + b

result = add(3, 5)
print(result)  # None !!!!!
```

`add(3, 5)` 返回了 `None`，而不是 `8`。原因在于 `wrapper` 调用了 `func()` 但**没有把它的返回值传出去**。

正确的写法：

```python
def log_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")
        result = func(*args, **kwargs)  # 接住返回值
        return result                   # 传出去
    return wrapper
```

这看起来很简单，但它是装饰器所有 Bug 中排名第一的存在——因为代码没报错，只是静默地丢了返回值。**你的装饰器里，`func(...)` 调用的结果一定要 catch 住并 return 出去。**

### 4.2 完整模板：一个"不会出错"的基础装饰器

```python
from functools import wraps

def my_decorator(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        # ===== 前置操作 =====
        # 比如：记录日志、检查权限、开始计时...

        result = func(*args, **kwargs)  # 调用原函数

        # ===== 后置操作 =====
        # 比如：记录日志、转换返回值、结束计时...

        return result  # 别忘记！
    return wrapper
```

这四行骨架是所有装饰器的共同基因。你写的任何装饰器，都是在这个骨架的前置/后置操作区填入不同的逻辑。

## 第五部分：装饰器工厂——让装饰器接受参数

### 5.1 当装饰器本身也需要参数时

前面的装饰器 `@add_logging` 能工作，但它不够灵活。假如你希望有些环境打印日志，有些不打印呢？你希望 `@add_logging(enabled=True)` 这样用：

```python
@add_logging(enabled=True)   # 启用日志
def func1():
    ...

@add_logging(enabled=False)  # 禁用日志
def func2():
    ...
```

这需要**给装饰器加参数**。但 `@` 后面的名字必须是一个函数（或可调用对象），它只能接收**一个参数（被装饰的函数）**。那怎么多传一个 `enabled` 呢？

答案是**再包一层函数**。这一层不是装饰器，而是"装饰器工厂"——用来先接收你给的参数，然后返回一个真正的装饰器：

```python
from functools import wraps

def add_logging(enabled=True):         # 第一层：工厂函数，接收你的参数
    def decorator(func):               # 第二层：真正的装饰器，接收被装饰的函数
        @wraps(func)
        def wrapper(*args, **kwargs):  # 第三层：包装函数
            if enabled:
                print(f"[DEBUG] 调用 {func.__name__}")
            return func(*args, **kwargs)
        return wrapper
    return decorator

@add_logging(enabled=True)             # 注意这里有括号！是函数调用
def greet(name):
    return f"Hello, {name}"

# 执行过程：
# add_logging(enabled=True) → 返回 decorator
# decorator(greet)           → 返回 wrapper
# greet = wrapper
```

### 5.2 嵌套层数速记法

装饰器的嵌套层数有一个简单的规律：

```
你的 @ 语法               对应的嵌套层数          执行过程
─────────────────────────────────────────────────────────────────
@decorator                两层                    decorator(func)
@decorator()              三层                    工厂() → decorator(func)
@decorator(arg=val)       三层                    工厂(arg=val) → decorator(func)
```

**记忆口诀**：
- 不带括号 → 两层嵌套（装饰器本身 + wrapper）
- 带括号（不管有没有参数）→ 三层嵌套（工厂 + 装饰器 + wrapper）

### 5.3 实战示例：可配置重试次数的重试装饰器

```python
import time
from functools import wraps

def retry(max_attempts=3, delay=1.0):
    """重试装饰器工厂
    max_attempts: 最大尝试次数
    delay: 每次重试之间的等待秒数
    """
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts:
                        raise  # 最后一次了，不再重试，直接抛出异常
                    print(f"[重试] {func.__name__} 第 {attempt} 次失败: {e}，{delay}s 后重试...")
                    time.sleep(delay)
        return wrapper
    return decorator

@retry(max_attempts=3, delay=0.5)
def call_external_api(url):
    """调用外部 API，偶尔会超时"""
    import random
    if random.random() < 0.7:
        raise ConnectionError("网络超时")
    return "API 返回数据"

print(call_external_api("https://api.example.com"))
```

## 第六部分：类装饰器——当装饰器需要"记住状态"

### 6.1 用类的 `__call__` 方法做装饰器

基于函数的装饰器有一个限制：**它自己很难维护状态**。比如你想统计某个函数被调用了多少次：

```python
from functools import update_wrapper

class CountCalls:
    def __init__(self, func):
        update_wrapper(self, func)   # 类装饰器的 "wraps 等价物"
        self.func = func
        self.count = 0               # 状态存储在实例属性中

    def __call__(self, *args, **kwargs):
        self.count += 1
        print(f"[计数] {self.func.__name__} 被调用了 {self.count} 次")
        return self.func(*args, **kwargs)

@CountCalls
def process_data():
    pass

process_data()  # [计数] process_data 被调用了 1 次
process_data()  # [计数] process_data 被调用了 2 次
process_data()  # [计数] process_data 被调用了 3 次
```

类装饰器的工作原理：
```
@CountCalls                    等价于：  process_data = CountCalls(process_data)
                                      ↓
                        CountCalls.__init__(self=instance, func=process_data)
                                      ↓
                        现在 process_data 指向 instance（一个 CountCalls 对象）
                                      ↓
                        调用 process_data() 时，Python 执行 instance.__call__()
```

**何时用类装饰器？** 当你需要在装饰器里维护可变状态时（计数器、缓存字典、连接池等）。没有状态需求时，函数装饰器更简洁。

### 6.2 实战示例：基于类的缓存装饰器

```python
from functools import update_wrapper

class Memoize:
    """缓存函数调用结果——相同输入直接返回缓存值"""
    def __init__(self, func):
        update_wrapper(self, func)
        self.func = func
        self.cache = {}             # 用字典做缓存

    def __call__(self, *args, **kwargs):
        # 构造缓存键（注意：这只对可哈希的参数有效）
        key = (args, tuple(sorted(kwargs.items())))
        if key not in self.cache:
            self.cache[key] = self.func(*args, **kwargs)
            print(f"[缓存] 计算 {self.func.__name__}{args} → {self.cache[key]}")
        else:
            print(f"[缓存] 命中 {self.func.__name__}{args}")
        return self.cache[key]

@Memoize
def fibonacci(n):
    """计算斐波那契数列第 n 项"""
    if n < 2:
        return n
    return fibonacci(n - 1) + fibonacci(n - 2)

print(fibonacci(10))  # 只计算 11 个值，其他全部命中缓存
```

注意 `fibonacci` 递归调用自己时，实际上调用的是被装饰后的版本（`Memoize` 实例），所以递归内部的调用也能命中缓存——这是递归 + 装饰器完美配合的经典案例。

## 第七部分：装饰器的类型标注——别让你的装饰器成为类型黑洞

### 7.1 为什么装饰器需要类型标注

在[上一篇文章](/articles/2026-06-02-python-type-annotations)中我们详细讲过 Python 的类型系统。装饰器有一个"类型破坏"的特性——如果你不给它加上正确的类型标注，**被装饰后函数的类型信息会全部丢失**：

```python
# 没有类型标注的装饰器
def log(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@log
def add(a: int, b: int) -> int:
    return a + b

# 类型检查器现在认为 add 是 (... -> Any)，不知道参数类型，不知道返回类型！
result = add(1, 2)  # mypy 认为 result 的类型是 Any
```

### 7.2 基础方案：`TypeVar` + `Callable`

```python
from typing import Callable, TypeVar
from functools import wraps

R = TypeVar("R")   # 代表"任意返回值类型"

def log(func: Callable[..., R]) -> Callable[..., R]:
    @wraps(func)
    def wrapper(*args, **kwargs) -> R:
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper
```

`Callable[..., R]` 意思是"接收任意参数，返回 R 类型的函数"。这比完全没有类型好，但它丢失了参数的具体类型——类型检查器不知道 `add` 的参数是 `int` 和 `int`。

### 7.3 完美方案：`ParamSpec`（Python 3.10+）

```python
from typing import Callable, TypeVar, ParamSpec
from functools import wraps

P = ParamSpec("P")  # 捕获完整的参数签名
R = TypeVar("R")    # 捕获返回值类型

def log(func: Callable[P, R]) -> Callable[P, R]:
    @wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@log
def add(a: int, b: int) -> int:
    return a + b

# 类型检查器完全知道：add(a: int, b: int) -> int ✅
result: int = add(1, 2)  # ✅ 类型正确
```

`ParamSpec` 就像一个"参数签名的拷贝机"——它把 `func` 的参数签名原样复制到 `wrapper` 上。这是目前类型标注装饰器的推荐方案。

### 7.4 带参数装饰器的类型标注

带参数的装饰器（工厂模式）的类型标注会多一层：

```python
from typing import Callable, TypeVar, ParamSpec

P = ParamSpec("P")
R = TypeVar("R")

def retry(
    max_attempts: int = 3,
    delay: float = 1.0,
) -> Callable[[Callable[P, R]], Callable[P, R]]:  # ← 类型比普通装饰器多一层
    def decorator(func: Callable[P, R]) -> Callable[P, R]:
        @wraps(func)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            for attempt in range(1, max_attempts + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts:
                        raise
                    print(f"重试 {attempt}/{max_attempts}: {e}")
                    time.sleep(delay)
        return wrapper
    return decorator
```

返回类型 `Callable[[Callable[P, R]], Callable[P, R]]` 可以拆解为：**"接收一个（P→R）的函数，返回另一个（P→R）的函数"**。

### 7.5 `Concatenate`——当装饰器注入参数时

有时候你的装饰器会给函数**注入**额外参数（比如注入数据库连接、注入当前用户 ID）：

```python
from typing import Callable, TypeVar, ParamSpec, Concatenate

P = ParamSpec("P")
R = TypeVar("R")

def with_user_id(func: Callable[Concatenate[int, P], R]) -> Callable[P, R]:
    """
    自动注入 user_id 作为第一个参数。
    被装饰的函数签名从  (user_id, *args) → R
    变成                  (*args) → R
    """
    @wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        user_id = get_current_user_id()  # 从上下文获取
        return func(user_id, *args, **kwargs)
    return wrapper

@with_user_id
def get_orders(user_id: int, status: str) -> list[dict]:
    ...

# 调用方不需要传 user_id，它被自动注入了
orders = get_orders("pending")  # user_id 由装饰器填入
```

`Concatenate[int, P]` 的意思是把 `int` 类型拼到 `P` 参数列表的最前面——装饰器注入了一个 `int` 参数。

## 第八部分：7 大实战场景——拿来就能用的装饰器

以下是后端开发中最常用的 7 种装饰器。每个都可以复制粘贴到你的项目中直接使用。

### 场景一：性能计时器

```python
import time
from functools import wraps

def timer(func):
    """测量函数执行时间"""
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"[计时] {func.__name__} 耗时 {elapsed:.4f}s")
        return result
    return wrapper
```

### 场景二：调试日志（自动打印参数和返回值）

```python
def debug(func):
    """打印函数调用时的参数和返回值"""
    @wraps(func)
    def wrapper(*args, **kwargs):
        args_repr = [repr(a) for a in args]
        kwargs_repr = [f"{k}={v!r}" for k, v in kwargs.items()]
        signature = ", ".join(args_repr + kwargs_repr)
        print(f">>> {func.__name__}({signature})")
        result = func(*args, **kwargs)
        print(f"<<< {func.__name__} 返回 {result!r}")
        return result
    return wrapper
```

### 场景三：缓存（Memoization）

```python
def memoize(func):
    """缓存函数结果——相同参数直接返回缓存，不再重新计算"""
    cache = {}            # 注意：缓存在装饰器作用域，不在 wrapper 里
    @wraps(func)
    def wrapper(*args, **kwargs):
        key = (args, frozenset(kwargs.items()))
        if key not in cache:
            cache[key] = func(*args, **kwargs)
        return cache[key]
    return wrapper

# 更推荐直接使用标准库
from functools import lru_cache

@lru_cache(maxsize=128)   # 标准库自带 LRU 缓存，别再自己造轮子
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)
```

### 场景四：权限校验

```python
def require_auth(func):
    """检查用户是否已登录"""
    @wraps(func)
    def wrapper(user, *args, **kwargs):
        if not user.is_authenticated:
            raise PermissionError("用户未登录！")
        return func(user, *args, **kwargs)
    return wrapper

@require_auth
def view_profile(user):
    return f"{user.name} 的个人主页"
```

### 场景五：自动重试

前面已经展示过完整实现。标准库风格推荐使用 [tenacity](https://github.com/jd/tenacity) 库：

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=1, max=10))
def call_unreliable_api():
    ...
```

### 场景六：限流器

```python
import time
from functools import wraps

def rate_limit(calls_per_second=5):
    """限制函数每秒最多调用 calls_per_second 次"""
    def decorator(func):
        last_called = [0.0]  # 用列表包装以支持闭包内修改

        @wraps(func)
        def wrapper(*args, **kwargs):
            elapsed = time.perf_counter() - last_called[0]
            min_interval = 1.0 / calls_per_second
            if elapsed < min_interval:
                time.sleep(min_interval - elapsed)
            result = func(*args, **kwargs)
            last_called[0] = time.perf_counter()
            return result
        return wrapper
    return decorator

@rate_limit(calls_per_second=2)
def call_api():
    """每秒最多 2 次调用"""
    print("API 调用中...")
```

### 场景七：输入参数校验

```python
def validate_types(**expected_types):
    """运行时校验函数参数的类型"""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            # 检查位置参数
            arg_names = func.__code__.co_varnames[:len(args)]
            for name, value in zip(arg_names, args):
                if name in expected_types:
                    if not isinstance(value, expected_types[name]):
                        raise TypeError(
                            f"{func.__name__}: 参数 '{name}' 期望 "
                            f"{expected_types[name].__name__}，实际为 {type(value).__name__}"
                        )
            # 检查关键字参数
            for name, value in kwargs.items():
                if name in expected_types:
                    if not isinstance(value, expected_types[name]):
                        raise TypeError(
                            f"{func.__name__}: 参数 '{name}' 期望 "
                            f"{expected_types[name].__name__}，实际为 {type(value).__name__}"
                        )
            return func(*args, **kwargs)
        return wrapper
    return decorator

@validate_types(name=str, age=int)
def create_user(name, age):
    return f"User: {name}, {age}"

create_user("Alice", 30)    # ✅
create_user("Bob", "三十")  # ❌ TypeError: 参数 'age' 期望 int，实际为 str
```

### 场景速查表

| 场景 | 推荐方案 | 复杂度 |
|------|----------|--------|
| 打印日志 | 手写 `@debug` 装饰器 | ⭐ |
| 测量性能 | 手写 `@timer` 装饰器 | ⭐ |
| 缓存结果 | `functools.lru_cache`（标准库） | ⭐ |
| 权限校验 | 手写 `@require_auth` | ⭐⭐ |
| 失败重试 | `tenacity` 库 | ⭐⭐ |
| 限流 | 手写或 `ratelimit` 库 | ⭐⭐ |
| 参数校验 | 手写 + Pydantic | ⭐⭐⭐ |

## 第九部分：装饰器 vs 其他方案——什么时候不该用装饰器

### 9.1 装饰器 vs 上下文管理器

```python
# 装饰器方式：适合"每次调用这个函数"都要做的事
@timer
def process():
    ...

# 上下文管理器方式：适合"某一段代码"需要做的事
with Timer() as t:
    process()
    do_other_things()
```

### 9.2 装饰器 vs 显式调用

```python
# 装饰器：适合横切关注点（cross-cutting concerns）
# 日志、缓存、认证——这些和业务逻辑无关，但散布在所有函数中

# 显式调用：适合业务逻辑本身
# 如果逻辑和业务紧密耦合，不要硬塞进装饰器里
def process_order(order):
    validate(order)       # 这就是业务逻辑的一部分，别用装饰器
    calculate_total(order)
    save(order)
```

### 9.3 什么时候不该用装饰器

1. **逻辑和业务强耦合**——如果只有 2 个函数用得到，别写装饰器，直接写在函数里
2. **需要访问函数的内部变量**——装饰器只能看到参数和返回值，看不到函数内部
3. **过度抽象**——如果你发现自己写了 5 层嵌套的装饰器工厂，是时候重新想想设计

## 第十部分：避坑指南

### 坑一：可变默认参数当缓存

```python
# ❌ 错误：cache={} 作为默认参数，所有调用共享同一个字典（Python 默认参数只求值一次）
def bad_memoize(func, cache={}):
    ...

# ✅ 正确：在装饰器函数体内定义 cache
def good_memoize(func):
    cache = {}   # 每次装饰新函数时创建新的 cache
    @wraps(func)
    def wrapper(*args):
        if args not in cache:
            cache[args] = func(*args)
        return cache[args]
    return wrapper
```

### 坑二：装饰器顺序搞错

```python
@login_required    # 先执行的（外层）——先检查登录
@rate_limit(5)     # 后执行的（内层）——再检查限流
def api():
    ...
# 错误顺序的话，限流检查在登录之前就没意义了——攻击者可以绕过登录直接消耗限流配额
```

### 坑三：装饰器里吞掉了异常但不返回

```python
# ❌ 错误：异常被吞掉，且没有 return
def safe_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        try:
            func(*args, **kwargs)  # 没 return！
        except Exception as e:
            print(f"Error: {e}")
    return wrapper

# ✅ 正确：要么返回默认值，要么重新抛出
def safe_call(default=None):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            try:
                return func(*args, **kwargs)  # 正常情况也要 return
            except Exception as e:
                print(f"Error: {e}")
                return default  # 异常时返回默认值
        return wrapper
    return decorator
```

### 坑四：装饰器工厂忘记 return

```python
# ❌ 错误：retry 不是装饰器工厂，它只是返回了 decorator，但忘记 return decorator
def retry(times):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for _ in range(times):
                try:
                    return func(*args, **kwargs)
                except:
                    pass
        return wrapper
    # ← 这里没有 return decorator！！Python 隐式返回 None

# ✅ 正确：最外层函数必须 return decorator
def retry(times):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            ...
        return wrapper
    return decorator  # ← 必须有这一行
```

## 总结

装饰器是 Python 中最优雅的"横切关注点"解决方案——不需要修改函数内部代码，就能统一添加日志、计时、缓存、认证等横向功能。

这篇文章覆盖了从入门到生产的五个层次：

1. **原理层**——函数是一等公民 → 闭包 → 装饰器 = `func = decorator(func)`
2. **语法层**——`@` 语法糖、`@wraps` 保留元信息、`*args/**kwargs` 万能转发
3. **进阶层**——装饰器工厂（带括号）、类装饰器（带状态）、堆叠顺序
4. **类型层**——`ParamSpec` + `TypeVar` 让被装饰函数不丢失类型信息
5. **实战层**——7 个拿来就用的装饰器，覆盖日志、计时、缓存、认证、重试、限流、校验

装饰器不是什么黑魔法——它只是一个把函数包在另一个函数里的模式。一旦你理解了 `func = decorator(func)` 这一行，剩下的全部是这套模式的变体。

### 给不同角色的建议

**给后端开发**：立即在你项目中的日志、认证、缓存三个方向使用装饰器。这三个场景收益最大，实现最简单。对于重试和限流，优先考虑 `tenacity` 和标准库的 `lru_cache`，不要重复造轮子。

**给新手**：先别学类装饰器和 ParamSpec。从最简单的 `def timer(func):` 开始，把"无参数两层嵌套"写熟练。然后逐渐加上 `@wraps`，再尝试"有参数三层嵌套"。装饰器的学习曲线是阶梯式的——每多一层嵌套都是一次顿悟。

**给框架/库作者**：你的公共 API 的每个装饰器都必须加上 `ParamSpec` 类型标注。你的用户依赖 IDE 的类型提示来正确使用你的装饰器——一个没有标注的装饰器可能在用户代码里埋下类型黑洞。

**给所有 Python 开发者**：下次你发现自己在三个以上的函数里复制粘贴了相同的前后逻辑时，停下来——**这就是装饰器在向你招手**。
