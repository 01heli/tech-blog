## 为什么你的查询这么慢？

慢查询是每个后端工程师的噩梦。当数据量从百万增长到千万级别时，原本正常运行的 SQL 可能突然成为系统瓶颈。

```sql
EXPLAIN SELECT * FROM orders
WHERE user_id = 10086
AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

使用 `EXPLAIN` 分析执行计划是第一步。但真正想要理解 MySQL 为什么选择某个执行计划，需要从索引的底层数据结构说起。

## B+Tree 索引的本质

MySQL InnoDB 引擎使用 B+Tree 作为索引数据结构。理解它的特性是写出高效查询的基础。

### 为什么是 B+Tree？

| 数据结构 | 等值查询 | 范围查询 | 排序 | 磁盘友好 |
|----------|----------|----------|------|----------|
| 哈希表 | O(1) | 不支持 | 不支持 | 差 |
| 二叉搜索树 | O(logN) | 支持 | 支持 | 差（树太高） |
| B 树 | O(logN) | 支持 | 支持 | 较好 |
| **B+Tree** | **O(logN)** | **优秀** | **优秀** | **最佳** |

B+Tree 相比 B 树的核心优势：

1. **所有数据存储在叶子节点**，非叶子节点仅存储索引键值和指针。这意味着单个非叶子节点可以容纳更多的键，树的高度更低（通常 3-4 层即可存储千万级数据）
2. **叶子节点之间通过双向链表连接**，天然支持高效的范围查询和排序扫描
3. 每次磁盘 I/O 读取一个节点（InnoDB 默认 16KB 页），低树高意味着更少的磁盘 I/O

### 聚簇索引 vs 二级索引

这是理解 MySQL 查询性能最关键的概念：

```
聚簇索引 (Clustered Index)
├── 叶子节点存储：完整的数据行
├── 每表有且仅有 1 个（通常是主键）
└── InnoDB 默认使用主键构建聚簇索引

二级索引 (Secondary Index)
├── 叶子节点存储：索引键 + 主键值
├── 可以有多个
└── 查询需要"回表"：二级索引 → 主键 → 聚簇索引 → 完整行
```

**回表**是 MySQL 查询中最常见的性能消耗来源。每次通过二级索引找到主键后，都需要再到聚簇索引中读取完整行数据，这相当于一次额外的随机磁盘 I/O。

**推荐使用自增 BIGINT 主键**的两个原因：
- 顺序写入，避免页分裂和页合并
- 主键本身占用空间小，二级索引叶子节点存储的主键值也更小

## 联合索引与最左前缀法则

联合索引是 MySQL 中最强大也最容易被误解的优化手段。

对于联合索引 `idx(a, b, c)`，B+Tree 会按照 `a → b → c` 的顺序进行排序。这意味着：

```sql
-- ✅ 全部命中：a 等值 + b 等值 + c 等值
WHERE a = 1 AND b = 2 AND c = 3

-- ✅ 命中 a 和 b：等值条件之后的范围条件依然可以使用
WHERE a = 1 AND b > 2 AND c = 3
-- 注意：c 列在这里失效，因为 b 是范围条件

-- ⚠️ 仅命中 a：跳过了中间列 b
WHERE a = 1 AND c = 3

-- ❌ 完全无法使用：跳过了最左列 a
WHERE b = 2 AND c = 3
```

MySQL 8.0 的**索引跳跃扫描 (Index Skip Scan)** 部分解决了这个问题——当最左列的唯一值很少时，优化器可以自动"跳过"最左列。但这个特性有限制条件，不应依赖它来弥补索引设计缺陷。

### 联合索引的设计法则

1. **等值列在前，范围列在后** — 范围条件之后的索引列会失效
2. **高区分度列优先** — 能过滤更多数据的列放前面
3. **高频查询列放最左** — 尽量让更多查询能用上最左前缀
4. **ORDER BY / GROUP BY 列纳入索引** — 避免 filesort 和 temporary

## 覆盖索引：终极优化手段

当一个查询需要的**所有列**都包含在索引中时，MySQL 可以直接从索引的叶子节点返回数据，完全避免回表操作。

```sql
-- 假设存在联合索引 idx_user_status_time(user_id, status, created_at)

-- ✅ 覆盖索引：查询列全部在索引中
SELECT user_id, status, created_at FROM orders
WHERE user_id = 10086 AND status = 'paid';
-- Extra: Using index （无需回表）

-- ❌ 需要回表：SELECT * 包含索引中没有的列
SELECT * FROM orders
WHERE user_id = 10086 AND status = 'paid';
-- Extra: Using index condition （需要回表）
```

覆盖索引在**深分页场景**中效果尤为显著：

```sql
-- ❌ 传统深分页：需要扫描 100020 行并全部回表，然后丢弃前 100000 行
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- ✅ 覆盖索引 + 延迟关联：先在索引中定位 20 个 id，再回表取整行
SELECT o.* FROM orders o
JOIN (
  SELECT id FROM orders ORDER BY id LIMIT 100000, 20
) tmp ON o.id = tmp.id;
```

在 500 万数据量下，这种优化可以将响应时间从 2 秒降到 20 毫秒。

但覆盖索引也不是免费的——索引越宽，写入性能越低，存储空间越大。在查询性能和写入性能之间需要做权衡。

## EXPLAIN 执行计划深度解读

`EXPLAIN` 的输出是优化器给出的"查询计划"，理解每个字段的含义是排查慢查询的基础。

### type：访问类型（从优到劣）

```
system  >  const  >  eq_ref  >  ref  >  range  >  index  >  ALL
  ★★★★★     ★★★★★     ★★★★☆    ★★★★☆    ★★★☆☆    ★★☆☆☆    ★☆☆☆☆
```

| type | 含义 | 示例 |
|------|------|------|
| `const` | 主键或唯一索引等值匹配，最多返回一行 | `WHERE id = 1` |
| `eq_ref` | JOIN 时，前表每行在后表唯一索引上匹配一行 | `JOIN ON a.id = b.id` |
| `ref` | 非唯一索引等值匹配，可能返回多行 | `WHERE user_id = 10086` |
| `range` | 索引范围扫描 | `WHERE id > 100 AND id < 200` |
| `index` | 全索引扫描（比全表扫描好一点） | 覆盖索引但无 WHERE 条件 |
| `ALL` | 全表扫描 | 没有可用索引，或优化器认为全表更快 |

**key_len** 字段也值得关注——它告诉你联合索引实际使用了多少列。如果 `key_len` 小于预期，说明部分索引列没有生效。

### Extra：需要警惕的信号

| Extra 值 | 评价 | 说明 |
|----------|------|------|
| `Using index` | 优秀 | 覆盖索引，无需回表 |
| `Using index condition` | 良好 | 索引下推（ICP），存储引擎层过滤 |
| `Using where` | 正常 | 在 Server 层用 WHERE 过滤 |
| `Using filesort` | **需要优化** | 无法利用索引排序，需要额外排序操作 |
| `Using temporary` | **严重** | 需要临时表，常见于 GROUP BY 和 DISTINCT 使用不当 |

出现 `Using filesort` 或 `Using temporary` 时，应优先考虑通过添加或调整索引来消除。

## 索引失效的常见场景

实际操作中，索引"莫名其妙"失效是最让人困惑的。以下是 9 种高频失效场景：

| 序号 | 场景 | 原因 | 解决方案 |
|------|------|------|----------|
| 1 | 违反最左前缀 | B+Tree 按列序组织 | 调整索引列顺序或查询条件 |
| 2 | 索引列上使用函数 | `WHERE YEAR(created_at) = 2026` | 改为范围查询 |
| 3 | 隐式类型转换 | 字符串列传入数字 | 统一参数类型 |
| 4 | LIKE `'%xxx'` | 前缀模糊无法定位 | 全文索引或 ES |
| 5 | OR 连接非索引列 | 存在非索引条件 | 改写为 UNION ALL |
| 6 | `!=` 或 `NOT IN` | 无法通过索引高效定位 | 改为正向条件 |
| 7 | `IS NOT NULL` | 优化器倾向全表扫描 | 设计时避免大量 NULL |
| 8 | 范围列后的索引失效 | `idx(a,b,c)` 中 a 范围后 b,c 失效 | 等值列放前，范围列放后 |
| 9 | 优化器主动放弃索引 | 认为回表代价太高 | ANALYZE TABLE 更新统计信息 |

## 慢查询优化的完整流程

### Step 1：发现慢查询

```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;           -- 超过 1 秒记录
SET GLOBAL min_examined_row_limit = 1000; -- 至少扫描 1000 行
```

使用 Percona Toolkit 中的 `pt-query-digest` 分析慢查询日志，按执行时间和频率排序。

### Step 2：分析执行计划

对每个慢查询执行 `EXPLAIN`，重点看 type、key、key_len、rows、Extra。也可以使用 `EXPLAIN ANALYZE`（MySQL 8.0.18+）获取实际的执行时间分布。

### Step 3：选择优化策略

优化从低代价到高代价依次考虑：

1. **SQL 层面** — 添加/调整索引、重构查询、消除 SELECT *、分页优化
2. **表结构层面** — 合理的字段类型、反范式化、避免 NULL
3. **配置层面** — `innodb_buffer_pool_size`（建议设为可用内存的 70-80%）
4. **架构层面** — 读写分离、分库分表、引入 Redis 缓存

### Step 4：验证效果

对比优化前后的 `EXPLAIN` 输出和实际执行时间。使用 `ANALYZE TABLE` 更新统计信息后再测试。

## 总结

MySQL 查询优化的核心可以概括为**四个减少和三个利用**：

- **减少数据访问量** — 只查需要的列，利用覆盖索引避免回表
- **减少返回数据量** — 分页查询，避免 SELECT *
- **减少交互次数** — 批量操作，合理使用 JOIN
- **减少服务器开销** — 避免函数操作索引列，消除 filesort
- **利用索引覆盖** — 让查询从索引直接获取数据
- **利用内存缓存** — 调大 buffer pool，让热数据常驻内存
- **利用并行能力** — MySQL 8.0 的并行查询、并行 DDL

优化没有银弹。每一条 EXPLAIN 输出、每一次慢查询日志，都在告诉你数据库的真实想法。用数据驱动优化，而不是凭直觉建索引。
