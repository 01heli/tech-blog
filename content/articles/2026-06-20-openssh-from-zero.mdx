## 一、一个你每天都在做，但可能从未认真想过的事

打开终端，敲下这行命令：

```bash
ssh root@192.168.1.100
```

输入密码，回车。一秒钟后，你"进入"了另一台电脑。这个过程太平常了，平常到你不会去想在敲下回车的那一瞬间，网络上到底发生了什么——你的密码是怎么传过去的？会不会被人偷看到？对面那台机器怎么证明它就是你要连的那台，而不是有人在冒充？

回到 1995 年。芬兰赫尔辛基理工大学的研究员 Tatu Ylönen 也遇到了类似的困惑。那年年初，学校网络遭到了一次密码嗅探攻击——攻击者在网络设备上安装了抓包程序，所有通过 Telnet 传输的用户名和密码被一览无余。Telnet 是当时的标配，但它有一个致命缺陷：**所有数据明文传输，包括密码**。

Ylönen 决定自己动手解决这个问题。他设计了一套协议，让客户端和服务器之间的所有通信都经过加密。他把它叫做 **Secure Shell**，简称 SSH。1995 年 7 月，ssh-1.0.0 作为免费软件发布。

```
Telnet 时代（明文传输）：
  你 ──"login: admin"──→ 网络 ──"login: admin"──→ 服务器
  你 ──"password: 123456"──→ 网络 ──"password: 123456"──→ 服务器
                              ↑
                         任何人都能看到

SSH 时代（加密传输）：
  你 ──"a7f3c9e1..."──→ 网络 ──"a7f3c9e1..."──→ 服务器
                            ↑
                       看到的只是乱码
```

这就是 SSH 最核心的价值：在不安全的网络上建立一条安全的加密通道。

但如果你以为 SSH 只是一个"加密版的 Telnet"，那你就严重低估它了。现代 OpenSSH 是一套精密的三层协议栈，包含了密钥协商、身份认证、通道复用、端口转发、文件传输等一整套能力。本文的目标就是从零开始，把你每天都在用的 `ssh` 命令彻底拆解清楚。

## 二、理论基础：SSH 是什么，从哪来，为什么要三层

### 2.1 从 SSH-1 到 SSH-2：一段绕不开的历史

SSH 协议经历了两个大版本，这个历史背景对于理解今天的很多设计决策至关重要。

**SSH-1（协议版本 1.3 / 1.5）** 诞生于 1995 年。它解决了一个真问题——加密通信——但有两个绕不开的硬伤：

第一个是专利问题。SSH-1 使用 RSA 算法做密钥交换和身份认证，而 RSA 算法在当时的美国是受专利保护的。这意味着在美国境内分发和使用 SSH 软件存在法律风险。

第二个是安全问题。SSH-1 使用 **CRC（循环冗余校验）** 来做数据完整性校验。CRC 的设计目标本是检测传输过程中的偶然比特错误（比如网线干扰造成的比特翻转），它根本就不是为对抗恶意攻击而设计的。攻击者可以在传输中插入数据而不会被校验机制发现——这被称为"插入攻击"（insertion attack）。

更麻烦的是，Ylönen 在 1995 年底成立了 SSH Communications Security 公司，将 SSH 商业化。后续版本的许可证越来越严格——限制商业使用、禁止移植到 Windows 等非 Unix 平台。社区开始寻找替代方案。

**SSH-2（协议版本 2.0）** 正是为了修补 SSH-1 的所有缺陷而设计的，后来成为了 IETF 标准（RFC 4250–4254）。它的关键改进包括：

| 改进维度 | SSH-1 | SSH-2 |
|---------|-------|-------|
| 密钥交换 | RSA（专利受限） | Diffie-Hellman（无专利） |
| 数据完整性 | CRC（可被攻击） | HMAC（密码学安全） |
| 协议架构 | 单体协议 | 分三层，每层独立 |
| 会话复用 | 不支持 | 单 TCP 连接上多路复用多个会话 |
| 文件传输 | 无标准支持 | 内置 SFTP 协议 |

> **重要提示：** OpenSSH 从 7.6 版本（2017 年 10 月发布）开始已经彻底移除了对 SSH-1 协议的支持。如果你手上的服务器还在运行 SSH-1，现在就应该升级。

### 2.2 OpenSSH 的诞生：社区对封闭协议的回答

1999 年，开源社区对商业 SSH 的封闭许可证已经忍无可忍。Björn Grönvall 拿了最后一个自由许可的 ssh-1.2.12 版本，修了几个 bug，做出了 OSSH。但 OSSH 只支持 SSH-1.3 协议，而且代码质量参差不齐。

同年 9 月，OpenBSD 项目的开发者们接手了 OSSH 的代码，开始了闪电般的重构。他们的目标很明确：

1. **代码要干净**——方便安全审计，每一行都能被独立审查
2. **协议要全**——SSH 1.5 和 SSH 2.0 都要支持
3. **许可证要自由**——BSD 许可证，不设任何限制

1999 年 12 月 1 日，OpenSSH 1.2.2 随 OpenBSD 2.6 正式发布。核心开发者 Markus Friedl 在短短几个月内就实现了 SSH 2.0 协议支持。2000 年 6 月，OpenSSH 2.0 发布，同时兼容 SSH-1 和 SSH-2。

今天，OpenSSH 是世界上使用最广泛的 SSH 实现。你用的 Mac、Ubuntu、CentOS、Debian，甚至 Windows 10 以后的版本，都内置了 OpenSSH。

### 2.3 三个层次：理解 SSH 协议的正确姿势

SSH-2 协议最精妙的设计，就是把它拆成了三个独立的层次。理解这三层，是理解 SSH 一切工作机制的基础。

```
┌──────────────────────────────────────────────┐
│         SSH-CONNECT（连接协议层）               │
│  RFC 4254                                    │
│  负责：会话 (shell)、端口转发、X11 转发         │
│        SFTP、Agent 转发                       │
│  "在安全通道上开辟多个逻辑信道"                  │
├──────────────────────────────────────────────┤
│        SSH-USERAUTH（用户认证层）               │
│  RFC 4252                                    │
│  负责：密码认证、公钥认证、键盘交互式认证         │
│        GSSAPI 认证、主机认证                   │
│  "向服务器证明你的身份"                         │
├──────────────────────────────────────────────┤
│         SSH-TRANS（传输层）                     │
│  RFC 4253                                    │
│  负责：算法协商、密钥交换、服务器身份验证          │
│        加密/解密、完整性校验、压缩               │
│  "建立一条加密管道"                            │
└──────────────────────────────────────────────┘
          │
          ▼
    TCP 连接（默认 22 端口）
```

这三层的关系可以用一个生活类比来理解：

> **传输层**相当于你在两个房间之间拉了一根密封的管道。管道本身是安全的——外面的人看不到里面在传什么，也没法往里塞东西。**认证层**相当于你在管道那头的房间里出示身份证，证明"我就是我"。**连接层**相当于你在管道里同时跑了好几条线——一根打电话、一根传文件、一根控制远程桌面——它们互相不干扰。

这种分层设计的最大好处是：每一层可以独立演进。你可以在传输层升级加密算法（比如从 AES-128 换成 AES-256）而不影响认证层和连接层的逻辑。同理，你可以在认证层增加双因素认证，而不需要改动传输层的一行代码。

## 三、深入解析：一次 SSH 连接的全过程

现在让我们打开引擎盖，看看在你敲下 `ssh` 命令的那一秒内，到底发生了什么。

### 3.1 第一阶段：TCP 连接与版本交换

SSH 客户端首先和服务器在 22 端口建立 TCP 连接。TCP 连接建立后，双方做的第一件事不是加密，而是互相报一下"我是谁"：

```
客户端 → 服务器: SSH-2.0-OpenSSH_9.7p1 Debian-7\r\n
服务器 → 客户端: SSH-2.0-OpenSSH_9.6p1 Ubuntu-3\r\n
```

这是一个纯文本的字符串，格式为 `SSH-<主版本>.<次版本>-<软件名及版本>`。为什么是明文？因为此刻双方还没有协商好用什么加密算法——鸡生蛋蛋生鸡的问题。这个版本交换同时也是双向的协议兼容性检测：如果客户端只支持 SSH-2.0 而服务器只支持 SSH-1.5，连接在这一步就会中止。

### 3.2 第二阶段：算法协商（SSH_MSG_KEXINIT）

版本交换完成后，双方各自发送一条 `SSH_MSG_KEXINIT` 消息，里面列出了自己支持的算法清单。每条消息包含了以下类别的算法列表，按优先级从高到低排列：

```
┌─────────────────────┬──────────────────────────────────┐
│  算法类别             │  举例                             │
├─────────────────────┼──────────────────────────────────┤
│  密钥交换 (KEX)       │  curve25519-sha256               │
│                      │  diffie-hellman-group14-sha256    │
├─────────────────────┼──────────────────────────────────┤
│  服务器主机密钥       │  ssh-ed25519                     │
│                      │  rsa-sha2-512                    │
├─────────────────────┼──────────────────────────────────┤
│  对称加密 (C→S)      │  chacha20-poly1305@openssh.com   │
│  对称加密 (S→C)      │  aes256-gcm@openssh.com          │
├─────────────────────┼──────────────────────────────────┤
│  MAC 完整性校验       │  hmac-sha2-256-etm@openssh.com   │
│                      │  umac-128-etm@openssh.com        │
├─────────────────────┼──────────────────────────────────┤
│  压缩 (可选)          │  none, zlib@openssh.com          │
└─────────────────────┴──────────────────────────────────┘
```

**协商规则很简单：取双方列表的交集，选客户端列表中最靠前的那一个。** 比如客户端最优先选 `chacha20-poly1305`，而服务器也支持它，那就用它。如果服务器不支持，就继续往下找，直到在服务器列表中找到第一个匹配项。

这里有一个初学者经常忽略的设计细节：**C→S 和 S→C 的算法是独立协商的**。这意味着从客户端到服务器的加密算法可以和从服务器到客户端的不同——虽然实践中大家通常会选成一样。

### 3.3 第三阶段：Diffie-Hellman 密钥交换

算法协商好了，接下来要做的是让双方安全地商定一个"共享秘密"——只有双方知道、任何窃听者都无法推导出来的密钥。这就是密钥交换（Key Exchange）。

现代 SSH 最常用的密钥交换算法是 **Diffie-Hellman 密钥交换**（更准确地说，是基于椭圆曲线的 ECDH，即 Curve25519）。它的数学原理极其巧妙：

```
前提条件：双方约定一个大质数 p 和一个生成元 g（这些都是公开的）

客户端                                    服务器
选择一个秘密随机数 x                      选择一个秘密随机数 y
计算 e = g^x mod p                      计算 f = g^y mod p
                                        收到 e 后计算 K = e^y mod p
        ──── 发送 e ───→
        ←── 发送 f + 签名 ──              用自己的主机私钥对哈希值签名
收到 f 后计算 K = f^x mod p              发送签名 + f
验证签名，确认服务器身份
```

关键点在于：**x 从未离开过客户端，y 从未离开过服务器**。攻击者可以看到 e 和 f（它们在网络上传输），但要从 e 和 f 反推出 K，需要解决离散对数问题——一个目前没有高效算法的数学难题。用大白话说：根据公开的 e 和 f 算出秘密 K，这个计算量之大连当今最强大的计算机都束手无策。

计算出的共享秘密 K 和交换过程中产生的哈希值 H 接下来被送入一个**密钥派生函数（KDF）**，生成六把不同的密钥：

```
初始向量 C→S:  hash(K || H || "A" || session_id)
初始向量 S→C:  hash(K || H || "B" || session_id)
加密密钥 C→S:  hash(K || H || "C" || session_id)
加密密钥 S→C:  hash(K || H || "D" || session_id)
完整性密钥 C→S: hash(K || H || "E" || session_id)
完整性密钥 S→C: hash(K || H || "F" || session_id)
```

为什么要六把钥匙而不是一把？这是密码学中的一个基本原则：**每个方向、每种用途各用各的密钥**。如果只用一个密钥加解密两个方向的所有数据，一旦某个方向的密钥被破解，另一个方向也会跟着沦陷。

### 3.4 第四阶段：服务器身份验证

在整个密钥交换过程中，有一个至关重要但容易被忽略的环节：**服务器身份验证**。

在你第一次连接一台新服务器时，你会看到这样的提示：

```
The authenticity of host '192.168.1.100 (192.168.1.100)' can't be established.
ED25519 key fingerprint is SHA256:gXrI3YxHq1MwJ2vN8kF5aL7dQj4tB6mC9sZ0wP3rU8.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

很多人看到这个提示就直接敲 `yes` 然后继续了。但这个提示恰恰是 SSH 安全模型中最脆弱的一环——**信任首次使用（TOFU, Trust On First Use）**。

服务器在密钥交换过程中，会用自己的主机私钥对关键数据进行签名。客户端收到签名后，用服务器的主机公钥验证——但前提是客户端知道"正确"的公钥长什么样。第一次连接时，客户端无从判断，于是它把公钥存到 `~/.ssh/known_hosts` 文件里，下次连接时比对。

```
~/.ssh/known_hosts 长这样：
192.168.1.100 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGx...
```

如果有人在你第一次连接时冒充了那台服务器（DNS 劫持、ARP 欺骗等），你就会把攻击者的公钥当成"正确"的公钥存下来，之后的每一次"加密"通信实际上都是在跟攻击者对话——这就是**中间人攻击（MITM）**。

**最佳实践：** 拿到一台新服务器后，通过带外渠道（管理后台、短信、电话）获取主机密钥指纹，在 `yes/no` 提示处手动比对。或者使用 SSH 证书（SSH Certificate）机制，由受信任的 CA 签发主机证书，彻底消除 TOFU 问题。

### 3.5 第五阶段：用户认证

加密通道建立后，客户端发起认证请求。SSH 支持多种认证方式，服务器会根据配置列出可用的认证方法列表，客户端依次尝试：

```
客户端 → 服务器: SSH_MSG_SERVICE_REQUEST "ssh-userauth"
服务器 → 客户端: SSH_MSG_USERAUTH_FAILURE (可用的方法: publickey,password)

方式 1: 公钥认证（推荐）
  客户端: "我要用 ssh-ed25519 密钥认证"
  服务器: "好，用这个随机数（challenge）来证明你持有私钥"
  客户端: 用私钥对 challenge 签名 → 发送签名
  服务器: 用 authorized_keys 中的公钥验证签名 → OK

方式 2: 密码认证（不推荐）
  客户端: "我用密码认证，用户名 root，密码 ********"
  服务器: 验证 /etc/shadow → OK

方式 3: 键盘交互式（用于 2FA）
  服务器: "请输入验证码："（通过 PAM 模块触发）
  客户端: "123456"
```

这里需要澄清一个常见的误解：**在公钥认证中，你的私钥从未离开过你的机器**。服务器发送一个随机 challenge，你用私钥对它签名，服务器用你预先部署的公钥验证签名。整个过程中私钥没有通过网络传输——它只是在你本地的内存里做了一次数学运算。

### 3.6 第六阶段：通道复用

认证通过后，连接协议层开始工作。SSH 最强大的特性之一，是它能够在单一 TCP 连接上同时运行多个"通道"：

```
一条 TCP 连接（端口 22）
├── Channel 0: 交互式 Shell (pty)
├── Channel 1: 本地端口转发 (localhost:5432 → 远程 PostgreSQL)
├── Channel 2: SFTP 文件传输
└── Channel 3: Agent 转发
```

每个通道都是独立的，有自己的编号、窗口大小（流控用）和数据流。这就像一条光纤电缆里同时跑着网络、电视、电话信号——不同的频率（通道），同一条物理线路。

通道的生命周期也很清晰：

```
打开: SSH_MSG_CHANNEL_OPEN (指定类型: "session", "direct-tcpip" 等)
确认: SSH_MSG_CHANNEL_OPEN_CONFIRMATION
传输: SSH_MSG_CHANNEL_DATA
      SSH_MSG_CHANNEL_WINDOW_ADJUST (流量控制)
关闭: SSH_MSG_CHANNEL_CLOSE
```

### 3.7 数据包格式：每一个比特都长什么样

算法协商完成、密钥派生完毕、通道打开之后，所有的数据都被封装成 **SSH 二进制数据包** 进行传输：

```
┌──────────────┬──────────┬───────────────┬──────────────────┬──────────┐
│  包长度(4B)   │ 填充长度  │   有效载荷      │   随机填充字节      │   MAC    │
│  uint32      │  (1B)    │   (变长)       │  (≥4B, 凑到块大小)  │  (变长)  │
└──────────────┴──────────┴───────────────┴──────────────────┴──────────┘
                                                  │
                                                  │ 加密范围
                                                  └─────────────────→
                                                                            │
                                                          MAC 范围        │
                                                  ┌───────────────────────→│
```

几个关键细节：
- **包长度字段**本身不在 MAC 保护范围内（否则就成了鸡生蛋：要验证 MAC 得先知道长度，要知道长度得先解密，要解密得先验证 MAC）。实际上它会在加密后再单独校验。
- **填充字节**最少 4 个，用来把有效载荷补到加密算法要求的块大小（比如 AES-CBC 要求 16 字节对齐）。填充内容是随机的，增加了流量分析的难度。
- 每个包都有一个 **序列号**（从 0 开始，每发一个包加 1），不会重置。序列号参与 MAC 计算，但不在包中传输——双方各自维护自己的计数器。如果收到序列号不对的包，连接立即断开。这是防止重放攻击的关键机制。

### 3.8 连接复用：为什么 Ansible 跑得那么快

如果你用过 Ansible 管理上百台服务器，你可能会注意到一个现象：第一批连接建立起来后，后续任务的执行速度明显变快。这不是幻觉——这是 SSH 的**连接复用（Connection Multiplexing）**在工作。

正常情况下，每次 `ssh` 命令都要经历完整的 TCP 三次握手 + 密钥交换 + 用户认证。这一整套下来，即便网络延迟很低，也要消耗几百毫秒。对于一次性执行多条命令的场景（典型如 Ansible），这些开销叠加起来就很可观了。

OpenSSH 的解法是：**第一个连接建立后，后续连接可以直接复用这条已有的 TCP 通道，作为新的逻辑信道打开**。省掉了 TCP 握手、密钥交换和用户认证——这三个最耗时的步骤。

配置方法（`~/.ssh/config`）：

```ssh-config
Host *
    ControlMaster auto
    ControlPath ~/.ssh/sockets/%r@%h-%p
    ControlPersist 600
```

- `ControlMaster auto`：自动尝试复用已有连接，没有的话就新建一个
- `ControlPath`：指定 socket 文件的存放路径（`%r`=用户名, `%h`=主机, `%p`=端口）
- `ControlPersist 600`：主连接在最后一个会话结束后保持 600 秒（10 分钟）

效果有多明显？一个直观的对比：

```
不开启复用: 连续执行 10 次 ssh remote 'echo hello'
  耗时: ~15.3 秒（每次都是完整握手）

开启复用: 连续执行 10 次 ssh remote 'echo hello'
  耗时: ~0.8 秒（第一次完整握手，后 9 次复用）
```

## 四、动手实践：从第一个密钥到生产级安全配置

理论基础讲了这么多，现在进入实战环节。下面这些命令和配置，你都可以在自己的环境里直接运行验证。

### 4.1 安装 OpenSSH

绝大多数 Linux 发行版都预装了 OpenSSH，但如果你的系统是最小化安装，可能需要手动安装：

```bash
# Debian / Ubuntu
sudo apt install openssh-server openssh-client

# RHEL / CentOS / Fedora
sudo dnf install openssh-server openssh-clients

# 启动 SSH 服务并设为开机自启
sudo systemctl enable --now sshd

# 确认服务在监听 22 端口
sudo ss -tlnp | grep 22
```

Windows 10（1809+）和 Windows 11 也内置了 OpenSSH，可以在"设置 → 应用 → 可选功能"中添加。

### 4.2 生成你的第一对 SSH 密钥

密钥认证是 SSH 安全模型的核心。生成密钥对：

```bash
# 首选：Ed25519 算法（现代、安全、密钥短）
ssh-keygen -t ed25519 -C "your_email@example.com"

# 如果老设备不支持 Ed25519（很少见），用 RSA 4096
ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
```

命令执行后会问你三个问题：
1. **保存位置**：直接回车，使用默认路径 `~/.ssh/id_ed25519`
2. **密码短语（passphrase）**：强烈建议设置。这相当于给你的私钥加了一道锁——即使私钥文件被偷了，没有 passphrase 也用不了
3. **确认密码短语**：再输入一遍

生成后的文件：

```bash
~/.ssh/
├── id_ed25519        # 私钥（绝对不能泄露！权限必须为 600）
└── id_ed25519.pub    # 公钥（可以放心部署到任何服务器）
```

**文件权限检查（非常重要）：**

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
```

如果 `~/.ssh` 目录或私钥文件的权限过于宽松（比如 `777`），OpenSSH 会直接拒绝使用。这是一个安全功能——你不应该让其他用户读到你的私钥。

### 4.3 把公钥部署到服务器

最省心的方式是用 `ssh-copy-id`：

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@remote-server
```

这个命令会把你的公钥追加到远程服务器的 `~/.ssh/authorized_keys` 文件中。如果你还没有服务器上的账号密码，可以手动操作：

```bash
# 在服务器上
mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI..." >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

部署完成后，测试免密登录：

```bash
ssh user@remote-server
# 如果设置了 passphrase，会要求输入 passphrase（不是服务器密码）
# 如果没设 passphrase，直接登录
```

### 4.4 客户端配置：让你每天的 ssh 命令少敲 80% 的字符

不要每次都输入 IP 地址和用户名。把你常用的连接配置写入 `~/.ssh/config`：

```ssh-config
# 全局默认值（对所有主机生效）
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
    IdentitiesOnly yes

# 生产服务器
Host prod-web
    HostName 10.0.1.100
    User root
    Port 22
    IdentityFile ~/.ssh/id_ed25519

# 跳板机 + 内网服务器
Host jump
    HostName jump.example.com
    User admin

Host prod-db
    HostName 10.0.2.50
    User postgres
    ProxyJump jump

# GitHub（使用特定密钥）
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
```

配置完成后，你只需要：

```bash
ssh prod-web          # 代替 ssh -i ~/.ssh/id_ed25519 root@10.0.1.100
ssh prod-db           # 自动通过跳板机连接
git clone git@github.com:user/repo.git  # 自动使用指定密钥
```

### 4.5 服务器安全加固

这是运维工作中性价比最高的投入——花半小时改几行配置，就能挡住 90% 以上的自动化攻击。以下配置在 `/etc/ssh/sshd_config` 中操作。

> **操作原则：** 修改之前先备份 `sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak`，修改后执行 `sudo sshd -t` 检查语法，确认无误再重启服务。**永远保持一个已登录的终端窗口不要关**——改了配置但不小心把自己锁在外面，这是运维的经典翻车现场。

```bash
# ───── 基础安全配置 ─────

# 禁用 root 直接登录（所有操作通过普通用户 + sudo）
PermitRootLogin no

# 只允许公钥认证（禁用密码登录，除非你真的需要）
PubkeyAuthentication yes
PasswordAuthentication no
ChallengeResponseAuthentication no

# 限制认证尝试次数（防暴力破解）
MaxAuthTries 3

# 登录超时（30 秒内完成认证，否则断开）
LoginGraceTime 30

# 限制并发未认证连接数
# 格式：start:rate:full
# 意思是：超过 5 个未认证连接后，以 30% 概率拒绝新连接，10 个以后全部拒绝
MaxStartups 5:30:10

# 最大会话数
MaxSessions 5

# ───── 加密算法强化 ─────

# 指定强加密算法（使用现代、安全的密码套件）
KexAlgorithms sntrup761x25519-sha512@openssh.com,curve25519-sha256,diffie-hellman-group18-sha512,diffie-hellman-group16-sha512

Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com

MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com

HostKeyAlgorithms ssh-ed25519,rsa-sha2-512,rsa-sha2-256

# ───── 会话管理 ─────

# 客户端心跳检测（300 秒发一次探测，2 次失败后断开）
ClientAliveInterval 300
ClientAliveCountMax 2

# 禁用 DNS 反向解析（加快连接速度，减少日志中的无用 DNS 查询）
UseDNS no

# ───── 关闭不需要的功能 ─────

# 如果你不需要这些功能，关掉它们可以减少攻击面
X11Forwarding no
AllowAgentForwarding no
PermitTunnel no
PermitUserEnvironment no

# ───── 访问控制 ─────

# 只允许指定用户 / 用户组连接
AllowUsers alice@10.0.0.0/24 bob@trusted-ip
AllowGroups sshadmins
```

修改完成后的操作：

```bash
# 1. 检查配置文件语法
sudo sshd -t

# 2. reload 比 restart 好——reload 不会断开已有的连接
sudo systemctl reload sshd
```

### 4.6 SSH Agent：让密钥管理更优雅

如果你为私钥设置了 passphrase，每次 `ssh` 都要输入一遍，比密码还麻烦。这时候 `ssh-agent` 就派上用场了：

```bash
# 启动 agent（大多数桌面环境已经自动启动了）
eval $(ssh-agent)

# 把密钥加入 agent（只需输入一次 passphrase）
ssh-add ~/.ssh/id_ed25519

# 查看已加载的密钥
ssh-add -l

# 需要时移除密钥
ssh-add -d ~/.ssh/id_ed25519
```

`ssh-agent` 的工作方式是把解密后的私钥保存在内存中，之后的 SSH 连接由 agent 代劳签名——私钥本身仍然不会离开 agent 的进程空间。

**安全提醒：** 当你使用 `ssh -A`（Agent 转发）把本地的 agent 透传到远程服务器时，远程服务器上的 root 用户可以通过你的 agent socket 冒充你登录其他服务器。**尽量用 ProxyJump 代替 Agent 转发**，让私钥始终只存在于你自己的机器上。

### 4.7 端口转发实战

SSH 的端口转发功能是解决"内网服务怎么安全暴露"问题的瑞士军刀。三种模式覆盖了绝大多数场景。

**本地转发（-L）：把远程服务搬到本地**

```bash
# 格式：ssh -L [本地地址:]本地端口:目标主机:目标端口 user@ssh-server
ssh -L 5432:localhost:5432 user@prod-server

# 效果：访问 localhost:5432 等于访问 prod-server 上的 PostgreSQL
psql -h localhost -p 5432 -U myuser
```

使用场景：你有一个部署在内网的数据库，没有公网 IP。但你可以 SSH 到应用服务器（有公网 IP），应用服务器能访问数据库。于是你用本地转发把远程数据库"映射"到本地端口。

**远程转发（-R）：把本地服务暴露到远程**

```bash
# 在自己的开发机上执行
ssh -R 8080:localhost:3000 user@public-server

# 效果：public-server 上的任何人访问 localhost:8080
#       实际访问的是你本地开发机的 3000 端口
```

使用场景：你在本地写了一个 Web 应用，想让同事或客户预览。你的机器没有公网 IP，但有一台公网服务器。用远程转发，把本地的开发服务器"借道"公网服务器暴露出去。

> **注意：** 远程转发默认只绑定到远程服务器的 `localhost`，外部访问不了。如果想允许外部访问，需要在 `sshd_config` 中设置 `GatewayPorts clientspecified`，然后在命令中指定绑定地址：`ssh -R 0.0.0.0:8080:localhost:3000 user@public-server`。

**动态转发（-D）：搭建 SOCKS 代理**

```bash
# 在本机 1080 端口开启 SOCKS5 代理
ssh -D 1080 user@remote-server
```

使用场景：你需要访问某个只能从特定 IP（比如公司服务器）访问的网站。在浏览器里把 SOCKS 代理设成 `localhost:1080`，流量就会通过 SSH 服务器转发——网站看到的来源 IP 就是 SSH 服务器的 IP。

**组合技巧——隧道 + 后台运行：**

```bash
# -N: 不执行远程命令（只建隧道）
# -f: 建立连接后在后台运行
# 组合使用：开完隧道就放后台，不占用终端
ssh -f -N -L 5432:localhost:5432 user@prod-server
```

### 4.8 ProxyJump：跳板机的最佳实践

前面讲服务器安全加固时提到了跳板机。这里给出完整的配置方案：

```bash
# 方案 A：命令行方式（适合临时使用）
ssh -J user@jump.example.com root@10.0.1.100

# 方案 B：配置文件方式（适合日常使用）
# ~/.ssh/config
Host jumphost
    HostName jump.example.com
    User admin

Host internal-*
    ProxyJump jumphost

Host internal-web
    HostName 10.0.1.100
    User root

Host internal-db
    HostName 10.0.2.50
    User postgres

# 现在直接：
ssh internal-web    # 自动通过跳板机连接
ssh internal-db     # 同理
```

ProxyJump 的工作原理不是"先登跳板机再在里面敲 ssh"，而是让 SSH 客户端把跳板机当作一个透明代理——你的 SSH 流量先加密到跳板机，跳板机解密后再加密转发到目标服务器。你的私钥从头到尾只存在于你的本地机器上。

### 4.9 Fail2Ban：自动封禁暴力破解 IP

无论你怎么加固 SSH，22 端口上总会有人来扫描。Fail2Ban 是一个日志分析工具，它能自动检测暴力破解行为并临时封禁攻击 IP：

```bash
# 安装
sudo apt install fail2ban

# 创建 SSH 专用配置
sudo tee /etc/fail2ban/jail.local << 'EOF'
[sshd]
enabled = true
port = 22
filter = sshd
logpath = /var/log/auth.log
maxretry = 3
bantime = 600
findtime = 600
EOF

# 启动
sudo systemctl enable --now fail2ban

# 查看被封禁的 IP
sudo fail2ban-client status sshd
```

参数含义：在 600 秒（10 分钟）内，如果有 IP 地址的 SSH 认证失败次数达到 3 次，就封禁该 IP 10 分钟。对于生产环境，建议把 `bantime` 调到 3600（一小时）以上。

## 五、进阶话题：那些鲜为人知但极其有用的功能

### 5.1 SSH 证书（Certificate）：告别 known_hosts 的烦恼

如果你的服务器数量超过 10 台，手动管理 `known_hosts` 文件就是一场噩梦——每次新建服务器都要全员通告："各位请执行 `ssh` 然后敲 `yes`"。SSH 证书机制优雅地解决了这个问题：

```
传统方式（TOFU）：
  每台服务器有独立的主机密钥
  客户端首次连接时手动确认，存入 known_hosts
  服务器重建 → 密钥变了 → 每个人都要手动删除旧指纹

证书方式：
  CA 私钥签发主机证书 → 部署到服务器
  客户端信任 CA 公钥 → 所有由该 CA 签发的服务器自动被信任
  服务器重建 → 重新签发 → 客户端无感知
```

配置步骤（简明版）：

```bash
# 1. 创建 CA 密钥（在安全的管理机上执行，不要在任何服务器上留 CA 私钥）
ssh-keygen -t ed25519 -f ca_host_key -C "My Host CA"

# 2. 用 CA 给服务器签发证书
ssh-keygen -s ca_host_key \
    -I "web-server-01" \
    -h \
    -n "web.example.com,192.168.1.100" \
    /etc/ssh/ssh_host_ed25519_key.pub

# 3. 在服务器上配置使用证书（sshd_config）
HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub

# 4. 在客户端信任 CA（~/.ssh/known_hosts 或全局 /etc/ssh/ssh_known_hosts）
@cert-authority *.example.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...
```

`@cert-authority` 这一行配置的意思是："凡是以 `*.example.com` 结尾的主机，只要它的证书是由这个 CA 私钥签发的，就自动信任，不用再问我 yes/no。"

### 5.2 SFTP：SCP 已死，SFTP 当立

很多人还在用 `scp` 传文件：

```bash
scp myfile.txt user@server:/home/user/
```

鲜为人知的是，OpenSSH 从 **9.0 版本（2022 年 4 月）** 开始，`scp` 命令的底层实现已经悄悄从老旧的 SCP 协议切换到了 SFTP 协议。SCP 协议（基于 rcp）有很多问题：它不支持断点续传、无法中断传输、文件名处理有安全隐患。而 SFTP 是一个完整的文件传输协议，支持列出目录、删除文件、修改权限等全套操作。

```bash
# 交互式 SFTP（类似于 FTP 客户端）
sftp user@server

# 常用 SFTP 命令（进入交互模式后）
ls / cd / get / put / rm / mkdir / chmod / rename

# 自动执行（适合脚本）
echo "put report.pdf" | sftp -b - user@server

# 断点续传（rsync 式用法）
reget large_file.iso
```

### 5.3 强制命令（ForceCommand）：精确控制"能做什么"

有时候你不想给一个人完整的 shell 权限，只想让他执行一个特定操作。比如，只允许某人触发一个部署脚本：

```bash
# /etc/ssh/sshd_config
Match User deploy-bot
    ForceCommand /usr/local/bin/deploy.sh
    PasswordAuthentication no
```

这个用户通过 SSH 连接服务器后，不会看到 shell 提示符——`deploy.sh` 会直接执行，执行完毕后连接断开。你可以记录日志、做参数校验，控制他能做的所有事情。

另一个常见的用法是 SFTP-only 用户——只允许文件传输，不给 shell：

```bash
Match Group sftpusers
    ForceCommand internal-sftp
    ChrootDirectory /home/%u
    PermitTunnel no
    AllowAgentForwarding no
    AllowTcpForwarding no
    X11Forwarding no
```

### 5.4 SSH 还能做 VPN

如果你觉得 SSH 的功能就这些了，那你还低估了它。OpenSSH 内置了对 TUN/TAP 虚拟网卡的支持，可以搭建 Layer 3（IP 层）VPN：

```bash
# 服务器端（需要 PermitTunnel yes）
ssh -w 0:0 root@server

# 两端各出现一个 tun0 网卡
# 配好 IP 和路由，就能像在同一个局域网一样通信
```

不过说实话，SSH VPN 的性能不如 WireGuard 或 OpenVPN——毕竟 TCP over TCP 的拥塞控制会互相打架。对于临时需要访问内网的场景可以用用，正式环境还是建议用专业的 VPN 方案。

## 六、总结与建议

### 给后端开发者

- 把你的数据库连接信息写进 `~/.ssh/config`，用本地端口转发映射到 `localhost`。别再在代码仓库里留下数据库 IP 和密码了。
- 学会使用 `ProxyJump`。现代微服务架构中，数据库服务器通常没有公网 IP，掌握 SSH 跳板是你排查线上问题的基本技能。
- 开启 `ControlMaster`。频繁 `ssh` 执行命令的场景（部署脚本、监控探测）会因此快好几倍。

### 给运维工程师

- **今天就去检查你的 `/etc/ssh/sshd_config`**。确认 `PermitRootLogin` 至少是 `prohibit-password`、`PasswordAuthentication no`（如果已全面使用密钥）、`MaxAuthTries 3`。
- 部署 Fail2Ban 或类似的入侵防御工具。这不是"锦上添花"——公网上的 SSH 端口每天会收到成百上千次扫描尝试。
- 如果你的服务器超过 10 台，认真考虑部署 SSH 证书（Certificate）体系。投入半天时间搭建 CA，省下未来无数次的 `known_hosts` 管理痛苦。
- 定期用 `ssh-audit` 工具扫描你的 SSH 服务配置：`ssh-audit your-server.com`。它会告诉你哪些算法已经过时、哪些配置存在安全风险。

### 给初学者

- 如果你现在还在用密码登录 SSH，**第一优先级的任务就是换成密钥认证**。这是投入最小、收益最大的安全提升。
- 阅读 `man ssh_config` 和 `man sshd_config`。OpenSSH 的手册页写得非常好，是你身边最权威的老师。
- 理解 `~/.ssh/` 下每个文件的作用：`id_*` 是私钥（绝不分享）、`*.pub` 是公钥（放心发送）、`authorized_keys` 是白名单（谁有公钥在此就能登录）、`known_hosts` 是信任列表（我确认过这些服务器是真的）。

### 一个简单的自检清单

在你合上这篇文章之前，快速过一遍：

```
□ 我的 SSH 密钥用的是 Ed25519 而不是 RSA 1024
□ 我的私钥设置了 passphrase
□ 我的服务器禁用了 root 密码登录
□ 我的 sshd_config 里 PasswordAuthentication 是 no
□ 我不用 ssh -A（Agent 转发），改用 ProxyJump
□ 我部署了 Fail2Ban 或类似的防护
□ 我的 known_hosts 不是一团乱麻
□ 我知道怎么用 ssh -L / -R / -D 解决临时访问问题
```

OpenSSH 跟 Linux 内核、GCC 编译器一样，属于那种"你每天都在用、它的存在感越轻越好"的基础设施。但真正理解它的工作原理——从 Diffie-Hellman 密钥交换到通道复用，从 host key verification 到端口转发——会让你在排查连接问题、设计网络架构、应对安全事件时，比你身边的工程师站得更高、看得更远。
