## 开篇："这代码在我机器上能跑啊！"

每个程序员都经历过这个场景：

> 后端："我本地测了没问题啊。"
> 前端："你用的 Node 什么版本？"
> 后端："18。"
> 前端："我的是 20……要不你试试装一下 v20？"
> 后端："行。哦对，你 Redis 是哪个版本？还有那个环境变量你设了没？"

两个小时过去了，问题没解决，咖啡倒是喝了两杯。

这种"环境不一致"的痛苦不仅出现在同事之间。开发环境和生产环境不一样，更是部署事故的头号来源。你本地用的是 macOS，服务器跑的是 Ubuntu，Python 版本差一个小版本号，系统库里缺一个 `libxml2`，数据库用的是不同的编码……任何一个差异都可能导致"明明本地能跑，上线就炸"。

2013 年，一家叫 dotCloud 的小公司开源了一个内部工具，后来这个工具的名字比公司本身还要出名——**Docker**。

Docker 的核心思想非常简单：**把应用程序和它依赖的一切（代码、运行时、系统库、环境变量）打包成一个标准化的"箱子"，在任何地方运行这个箱子，里面的东西都一样。**

如果你曾经往朋友家搬过台式机——显示器、主机、键盘、鼠标、一堆连接线——你就知道为什么"一体机"会更方便。Docker 就是软件的"一体机"：一个集装箱，开箱即用。

这篇文章会从零讲起：Docker 怎么解决环境一致性问题的、它的底层原理是什么、怎么写出一个生产级的 Dockerfile、以及那些你迟早会踩的坑该怎么避开。

## Docker 是什么？

### 一句话定义

**Docker 是一个平台，它把应用程序及其全部依赖打包进一个叫做"容器"的轻量级、可移植的隔离环境中，确保在任何机器上运行结果一致。**

拆开来看四个关键词：

- **打包**：不是"安装一个 Python"，而是"把 Python 和你写的代码、需要的库、系统依赖一起打成一个包"。这个包就是 **镜像（Image）**。
- **轻量级**：一个容器只占几十 MB，启动时间以毫秒计。同一台物理机上可以跑几百个容器。
- **隔离**：容器之间互相看不到对方的进程、文件、网络。每个容器都觉得自己是"独占这台机器"的。
- **一致**：同一个镜像，在你的 MacBook 上和阿里云 ECS 上跑，里面是一模一样的环境。

### 容器 vs 虚拟机

理解 Docker 最好的方式是把它和虚拟机比起来看：

```
        虚拟机 (VM)                            Docker 容器
┌──────────────────────────────┐    ┌──────────────────────────────┐
│  ┌─────────┐   ┌─────────┐  │    │  ┌─────────┐   ┌─────────┐  │
│  │  App A  │   │  App B  │  │    │  │  App A  │   │  App B  │  │
│  ├─────────┤   ├─────────┤  │    │  ├─────────┤   ├─────────┤  │
│  │Bin/Libs │   │Bin/Libs │  │    │  │Bin/Libs │   │Bin/Libs │  │
│  ├─────────┤   ├─────────┤  │    │  └────┬────┘   └────┬────┘  │
│  │Guest OS │   │Guest OS │  │    │       │             │       │
│  └────┬────┘   └────┬────┘  │    │       └──────┬──────┘       │
│       └──────┬──────┘       │    │              │              │
│              │              │    │    ┌─────────┴─────────┐    │
│  ┌───────────┴───────────┐  │    │    │   Docker Engine   │    │
│  │      Hypervisor       │  │    │    ├──────────────────┤    │
│  ├───────────────────────┤  │    │    │     Host OS       │    │
│  │       Host OS         │  │    │    ├──────────────────┤    │
│  ├───────────────────────┤  │    │    │  Infrastructure   │    │
│  │    Infrastructure     │  │    │    └──────────────────┘    │
│  └───────────────────────┘  │    │                            │
└──────────────────────────────┘    └──────────────────────────────┘

  每个 App 自带一个完整 OS              所有 App 共享一个 OS 内核
```

关键区别：**VM 虚拟的是硬件，每个 VM 跑一套完整的操作系统。容器共享宿主机的操作系统内核，只隔离应用层。**

| 维度 | 虚拟机 | Docker 容器 |
|------|--------|------------|
| **启动速度** | 几十秒到几分钟 | 几十毫秒到几秒 |
| **磁盘占用** | 几个 GB / 台 | 几十 MB / 个 |
| **内存开销** | 每台 VM 要跑一个完整 OS | 只多占应用本身的量 |
| **单机密度** | 几十台 | 几百上千个 |
| **隔离强度** | 硬件级（强） | 进程级（较弱，但够用） |
| **可移植性** | 依赖 Hypervisor 类型 | 只要装了 Docker 就能跑 |

> 一句话总结：**VM 是"一台虚拟的电脑"，容器是"一个被隔离的进程"**。这个认知是理解 Docker 的基石。

### Docker 的核心三件套

| 概念 | 是什么 | 类比 |
|------|--------|------|
| **镜像（Image）** | 一个只读的模板，包含运行应用所需的一切 | 一份"安装包"或"程序安装光盘" |
| **容器（Container）** | 镜像的运行实例——本质上是宿主机上一个被隔离的进程 | 用安装包安装好、正在运行的程序 |
| **仓库（Registry）** | 存储和分发镜像的地方（Docker Hub 是最大的公共仓库） | App Store / npm registry |

它们的关系：

```
docker build ──→ Image ──→ docker push ──→ Registry (Docker Hub)
                     │
                docker run
                     │
                     ▼
                Container (运行中的进程)
```

## 底层原理：三个 Linux 内核特性撑起了容器

Docker 不是魔法。它的底层依赖三个 Linux 内核技术：**Namespace**（隔离"能看到什么"）、**Cgroups**（限制"能用多少"）、**Union Filesystem**（管理"文件怎么存"）。

### Namespace：让进程觉得自己是"唯一的"

Linux Namespace 的作用是**给进程创建一个"幻觉世界"**——进程在里面看到的是自己专属的 PID 编号、文件系统、网络接口，以为自己独占整台机器，但其实只是内核在玩"障眼法"。

Linux 内核目前支持 8 种 Namespace，Docker 全部都用上了：

| Namespace | 隔离什么 | 效果 |
|-----------|---------|------|
| **PID** | 进程 ID | 容器里 `ps aux` 只看到容器内的进程，且第一个进程 PID=1 |
| **Mount** | 文件系统挂载点 | 容器看到的是自己的根文件系统 `/`，不是宿主机的 `/` |
| **Network** | 网络接口、IP、端口 | 容器有自己的 `eth0`、独立 IP 地址 |
| **UTS** | 主机名和域名 | 容器可以有自己的 hostname |
| **IPC** | 进程间通信 | 共享内存、信号量只在容器内可见 |
| **User** | 用户和组 ID | 容器里的 root（UID 0）可以映射到宿主机上的普通用户 |
| **Cgroup** | 控制组视图 | 容器内看到的是自己的 Cgroup 层级 |
| **Time** | 系统时间 | 容器可以有不同的系统时钟（Linux 5.6+） |

用一个简单的类比：Namespace 就像给每个进程发了一副 AR 眼镜——透过眼镜，进程看到的世界是"自己独占这台机器"。但实际上这些进程和谐地跑在同一个 Linux 内核上，互相不知道对方的存在。

你可以用 `unshare` 命令手动体验一下 Namespace：

```bash
# 在一个隔离的 PID namespace 里运行 bash
sudo unshare --pid --fork --mount-proc bash
ps aux   # 只能看到 bash 自己和 ps 两个进程！
```

### Cgroups：限制"这个容器最多用多少资源"

Namespace 解决了"能看到什么"，但没解决"能用多少"。如果某个容器里的进程开始疯狂吃 CPU 和内存，没有 Cgroups 的话，它会影响所有其他容器和宿主机本身。

**Cgroups（Control Groups）** 的作用是**给进程组套上一个"资源项圈"**——你可以精确限制一个容器能用多少 CPU、多少内存、多少磁盘 IO。

```bash
# 限制容器最多用 512MB 内存和 1.5 个 CPU 核心
docker run -d \
  --memory="512m" \
  --cpus="1.5" \
  nginx
```

Cgroups 的工作原理很简单：内核在 `/sys/fs/cgroup/` 下维护了一套虚拟文件系统，每个资源子系统（CPU、内存、IO 等）都是一个目录。把进程的 PID 写进这个目录，再向目录里的 `cpu.shares` 或 `memory.limit_in_bytes` 写入限制值，内核就会强制执行。

| Cgroup 控制器 | 限制什么 | 对应的 docker run 参数 |
|--------------|---------|----------------------|
| **cpu** | CPU 时间分配 | `--cpus`, `--cpu-shares` |
| **memory** | 内存使用上限 | `--memory` |
| **blkio** | 磁盘 IO 吞吐 | `--blkio-weight`, `--device-read-bps` |
| **pids** | 进程数量上限 | `--pids-limit` |
| **devices** | 可访问的设备 | 内置，默认只开放安全的设备 |

### OverlayFS：分层文件系统

Docker 镜像为什么能做到"同一台机器上跑几十个容器，磁盘增量只有几十 MB"？答案在**分层文件系统**。

Docker 镜像是由多个**只读层**叠起来的，每个层只记录相对于前一层的"变化"。当你执行 `docker run` 时，Docker 在所有这些只读层之上加一个**可写层**（容器层），然后把所有层"合并"成一个统一视图给容器用。

```
┌─────────────────────────────┐
│     可写层 (Container Layer)  │  ← 每个容器独有，记录所有写入操作
├─────────────────────────────┤
│     镜像层 3: 你的应用代码     │  ← COPY . .    (几 MB)
├─────────────────────────────┤
│     镜像层 2: 安装依赖        │  ← RUN pip install  (几十 MB)
├─────────────────────────────┤
│     镜像层 1: Python 运行时    │  ← FROM python:3.12-slim  (约 150MB)
├─────────────────────────────┤
│     镜像层 0: Debian 基础系统  │  ← Python 镜像的基础 (已包含在上一层)
└─────────────────────────────┘
```

关键特性：

- **写时复制（Copy-on-Write）**：只有当容器要修改某个文件时，Docker 才把那个文件从只读层复制到可写层。读操作直接从只读层读取，不消耗额外空间。
- **层共享**：一台机器上跑 10 个基于 `python:3.12-slim` 的容器，只读层只需要存一份。

```
10 个容器 × 每个独有可写层 (几 MB)  +  1 份共享只读层 (150MB)
≈ 150 MB + 几十 MB，而不是 150 MB × 10
```

这种设计让 Docker 镜像的构建、分发和存储都非常高效。

## 动手实践：从零写一个生产级 Docker 项目

理论讲了这么多，来动手。我们以一个 Python Web 应用（FastAPI）为例，从最简单的 Dockerfile 开始，逐步优化到生产级别。

### 第一步：单阶段构建（入门版）

这是新手最自然的写法——把所有东西放一个镜像里：

```dockerfile
FROM python:3.12
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

这个 Dockerfile 能跑，但有一个致命问题：**最终镜像约 1GB**。它包含了整个 Python 源码、编译工具链、pip 缓存、以及一大堆运行时根本不需要的东西。把它推到 Docker Hub 要等很久，每次部署拉镜像也很慢。

### 第二步：换个 slim 基础镜像（省钱版）

```dockerfile
FROM python:3.12-slim       # slim：去掉编译工具和文档，约 150MB vs 1GB
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

镜像从 1GB 降到大概 200-300MB。这是最小改动、最大收益的一步。对于大多数项目，`slim` 已经够用了。

### 第三步：优化层缓存（加速版）

Docker 构建镜像时是一层一层执行的，每一层构建完都会被缓存。关键是：**如果某一层的内容变了，它和它之后的所有层都要重新构建。** 所以我们应该把"变化频率最低"的东西放在前面：

```dockerfile
FROM python:3.12-slim
WORKDIR /app

# 先复制依赖文件（变化频率低）→ 依赖安装层可以缓存住
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 再复制应用代码（变化频率高）
COPY . .

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

效果：如果你只改了 `app/main.py`，前两层（`slim` 基础镜像 + 依赖安装）直接从缓存取，只需要重新 `COPY . .` 这一层——构建从 2 分钟缩短到 5 秒。

### 第四步：多阶段构建（生产版）

多阶段构建是 Docker 17.05 引入的功能，能让你在一个 Dockerfile 里定义多个"阶段"，最终镜像只保留最后一个阶段的内容：

```dockerfile
# ============ 阶段 1：构建阶段 ============
FROM python:3.12-slim AS builder

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt
# --user 安装到 ~/.local，后面复制时不会带乱七八糟的系统路径

# ============ 阶段 2：运行阶段 ============
FROM python:3.12-slim AS runner

# 创建非 root 用户
RUN addgroup --system app && adduser --system --group app

WORKDIR /app

# 只从 builder 复制运行时需要的东西
COPY --from=builder /root/.local /home/app/.local
COPY . .

# 确保可执行文件在 PATH 中
ENV PATH=/home/app/.local/bin:$PATH

# 切换到非 root 用户
USER app

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

多阶段构建的精妙之处在于：**`builder` 阶段里的 pip、setuptools、wheel、C 编译器、头文件全部留在了 builder，最终镜像（`runner`）根本没这些东西。** 镜像大小可以进一步降到 150-200MB。

对于编译型语言（Go、Rust），效果更显著：

```dockerfile
# Go 多阶段构建：最终镜像从 800MB 降到约 10MB
FROM golang:1.22 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o myapp

FROM alpine:3.19              # 只放编译好的二进制，连 Go 都没装
COPY --from=builder /app/myapp /usr/local/bin/myapp
CMD ["myapp"]
```

### 第五步：Docker Compose 编排多容器应用

真实的项目很少只有一个容器。Web 后端 + 数据库 + 缓存是标配。Docker Compose 用一个 YAML 文件定义这些容器的关系和配置：

```yaml
services:
  backend:
    build:
      context: .
      target: runner            # 用多阶段构建的 runner 阶段
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://app:${DB_PASSWORD}@db:5432/app
      - REDIS_URL=redis://cache:6379
    depends_on:
      db:
        condition: service_healthy   # 等数据库就绪再启动
      cache:
        condition: service_started
    volumes:
      - ./uploads:/app/uploads       # 上传文件持久化
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}   # 从 .env 文件读取，不进版本控制
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data   # 数据持久化
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      timeout: 3s
      retries: 5

  cache:
    image: redis:7-alpine
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pgdata:
  redisdata:
```

用一行命令启动全家桶：

```bash
docker compose up -d
```

### 一个 .dockerignore 能省几百 MB

构建上下文（Docker daemon 接收到的文件集合）默认是 Dockerfile 所在目录的全部内容。不加 `.dockerignore`，你会把 `node_modules`、`.git`、测试报告、虚拟环境全打包进去：

```
node_modules
.git
.env
*.md
dist
build
__pycache__
*.pyc
.coverage
.pytest_cache
.gitignore
Dockerfile
docker-compose.yml
```

加上这个文件后，构建上下文可能从 500MB 降到 5MB，构建速度质的飞跃。

## Docker 网络

Docker 为每个容器创建独立的网络命名空间，容器之间默认是隔离的。要让它们互通（比如 backend 连 db），你需要定义网络。

### Bridge 网络（单机模式，也是最常用的）

默认网络驱动。同一台宿主机上的容器通过一个虚拟交换机（`docker0` 网桥）通信：

```bash
# 创建一个自定义 bridge 网络（比默认 bridge 好：支持 DNS 名称解析）
docker network create mynet

# 把容器连接到同一个网络
docker run -d --name backend --network mynet myapp
docker run -d --name db --network mynet postgres:16-alpine

# backend 可以直接 ping db（Docker 内置 DNS 把容器名解析为 IP）
docker exec backend ping db   # 成功！
```

**为什么用自定义 bridge 而不是默认 bridge？** 默认 bridge 网络不支持 DNS 名称解析——容器之间只能通过 IP 通信，而 IP 在容器重启后会变。自定义 bridge 可以用容器名互访。

### Overlay 网络（跨主机模式）

当你的应用部署在 Docker Swarm 集群的多台机器上时，Overlay 网络让不同宿主机上的容器可以像在同一台机器上一样通信：

```bash
docker swarm init
docker network create --driver overlay --attachable my_overlay
```

Overlay 网络内部通过 VXLAN 隧道封装流量，对容器透明。不过说实话，2026 年用 Docker Swarm 的人已经越来越少了，多机编排几乎都是 Kubernetes 的天下——但 Overlay 网络的原理在 K8s 的 CNI 插件（Flannel、Calico）中仍然在大量使用。

### 网络驱动对比

| 驱动 | 范围 | DNS 解析 | 典型场景 |
|------|------|---------|---------|
| **bridge（默认）** | 单机 | 不支持 | 不推荐直接用 |
| **bridge（自定义）** | 单机 | 支持 | 开发环境、单机部署 |
| **host** | 单机 | N/A | 高性能网络（跳过 Docker 网络栈） |
| **overlay** | 多机 | 支持 | Swarm 集群 |
| **none** | 无网络 | N/A | 安全沙箱测试 |

## Docker 存储：数据不能丢

容器的设计哲学是**无状态和可替换**。容器删除时，它的可写层（容器层）也会被删除。所以任何需要持久化的数据——数据库文件、用户上传、日志——都必须放在 **Volume** 里。

### 三种存储挂载方式

| 类型 | 存储位置 | 管理方 | 适用场景 |
|------|---------|--------|---------|
| **Named Volume** | `/var/lib/docker/volumes/<name>/` | Docker | 数据库文件、应用产生的持久数据 |
| **Bind Mount** | 宿主机上的任意路径 | 用户自己 | 开发时挂载源码实现热重载 |
| **tmpfs** | 内存 | 内核 | 敏感临时数据（密钥、token） |

### 实际用法

```bash
# Named Volume —— Docker 管理，最推荐
docker run -v pgdata:/var/lib/postgresql/data postgres:16

# Bind Mount —— 开发时好用
docker run -v $(pwd)/src:/app/src myapp   # 改了 src/ 里的代码，容器里立刻生效

# 只读挂载 —— 防止应用篡改配置
docker run --mount type=bind,src=$(pwd)/config.yaml,dst=/app/config.yaml,readonly myapp
```

一个常见的坑：**不要用 Bind Mount 来持久化数据库数据。** Bind Mount 的路径依赖宿主机文件系统，换一台机器（比如 macOS 到 Linux）路径结构不同，容器就起不来。用 Named Volume，Docker 帮你处理跨平台兼容性。

### Volume 的生命周期

```bash
docker volume ls                  # 列出所有 Volume
docker volume inspect pgdata      # 查看 Volume 在宿主机上的实际路径
docker volume prune               # 清理所有未被任何容器使用的 Volume（慎用！）
docker compose down -v            # 停止容器并删除 Volume（数据彻底没了！）
```

## Docker 安全与生产优化

### 安全第一原则：永远不要用 root 运行容器

默认情况下，Docker 容器以 root（UID 0）身份运行。如果应用存在漏洞允许攻击者在容器内执行命令，以 root 运行的容器就意味着攻击者可能通过容器逃逸影响到宿主机。

```dockerfile
# 创建专用用户
RUN addgroup --system --gid 1001 app && \
    adduser --system --uid 1001 --gid 1001 app

# 切换到非 root 用户
USER app
```

生产环境的 docker-compose 还应该加上：

```yaml
services:
  app:
    user: "1001:1001"           # 非 root
    read_only: true              # 只读根文件系统
    security_opt:
      - no-new-privileges:true   # 禁止提权
    cap_drop:
      - ALL                      # 去掉所有 Linux Capability
    cap_add:
      - NET_BIND_SERVICE         # 只加回确实需要的
```

### 镜像瘦身清单

| 技巧 | 效果 |
|------|------|
| 用 `slim` / `alpine` 变体 | python:3.12 (1GB) → python:3.12-slim (150MB) → python:3.12-alpine (50MB) |
| 多阶段构建 | 最终镜像不含编译器、构建工具、开发依赖 |
| 善用 `.dockerignore` | 减少构建上下文体积，也避免了把 `.env` 打进镜像 |
| 清理同一层 | `apt-get update && apt-get install -y xxx && rm -rf /var/lib/apt/lists/*` 在同一条 RUN 里 |
| Go/Rust 用 `FROM scratch` | 就是空镜像，只能放编译好的静态链接二进制，最终镜像 = 你的程序（5-15MB） |

### 标签策略

```bash
# 不要用 :latest（谁知道 latest 今天是什么版本）
docker build -t myapp:latest .           # 坏习惯

# 用 Git SHA + 语义版本号
docker build -t myapp:git-$(git rev-parse --short HEAD) .   # 可追溯
docker build -t myapp:1.2.3 .                               # 可读
```

### 安全扫描

在 CI/CD 里集成安全扫描，把漏洞拦截在部署之前：

```bash
# Trivy —— 免费的容器漏洞扫描器
trivy image myapp:latest

# 扫描结果示例：
# myapp:latest (debian 12.5)
# Total: 0 (CRITICAL: 0, HIGH: 0, MEDIUM: 0, LOW: 0)
```

### 健康检查

让 Docker 自己知道容器是不是真的在"正常工作"，而不只是"进程没挂"：

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:8000/health || exit 1
```

在 Compose 中：

```yaml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
  interval: 30s
  timeout: 3s
  retries: 3
  start_period: 10s   # 给应用启动留点时间
```

配合 `depends_on` 的 `condition: service_healthy`，可以确保数据库就绪后才启动后端，而不是"容器起来了但数据库还没准备好接受连接"。

## 总结与建议

Docker 解决的核心问题可以用一句话概括：**在软件世界里，让"在我机器上能跑"不再是一句空话。** 它通过 Linux 内核的 Namespace（隔离）、Cgroups（限资源）、OverlayFS（分层存储）这三大技术，用极低的代价实现了应用的标准化打包和运行。

针对不同角色，建议如下：

**后端开发者**：学会写 Dockerfile 不是可选项，是必修课。从 `slim` 基础镜像开始，理解层的缓存机制，养成 `.dockerignore` 的习惯。能写 `docker-compose.yml` 在本地一键启动全家桶（后端 + DB + Redis + 消息队列），能极大提升日常开发效率——不用再手动装 MySQL 和 Redis 了。

**前端开发者**：至少掌握 `docker build` 和 `docker run`。遇到 Node 版本问题，不用装 nvm 来回切换，直接在容器里跑。另外，用 Docker 的多阶段构建，可以把前端构建（`npm run build`）做成第一阶段，最终用 Nginx 做第二阶段的静态文件服务器，得到一个不到 50MB 的生产镜像。

**运维/SRE**：关注容器安全——非 root、只读文件系统、最小 Capability、镜像扫描。关注资源限制（一定要设 `--memory` 和 `--cpus`，生产环境不止一次出现过"一个容器吃光整台机器内存"的事故）。关注日志收集（`json-file` driver + `max-size` + `max-file`，避免 Docker 日志撑爆磁盘）。

**架构师**：Docker 是云原生的入口。理解了容器，Kubernetes 就是"管几百个容器的编排器"而不是一个神秘的黑盒。容器化是微服务化的前提——没有容器，微服务的部署和维护成本会高到不可接受。

最后，一个建议：**不要等到项目上线了才学 Docker。** 下一个项目，第一天就用 `docker-compose up` 启动你的开发环境。
