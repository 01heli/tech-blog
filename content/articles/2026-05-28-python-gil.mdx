## 从一个反常识的实验开始

先看一段代码，你认为 4 个线程同时做 CPU 计算会比 1 个线程快吗？

```python
import threading
import time

def countdown(n):
    while n > 0:
        n -= 1

def single_thread():
    start = time.perf_counter()
    countdown(50_000_000)
    print(f"单线程: {time.perf_counter() - start:.2f}s")

def multi_thread():
    start = time.perf_counter()
    threads = [threading.Thread(target=countdown, args=(12_500_000,)) for _ in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    print(f"4 线程: {time.perf_counter() - start:.2f}s")
```

在 4 核机器上运行的结果让人意外：**4 线程比单线程还要慢**，甚至慢 20%-50%。这不是 bug——这就是 GIL。

## 什么是 GIL

GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器中的一个互斥锁，它在任意时刻只允许**一个线程**执行 Python 字节码，即使运行在多核 CPU 上也是如此。

```
┌────────────────────────────────────────────────────┐
│                   CPython 进程                      │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐           │
│  │ 线程1 │  │ 线程2 │  │ 线程3 │  │ 线程4 │           │
│  └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘           │
│     │         │         │         │                │
│     └─────────┼─────────┼─────────┘                │
│               ▼         ▼                          │
│         ┌─────────────────────┐                    │
│         │       GIL           │  ← 只有一把钥匙     │
│         └─────────┬───────────┘                    │
│                   ▼                                │
│         ┌─────────────────────┐                    │
│         │   Python 解释器      │  ← 同一时刻只有一个  │
│         │  (执行字节码)        │     线程能进入       │
│         └─────────────────────┘                    │
└────────────────────────────────────────────────────┘
```

需要明确的是：**GIL 是 CPython 的实现特性，不是 Python 语言规范的一部分**。其他 Python 实现如 Jython（运行在 JVM 上）和 IronPython（运行在 .NET CLR 上）就没有 GIL。但在实际使用中，CPython 是绝对的主流，所以"Python 有 GIL"这句话在工程语境下是正确的。

## GIL 为什么存在：回到 1992 年

GIL 是 Guido van Rossum 在 1992 年为 Python 添加多线程支持时引入的。要理解这个决策，需要回到那个时代的背景。

### 根本原因：引用计数

CPython 使用**引用计数**作为主要的内存管理机制。每个 Python 对象（`PyObject`）都有一个 `ob_refcnt` 字段：

```c
// CPython 源码中的 PyObject 结构（简化）
typedef struct _object {
    Py_ssize_t ob_refcnt;      // 引用计数
    PyTypeObject *ob_type;      // 类型指针
} PyObject;
```

通过 `Py_INCREF` 和 `Py_DECREF` 两个宏来管理引用计数：

```c
#define Py_INCREF(op) ((op)->ob_refcnt++)
#define Py_DECREF(op) \
    if (--((op)->ob_refcnt) != 0) ; else _Py_Dealloc(op)
```

这意味着每次创建引用、传递参数、访问属性时，都在修改 `ob_refcnt`。在正常的 Python 程序执行过程中，这两个宏**每秒会被调用数百万次**。

如果没有 GIL，两个线程同时执行 `Py_DECREF` 会发生什么：

```
线程 A: 读取 ob_refcnt = 3
线程 B: 读取 ob_refcnt = 3
线程 A: 写入 ob_refcnt = 2
线程 B: 写入 ob_refcnt = 2   ← 应该是 1，数据竞争！
```

结果就是引用计数永远无法归零（内存泄漏），或者在错误的时间归零（提前释放导致崩溃）。这是一个典型的**数据竞争**问题。

### 为什么不用其他方案

当时面临几种选择：

**方案一：原子引用计数。** 把每个 `Py_INCREF`/`Py_DECREF` 都变成原子操作。问题是 1992 年的硬件上原子操作非常昂贵，会给单线程代码带来约 30% 的性能退化。对于当时几乎全是单线程的应用场景来说，这是不可接受的。

**方案二：细粒度锁。** 给每个对象或每类对象加锁。1999 年 Greg Stein 做了这个尝试——结果单线程性能下降了约 2 倍。锁的获取和释放本身就是昂贵的操作，当成千上万个对象都在做这件事时，开销远远超过了收益。

**方案三：追踪式 GC。** 像 JVM 或 .NET 那样用追踪式垃圾回收替代引用计数。但这会完全改变 CPython 的对象模型和 C API，意味着所有的 C 扩展都要重写。Python 生态依赖的 C 扩展数量庞大，这条路在当时和现在都行不通。

**方案四：一把全局锁。** 一个互斥锁，任何线程在执行 Python 字节码前先获取。实现简单，单线程性能零损失，C 扩展开发者容易理解。在多核 CPU 还不存在的 1992 年，这是最优解。

Guido 选择了方案四。他说过一句著名的话：

> "I'd welcome a set of patches into Py3k only if the performance for a single-threaded program (and for a multi-threaded but I/O-bound program) does not decrease."

翻译：**只有在单线程和 I/O 密集型程序性能不下降的前提下，才欢迎移除 GIL 的补丁。** 这成了此后 30 年所有 GIL 移除尝试必须跨越的基准线。

### 历史背景：单核时代

1992 年没有多核 CPU。第一款商用多核处理器（IBM POWER4）直到 2001 年才出现。在那个时代，线程的唯一用途就是 I/O 并发——让程序在等待磁盘或网络时不阻塞其他任务。GIL 对此完全够用。

换句话说，GIL 不是一个 bug，它是**单核时代一个极其正确的工程决策**。只是因为 CPU 的发展方向变了，它才逐渐变成了瓶颈。

## GIL 的内部实现

了解 GIL 在 CPython 源码中是如何实现的，能帮助你准确判断它在什么场景下是瓶颈。

### 核心数据结构

在 CPython 3.12+ 的源码中（`Python/ceval_gil.c`），GIL 由以下组件构成：

```
gil_locked        — 原子布尔变量，标识 GIL 是否被持有
gil_mutex         — 互斥锁，保护对 gil_locked 的访问
gil_cond          — 条件变量，让等待 GIL 的线程睡眠/唤醒
gil_drop_request  — 原子布尔变量，请求当前持有者释放 GIL
gil_switch_number — 计数器，记录 GIL 切换次数
gil_last_holder   — 原子指针，记录最后一次持有 GIL 的线程
```

### 获取 GIL：`take_gil()` 的全过程

这是 GIL 最核心的函数。当一个线程想要执行 Python 代码时，它必须调用 `take_gil()`：

```
1. 获取 gil_mutex（进入临界区）
        │
        ▼
2. gil_locked == 0 ?
   ┌─ 是 ──→ 跳转到第 6 步，直接获取 GIL
   │
   └─ 否 ──→ 进入等待循环
        │
        ▼
3. COND_TIMED_WAIT(gil_cond, gil_mutex, interval)
   默认等待 5000 微秒（5 毫秒）
        │
        ▼
4. 超时了？ 且 GIL 仍被持有？ 且 switch_number 没变？
   ┌─ 是 ──→ SET_GIL_DROP_REQUEST ← 请求当前线程释放
   │
   └─ 否 ──→ 回到步骤 2
        │
        ▼
5. GIL 空闲了 → 跳转到步骤 6
        │
        ▼
6. gil_locked = 1
   gil_last_holder = 当前线程
   gil_switch_number++
   释放 gil_mutex（离开临界区）
```

关键细节：**等待线程不会立即抢占**。新线程想拿 GIL 时，会先等 5ms。如果在这 5ms 内 GIL 自然释放了，就拿走；如果 5ms 后 GIL 还在被持有，才设置 `gil_drop_request` 标志**请求**当前线程释放。这是一种**协作式**机制。

### 释放 GIL：两种方式

**方式一：主动释放（I/O 操作时）。** 当 Python 代码执行阻塞 I/O 时，通过 `Py_BEGIN_ALLOW_THREADS` 和 `Py_END_ALLOW_THREADS` 宏主动释放 GIL：

```c
// socket 模块中的实际代码逻辑
Py_BEGIN_ALLOW_THREADS          // 释放 GIL
res = connect(sock_fd, addr, addrlen);  // 阻塞等待网络
Py_END_ALLOW_THREADS            // 重新获取 GIL
```

在 `Py_BEGIN_ALLOW_THREADS` 和 `Py_END_ALLOW_THREADS` 之间的代码**不持有 GIL**，其他线程可以执行 Python 字节码。这就是为什么 I/O 密集型多线程程序在 Python 中有效——在等待 I/O 的大部分时间里，线程并不持有 GIL。

**方式二：被动释放（被请求）。** 解释器主循环（`_PyEval_EvalFrameDefault`）在每次字节码指令执行后检查 `eval_breaker` 标志。如果检测到 `gil_drop_request` 被设置：

```
当前线程在字节码循环中
        │
        ▼
检查 eval_breaker 标志
        │
        ▼
gil_drop_request 被设置？
   ┌─ 是 ──→ 释放 GIL → 等待其他线程获取 → 重新获取
   │
   └─ 否 ──→ 继续执行下一个字节码指令
```

线程切换间隔可以通过 `sys.setswitchinterval()` 调整，默认值在 Python 3 中是 5 毫秒。

### 操作系统线程的实际状态

在任意时刻，一个运行 Python 多线程程序的进程中，各线程的真实状态是：

```
线程 A: [运行中] → 持有 GIL，执行 Python 字节码
线程 B: [就绪]   → 在 take_gil() 中等待，操作系统挂起在条件变量上
线程 C: [阻塞]   → 在 os.read() 中，已释放 GIL，内核在等待磁盘数据
线程 D: [就绪]   → 刚完成 I/O，在 Py_END_ALLOW_THREADS 中尝试重新拿 GIL
```

线程 B 和 D 处于"想要 GIL 但拿不到"的状态。线程 C 在做真正的系统级 I/O，同时不持有 GIL，不阻塞其他线程。

## GIL 对性能的真实影响

### CPU 密集型：多线程反而更慢

用一段代码来直观展示 GIL 对 CPU 密集型任务的影响：

```python
import time
import threading

def cpu_bound(n):
    """纯 Python 的 CPU 计算"""
    result = 0
    for i in range(n):
        result += i * i
    return result

# 单线程
start = time.perf_counter()
for _ in range(4):
    cpu_bound(10_000_000)
print(f"单线程串行: {time.perf_counter() - start:.2f}s")

# 多线程
start = time.perf_counter()
threads = [threading.Thread(target=cpu_bound, args=(10_000_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"多线程并行: {time.perf_counter() - start:.2f}s")
```

在 8 核 CPU 上的典型结果：

```
单线程串行: 3.05s
多线程并行: 4.21s   ← 反而更慢！
```

多线程更慢的原因是：
1. **GIL 竞争**：4 个线程抢一把锁，只有一个能干活
2. **上下文切换开销**：每 5ms 切换一次线程，切来切去增加了系统开销
3. **缓存失效**：线程在不同 CPU 核心间迁移，导致 CPU 缓存反复失效

这就是很多初学者困惑的来源——**Python 的多线程在 CPU 密集场景下不能利用多核**。

### I/O 密集型：多线程效果显著

但把场景换成 I/O 密集，情况完全不同：

```python
import time
import threading
import requests

def io_bound(url):
    """网络 I/O 密集操作"""
    return requests.get(url).text

urls = ["https://httpbin.org/delay/1"] * 10

# 单线程串行
start = time.perf_counter()
for url in urls:
    io_bound(url)
print(f"单线程串行: {time.perf_counter() - start:.2f}s")

# 多线程
start = time.perf_counter()
threads = [threading.Thread(target=io_bound, args=(url,)) for url in urls]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"多线程并行: {time.perf_counter() - start:.2f}s")
```

结果：

```
单线程串行: 12.71s
多线程并行: 1.82s    ← 接近理想加速比
```

因为在 `requests.get()` 内部，当底层的 `socket.recv()` 被调用时，CPython 通过 `Py_BEGIN_ALLOW_THREADS` 释放了 GIL。所有线程在等待网络数据时都不持有 GIL，每个线程都在真正的系统级并发等待。

### 判定你的场景属于哪一类

```
你的 Python 程序慢吗？
        │
        ▼
   时间花在哪里了？
        │
   ┌────┼────┬──────────┐
   ▼    ▼    ▼          ▼
 磁盘  网络  CPU计算   数据库
 I/O   I/O  (纯Python)  查询
   │    │       │          │
   ▼    ▼       ▼          ▼
 多线程 多线程  GIL是瓶颈  多线程
 有效  有效   需要绕过GIL  有效
```

核心判断逻辑：**如果一个线程大部分时间在等（等网络、等磁盘、等数据库），那多线程就有效；如果大部分时间在算（纯 Python 循环、字符串处理、JSON 解析），那多线程不如单线程。**

## 为什么移除 GIL 如此困难

过去 30 年间有多次移除 GIL 的尝试，都以失败告终。理解这些尝试的失败原因，比理解 GIL 本身更能把握问题的本质。

### 第一次尝试：Greg Stein（1999）

Greg Stein 在 Python 1.5 时代做了第一次严肃的尝试。他的方案是用细粒度锁替代 GIL——给所有可变数据结构加锁。

**结果：单线程性能下降约 2 倍。** 锁的开销来自于每个操作都要 acquire/release 锁。在单核机器上（那是 1999 年），用两倍的开销换取多线程的并行能力没有意义。

### 第二次尝试：Gilectomy（2016）

Larry Hastings 的 Gilectomy 项目使用了更现代的技术——原子引用计数配合细粒度锁定可变对象。

**结果：单线程 wall time 慢 3.5 倍，CPU time 多 25 倍，内存使用暴增。** 原子操作虽然在 2016 年的硬件上比 1999 年快得多，但在引用计数这个每秒百万次调用的路径上，仍然不够快。

核心问题在于引用计数。Python 程序执行过程中，最频繁的操作就是 `Py_INCREF` 和 `Py_DECREF`——每访问一个变量、传递一个参数、压入一次栈帧都在发生。把这一对操作从普通的 `++` 和 `--` 升级为原子操作，性能损失会被放大到不可接受的程度。

### 第三次尝试：PEP 554 子解释器

另一种思路：如果能给每个线程分配独立的 Python 解释器实例呢？PEP 554 提出了 sub-interpreters 的概念——在同一个进程中创建多个互不共享的解释器，各自拥有独立的 GIL。

```
┌────────────────────────────────────────────┐
│               Python 主进程                  │
│                                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │ 解释器 A  │  │ 解释器 B  │  │ 解释器 C  │ │
│  │ GIL_A    │  │ GIL_B    │  │ GIL_C    │ │
│  │ 线程1    │  │ 线程2    │  │ 线程3    │ │
│  └──────────┘  └──────────┘  └──────────┘ │
│       │              │              │       │
│       └──────────────┼──────────────┘       │
│                      │                      │
│            ┌─────────────────┐              │
│            │   共享内存通道    │  ← 通过 pickle│
│            └─────────────────┘    序列化通信  │
└────────────────────────────────────────────┘
```

问题在于解释器之间完全隔离，不能直接共享对象——必须通过序列化传递数据。对于需要频繁数据交换的场景，序列化/反序列化本身的开销可能超过 GIL 带来的限制。

### 为什么 PEP 703 成功了

Sam Gross 的 PEP 703 之所以成功，在于它没有试图"去掉 GIL"，而是**创造了一个 GIL 可被禁用的 CPython 变体**。关键技术突破：

**偏向引用计数（Biased Reference Counting）**：每个对象有"所有者线程"的概念。所有者线程使用本地引用计数（不需要原子操作），只有跨线程共享的对象才使用原子引用计数。在大多数场景中，对象只在所有者线程内被引用，这意味着绝大多数 `Py_INCREF`/`Py_DECREF` 仍然是普通的 `++`/`--`。

**延迟引用计数**：某些高频修改的对象（如不可变常量）的引用计数被"延迟"处理，减少原子操作冲突。

**QSBR（Quiescent State-Based Reclamation）**：一种无锁的内存回收机制，避免 stop-the-world 式的 GC 暂停。

## 绕过 GIL 的六种方案

在自由线程模式完全普及之前（这可能还需要 3-5 年），日常开发中还是需要知道如何绕过 GIL。

### 方案一：multiprocessing（标准库，最通用）

适用场景：CPU 密集的纯 Python 计算，并行处理独立的任务。

```python
from multiprocessing import Pool
import time


def cpu_intensive(n):
    """计算密集任务：求和"""
    return sum(i * i for i in range(n))


if __name__ == "__main__":
    numbers = [10_000_000] * 8

    # 进程池并行
    start = time.perf_counter()
    with Pool(processes=8) as pool:
        results = pool.map(cpu_intensive, numbers)
    print(f"8 进程: {time.perf_counter() - start:.2f}s")
```

**代价**：每个子进程有独立的 Python 解释器和内存空间——一个原本用 100MB 的主进程，fork 出 8 个子进程后总内存占用可能超过 1GB。进程间数据传递通过 pickle 序列化，大型对象的序列化开销不可忽略。

### 方案二：concurrent.futures（更友好的进程池）

```python
from concurrent.futures import ProcessPoolExecutor, as_completed
import time


def task(x):
    return x ** x


with ProcessPoolExecutor(max_workers=4) as executor:
    futures = {executor.submit(task, i): i for i in range(10)}
    for future in as_completed(futures):
        result = future.result()
        print(f"完成: {futures[future]}^{futures[future]} = {result}")
```

`ProcessPoolExecutor` 封装了 `multiprocessing`，API 与线程池一致，迁移成本更低。适合"有大量独立任务要执行"的场景。

### 方案三：C 扩展释放 GIL

如果你在用 NumPy、Pandas、SciPy 等科学计算库，"绕过 GIL"这件事实际上已经自动发生了。这些库的底层计算逻辑使用 C/Fortran 实现，在执行计算前会释放 GIL：

```c
// NumPy 类库内部的典型模式
Py_BEGIN_ALLOW_THREADS          // 释放 GIL
cblas_dgemm(...);               // 调用 BLAS 做矩阵乘法（多线程并行）
Py_END_ALLOW_THREADS            // 重新获取 GIL
```

这意味着如果你的代码大部分时间花在 NumPy 运算上，**`threading` 已经可以让你利用多核**。问题只出在你自己写的 Python 循环上。

```python
import numpy as np
from concurrent.futures import ThreadPoolExecutor

# 这个多线程有效——np.dot 释放了 GIL
a = np.random.randn(1000, 1000)
b = np.random.randn(1000, 1000)

with ThreadPoolExecutor(max_workers=4) as executor:
    futures = [executor.submit(np.dot, a, b) for _ in range(4)]
    results = [f.result() for f in futures]
```

**陷阱**：Pandas 的 `.apply()` 配合 Python 函数时，每个回调都在 GIL 保护下执行，多线程无效。应该优先使用向量化操作。

### 方案四：Cython 的 nogil 块

Cython 允许你在 Python 语法基础上编写 C 扩展，通过 `nogil` 声明释放 GIL：

```cython
# 文件: compute.pyx
cdef double compute_chunk(double[:] data) nogil:
    """nogil 声明：此函数不操作任何 Python 对象"""
    cdef int i
    cdef double result = 0.0
    for i in range(data.shape[0]):
        result += data[i] * data[i]
    return result

def parallel_compute(double[:] data, int num_threads):
    from cython.parallel import prange
    cdef int i
    cdef double total = 0.0
    with nogil:  # 释放 GIL
        for i in prange(num_threads, nogil=True):
            total += compute_chunk(data)
    return total
```

Cython 的优势在于完全控制。劣势在于 `nogil` 块中**不能操作任何 Python 对象**——只能使用 C 类型（`int`、`double`、C 数组、`cython.view.array`）。Python 字符串、列表、字典、甚至异常处理，在 `nogil` 块中都不能使用。

### 方案五：Numba（JIT 编译）

Numba 是最简单的方案之一——给纯数值计算的函数加一个装饰器：

```python
from numba import njit
from concurrent.futures import ThreadPoolExecutor
import time


@njit(nogil=True)
def heavy_compute(start, end):
    """纯数值计算——Numba 编译为机器码，不依赖 GIL"""
    total = 0.0
    for i in range(start, end):
        total += (i * 0.618) ** 0.5
    return total


# 多线程 CPU 计算现在真正并行！
chunks = [(i * 1_000_000, (i + 1) * 1_000_000) for i in range(8)]
with ThreadPoolExecutor(max_workers=8) as executor:
    results = list(executor.map(lambda x: heavy_compute(*x), chunks))
```

Numba 的工作原理是将 Python 函数 JIT 编译为 LLVM 机器码。`nogil=True` 告诉 Numba 生成的代码不依赖 Python 解释器，因此可以脱离 GIL 运行。

适用条件：纯数值计算，NumPy 数组操作，循环体中没有 Python 对象。如果函数里有字符串处理、I/O 操作、调用其他 Python 函数，Numba 要么无法编译，要么回退到 Python 模式（重新受 GIL 约束）。

### 方案六：asyncio（单线程高并发）

asyncio 不能绕过 GIL，但它提供了一种完全不同的并发思路——**单线程内的事件循环**：

```python
import asyncio
import aiohttp


async def fetch(session, url):
    async with session.get(url) as resp:
        return await resp.text()


async def main():
    urls = ["https://httpbin.org/delay/1"] * 100
    async with aiohttp.ClientSession() as session:
        tasks = [fetch(session, url) for url in urls]
        results = await asyncio.gather(*tasks)
        return results


asyncio.run(main())  # 100 个请求，一个线程，约 1 秒完成
```

asyncio 的精髓在于：**在等待 I/O 的时间里去处理另一个请求**。一个线程就能处理上万个并发连接。它的限制同样明确：所有代码必须是非阻塞的，且不解决 CPU 密集问题。

### 方案选型速查表

| 场景 | 推荐方案 | 有效原因 |
|------|----------|----------|
| 纯 Python 数值计算（无外部库） | `multiprocessing` | 每个进程有自己的 GIL |
| 纯 Python 数值计算（大量小任务） | `ProcessPoolExecutor` | 更友好的进程池 API |
| NumPy/PyTorch/TensorFlow 运算 | `threading` | 运算过程释放了 GIL |
| 大量网络请求并发 | `asyncio` + `aiohttp` | 单线程事件循环，非阻塞 I/O |
| 需要 Python 级代码的真正并行 | Cython + `nogil` | 编译为 C，脱离 GIL 约束 |
| 纯数值函数，不想学 Cython | Numba `@njit(nogil=True)` | JIT 编译为机器码 |
| Python 3.13+ 新项目 | 自由线程模式 | 直接去掉 GIL，多线程真正并行 |

## Python 3.13+ 的自由线程时代

### 什么是自由线程模式

从 Python 3.13（2024 年 10 月发布）开始，CPython 提供了一种**自由线程（free-threaded）**编译选项——构建出一个没有 GIL 的 Python 解释器。这个功能在 3.13 中标记为实验性，在 3.14（2025 年 10 月发布）中进入"受支持"阶段。

```bash
# 安装自由线程版本（macOS 官方安装器自带 python3.13t）
# Ubuntu/Debian
sudo apt install python3.13t

# 通过 pyenv 安装
pyenv install 3.13t

# 确认是自由线程版本
python3.13t -VV
# Python 3.13.0 experimental free-threading build

# 运行时检查
python3.13t -c "import sys; print(not sys._is_gil_enabled())"
# True
```

### 性能表现

不再有 GIL 限制的多线程，CPU 密集任务终于能线性加速：

```python
import threading
import time

def cpu_work(n):
    total = 0
    for i in range(n):
        total += i
    return total

def benchmark(threads_count, work_per_thread):
    start = time.perf_counter()
    threads = [
        threading.Thread(target=cpu_work, args=(work_per_thread,))
        for _ in range(threads_count)
    ]
    for t in threads: t.start()
    for t in threads: t.join()
    return time.perf_counter() - start

# GIL 版本（python3.13）
print("=== 有 GIL ===")
print(f"1 线程: {benchmark(1, 100_000_000):.2f}s")
print(f"4 线程: {benchmark(4, 25_000_000):.2f}s")  # 预期和单线程差不多

# 自由线程版本（python3.13t）
print("=== 无 GIL ===")
print(f"1 线程: {benchmark(1, 100_000_000):.2f}s")
print(f"4 线程: {benchmark(4, 25_000_000):.2f}s")  # 预期接近 4 倍加速
```

来自社区的基准测试数据：

| 工作负载 | 有 GIL | 无 GIL | 加速比 |
|----------|--------|--------|--------|
| 数据管道处理（64 核） | 1.12x | 6.22x | 5.5x |
| API 压力测试 | 0.73x | 13.93x | 19x |
| 3 线程计算（x86） | 0.61x | 2.08x | 3.4x |

### 代价与权衡

**单线程性能退化**：自由线程模式下没有 GIL 保护，每个引用计数操作都需要原子指令。在 Python 3.13 中，单线程性能退化约 40%（主要因为自适应解释器被禁用），到 3.14 已改善到约 3%-8%。

**内存开销**：3.13 中某些对象被标记为"不可回收"以减少引用计数竞争，导致额外内存占用。3.14 通过改进的偏向引用计数大幅缓解。

**线程安全不再是免费的**：GIL 曾提供"意外"的线程安全性——`list.append()` 之类的基本操作在有 GIL 时看起来像是原子的。自由线程模式下，**任何共享可变数据的并发修改都需要显式同步**：

```python
# 有 GIL 时这段代码"碰巧"安全（但不应该依赖）
count = 0

def increment():
    global count
    for _ in range(100000):
        count += 1  # 有 GIL 时很少出问题，但本质上是竞态

# 自由线程模式：必须加锁
import threading
lock = threading.Lock()
count = 0

def increment_safe():
    global count
    for _ in range(100000):
        with lock:
            count += 1
```

### C 扩展兼容性

C 扩展需要显式声明是否兼容自由线程模式。PyO3（Rust 的 Python 绑定）支持通过 `#[pymodule(gil_used = false)]` 声明。纯 Python 的包不受影响。

目前大约 **1/6 的 Top 360 PyPI 包**已经提供自由线程兼容的 wheel。NumPy、Pandas、SciPy 等主流科学计算包已支持。

如果一个 C 扩展不兼容自由线程模式，CPython 会在导入时**自动重新启用 GIL**并打印一条警告：

```
ImportWarning: The module 'some_extension' is not compatible with
free-threading. The GIL will be enabled for your process.
```

## 最佳实践总结

### 立即可以做的事

1. **定位瓶颈，不要猜测。** 用 `cProfile` 或 `py-spy` profile 你的程序。如果 80% 的时间花在 NumPy 的矩阵运算上，GIL 根本不是你的问题。

2. **区分 CPU 密集和 I/O 密集。** I/O 密集场景放心用 `threading` 或 `asyncio`，GIL 会在 I/O 等待时自动释放。

3. **用向量化操作替代 Python 循环。** Pandas 的 `.apply(lambda x: ...)` 受 GIL 约束；`df['col'].sum()` 在 C 层执行，不受约束。能向量化就向量化。

4. **先尝试 C 扩展库，再考虑 multiprocessing。** NumPy、Polars、lxml 等库在底层释放 GIL。如果能用它们替代纯 Python 实现，多线程就能工作。

5. **CPU 密集纯 Python → multiprocessing。** 当上面几条都不适用时，用 `ProcessPoolExecutor`。注意内存开销和序列化成本。

### 展望自由线程

如果你在启动新项目，建议用 `python3.13t` 做兼容性测试。自由线程是 Python 社区 30 年来最重要的一次底层变革——它不会在一夜之间改变一切，但会成为默认选项。

GIL 的故事是一个关于**工程权衡**的经典案例。一个在 1992 年做出的正确决策，支撑了 Python 三十年的发展，现在正被更先进的工程技术平稳替代。理解 GIL 的设计考量、内部机制和绕过方案，能让你在它彻底成为历史之前，写出最优的 Python 并发代码。
