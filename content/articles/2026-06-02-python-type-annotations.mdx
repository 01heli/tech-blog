## 从一个让你血压飙升的夜晚说起

凌晨两点，你接到一个紧急 Bug：用户注册接口返回 500 错误。你找到对应的代码：

```python
def process_user(data, options=None):
    result = helper(data)
    if options:
        result = apply_options(result, options)
    return save(result)
```

你盯着这段代码，脑子里冒出三个问题：

1. `data` 是什么？一个字典？一个对象？还是 JSON 字符串？
2. `helper()` 返回什么？`result` 长什么样？
3. `options` 是字典还是列表？里面有哪些字段？

你不得不用 `print()` 一行一行地追踪，甚至要翻到数据库看最终落库的结构。这个过程浪费了你 40 分钟——而修 Bug 本身只花了 5 分钟。

这种痛苦有一个名字：**缺少类型信息**。

Python 是一门动态类型语言，变量的类型在运行时才确定。这给了我们极大的灵活性，但也让"阅读别人的 Python 代码"变成了一场推理游戏。**类型注解（Type Annotations）** 就是来解决这个问题的——它让你在写代码时，就明确告诉读代码的人（包括三个月后的你自己）："这个参数应该传什么，这个函数会返回什么。"

这篇文章将从零开始，带你彻底掌握 Python 类型注解和函数签名的全部核心知识。

## 第一部分：基础类型注解——给你的函数穿上"说明书"

### 1.1 从一个最简单的例子开始

```python
# 没有类型注解——全靠猜
def greet(name, age):
    return f"{name} is {age} years old"

# 有类型注解——一目了然
def greet(name: str, age: int) -> str:
    return f"{name} is {age} years old"
```

语法极其简单：

```
def 函数名(参数名: 类型, ...) -> 返回值类型:
```

这行代码告诉你三件事：
- `name` 应该传一个字符串
- `age` 应该传一个整数
- 这个函数返回一个字符串

**注意**：这些注解在运行时**不会被强制执行**。你可以传一个列表给 `name`，Python 不会报错——至少不会在传参的时候报错。类型注解的价值体现在**写代码的时候**（IDE 自动补全和提示）和**运行类型检查器的时候**（mypy/pyright 提前发现错误）。

### 1.2 内置类型的全家桶

Python 3.9+ 可以直接使用内置类型作为泛型注解：

```python
# 基础类型
name: str = "Alice"
age: int = 30
price: float = 9.99
is_active: bool = True
nothing: None = None

# 容器类型（Python 3.9+ 可以直接用内置类型写泛型）
names: list[str] = ["Alice", "Bob"]
scores: tuple[int, str] = (1, "first")
config: dict[str, int] = {"timeout": 30, "retries": 3}
unique_ids: set[int] = {1, 2, 3}

# 联合类型：一个变量可以是多种类型之一
def get_user(user_id: int | str) -> dict[str, str] | None:
    """接收数字 ID 或用户名字符串，返回用户字典或 None"""
    ...
```

这里有一个 Python 3.10 引入的优雅语法：**`X | Y` 替代 `Union[X, Y]`**：

```python
# 旧写法（不推荐）
from typing import Union, Optional

def old_style(x: Union[int, str], y: Optional[float] = None) -> None:
    ...

# 新写法（Python 3.10+，推荐）
def new_style(x: int | str, y: float | None = None) -> None:
    ...
```

`X | None` 就是 `Optional[X]` 的现代化写法——更直观，不需要额外导入。

### 1.3 类型注解的演进时间线

Python 的类型系统在近几年经历了爆发式演进。先建立一个整体时间线，方便你在不同版本间找到对应的语法：

```
Python 3.0  (2008)  → 函数注解语法诞生（PEP 3107），但只作为元数据存在
Python 3.5  (2015)  → typing 模块诞生（PEP 484），类型注解有了标准库支持
Python 3.6  (2016)  → 变量注解语法（PEP 526）：x: int = 5
Python 3.7  (2018)  → from __future__ import annotations 延迟求值
Python 3.8  (2019)  → TypedDict、Literal、Protocol、final 加入 typing
Python 3.9  (2020)  → list[int] 替代 typing.List[int]（PEP 585）
Python 3.10 (2021)  → X | Y 替代 Union[X, Y]（PEP 604）
Python 3.11 (2022)  → Self 类型、LiteralString、NotRequired、Never（PEP 673/675）
Python 3.12 (2023)  → 泛型新语法 class Foo[T]（PEP 695）、type 语句
Python 3.13 (2024)  → 类型参数默认值（PEP 696）、annotationlib 模块
Python 3.14 (2025)  → annotationlib 正式化、类型系统持续完善
```

如果你是 Python 3.10+ 的新项目，可以直接使用最现代的语法。如果你在维护老项目，好消息是旧的 `typing` 语法**从未被废弃**——新旧语法可以和平共存。

### 1.4 `Any`：类型系统里的"万能后门"

```python
from typing import Any

def dangerous(data: Any) -> Any:
    return data.do_something()  # 类型检查器不会帮你检查任何东西
```

`Any` 告诉类型检查器："别管这个值，它可以是任何类型。"它在两种场景下有用：
- 与不提供类型存根（stub）的第三方库交互时
- 逐步为老项目添加类型注解时

但 `Any` 是传染病——`Any` 经过的任何运算，结果也是 `Any`。**每个 `Any` 都是一处类型安全的漏洞。** 能用具体类型就不用 `Any`，能泛型就不 `Any`。

## 第二部分：函数签名——用类型描述"怎么调用一个函数"

函数签名（Function Signature）是类型注解中最核心也最容易被忽略的概念。它不只是在参数后面加个类型——它要描述：**这个函数接收什么、返回什么、参数之间有怎样的类型关系**。

### 2.1 基础函数签名

```python
# 最完整的函数签名包含：参数类型 + 默认值 + 返回值类型
def fetch_data(
    url: str,
    timeout: float = 5.0,
    *,
    headers: dict[str, str] | None = None,
    retries: int = 3,
) -> tuple[int, bytes]:
    """
    参数说明：
    - url: 请求地址
    - timeout: 超时秒数（仅限关键字参数，* 后面的参数必须用关键字传）
    - headers: 自定义请求头（可选）
    - retries: 失败重试次数
    返回：(状态码, 响应体)
    """
    ...
```

这里有一个容易被忽略的细节——`*` 在参数列表中的作用：

```python
# * 之后的所有参数都变成了"仅限关键字参数"
def configure(host: str, *, port: int, debug: bool = False) -> None:
    ...

configure("localhost", port=8080)          # ✅
configure("localhost", 8080)               # ❌ TypeError！必须写 port=
```

这种写法强迫调用方在关键配置上使用命名参数，极大提升了可读性——`configure("localhost", port=8080)` 比 `configure("localhost", 8080)` 清楚一百倍。

### 2.2 `Callable`——当参数是"一个函数"时

这是类型注解最常见的"进阶场景"。你需要把一个函数传给另一个函数时，怎么标注它？

```python
from typing import Callable

# Callable[[参数1类型, 参数2类型, ...], 返回值类型]

def apply_twice(func: Callable[[int], int], x: int) -> int:
    """把函数调用两次：func(func(x))"""
    return func(func(x))

def double(n: int) -> int:
    return n * 2

print(apply_twice(double, 5))  # 20：5 → 10 → 20

# 更多例子
Callback = Callable[[str, int], bool]   # 接收 str 和 int，返回 bool
Handler = Callable[[], None]            # 无参数，不返回
MultiCB = Callable[..., list[str]]      # 参数随意，返回 list[str]
```

`Callable` 的格式可以用一句话记住：**方括号里先写参数类型组成的列表，再写返回值类型**。

### 2.3 `@overload`——同一个函数，多张"脸"

有些函数的行为会根据参数类型而变化。比如标准库的 `open()`：

```python
open("file.txt")            # 返回 TextIOWrapper（文本模式）
open("file.txt", "rb")      # 返回 BufferedReader（二进制模式）
```

你无法用单一的 `Callable` 描述它——因为**参数类型和返回值类型之间存在依赖关系**。这时用 `@overload`：

```python
from typing import overload, Literal

@overload
def smart_open(path: str, mode: Literal["r", "w"]) -> str: ...

@overload
def smart_open(path: str, mode: Literal["rb", "wb"]) -> bytes: ...

def smart_open(path: str, mode: str) -> str | bytes:
    # 真正的实现写在这里
    if "b" in mode:
        return open(path, mode).read()  # type: ignore[return-value]
    return open(path, mode).read()
```

`@overload` 的精髓在于：**装饰的函数体可以留空（用 `...` 占位），它们只是给类型检查器看的"说明书"**。真正干活的函数写在最后，不带 `@overload`。这种模式在重载运算符、处理不同类型输入、为第三方库编写类型存根时极其有用。

### 2.4 `ParamSpec`——为装饰器保留完整签名

这是高阶 Python 中最强大的类型工具。当你写一个装饰器时，你希望被装饰函数的**参数签名原封不动地保留下来**：

```python
from typing import Callable, TypeVar, ParamSpec

P = ParamSpec("P")   # 代表"任意参数列表"
R = TypeVar("R")     # 代表"任意返回类型"

def with_logging(func: Callable[P, R]) -> Callable[P, R]:
    """一个保留原函数签名的日志装饰器"""
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"[LOG] 调用 {func.__name__}")
        result = func(*args, **kwargs)
        print(f"[LOG] {func.__name__} 返回 {type(result).__name__}")
        return result
    return wrapper

@with_logging
def add(a: int, b: int) -> int:
    return a + b

# IDE 知道 add(1, 2) 返回 int，并且 a 和 b 都是 int！
result: int = add(1, 2)  # ✅ 类型检查通过
```

在没有 `ParamSpec` 之前（Python 3.9 及更早），你只能把装饰器的参数写成 `*args: Any, **kwargs: Any`——丢失了原始参数的类型信息。`ParamSpec` 解决了这个长期痛点。

实际操作中，`ParamSpec` + `TypeVar` + `Callable` 的组合几乎适用于所有装饰器场景：

```python
from typing import Callable, TypeVar, ParamSpec
import time

P = ParamSpec("P")
R = TypeVar("R")

def measure_time(func: Callable[P, R]) -> Callable[P, R]:
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} 耗时 {elapsed:.3f}s")
        return result
    return wrapper

@measure_time
def compute(n: int) -> float:
    return sum(i ** 0.5 for i in range(n))

# compute 的参数和返回值类型被完整保留！
```

### 2.5 `Self`——链式调用爱好者的福音

Python 3.11 引入了 `Self` 类型。在以前，要让一个类的方法返回"自己的类型"，你得绕一个大圈子：

```python
# Python 3.10 及之前的写法（繁琐）
from typing import TypeVar
TBuilder = TypeVar("TBuilder", bound="Builder")

class Builder:
    def set_x(self: TBuilder, x: int) -> TBuilder:
        self.x = x
        return self
    def set_y(self: TBuilder, y: int) -> TBuilder:
        self.y = y
        return self

# Python 3.11+ 的写法（直观）
from typing import Self

class Builder:
    def set_x(self, x: int) -> Self:
        self.x = x
        return self
    def set_y(self, y: int) -> Self:
        self.y = y
        return self

# 链式调用，类型检查完全正确
b = Builder().set_x(10).set_y(20)
```

`Self` 还会自动处理继承关系——子类的 `set_x()` 返回的就是子类类型，不需要重新标注。

## 第三部分：结构化类型——让 dict 不再是"黑洞"

Python 中最常见的数据载体是字典。但 `dict[str, Any]` 给不了你任何有用的信息——你知道键是字符串，但不知道键名叫什么、值分别是什么类型。

### 3.1 `TypedDict`——给字典写一份"字段合同"

```python
from typing import TypedDict

class Movie(TypedDict):
    """这就是一份字典的'字段合同'"""
    title: str
    year: int
    rating: float

# 现在 IDE 会提示你 title、year、rating 三个键
# 类型检查器会验证每个键对应的值的类型
def format_movie(m: Movie) -> str:
    return f"《{m['title']}》（{m['year']}），评分 {m['rating']}"

movie: Movie = {
    "title": "盗梦空间",
    "year": 2010,
    "rating": 9.3,
}

print(format_movie(movie))  # ✅
# format_movie({"title": "xxx"})  # ❌ 缺少 year 和 rating，mypy 会报错
```

Python 3.11 引入了 `NotRequired`，用来标记可选字段：

```python
from typing import TypedDict, NotRequired

class UserProfile(TypedDict):
    name: str
    email: str
    age: NotRequired[int]        # 可以不提供
    bio: NotRequired[str]        # 可以不提供

# 两种声明方式：class 语法 vs 函数式语法
# class 语法（推荐，IDE 支持更好）
class Point(TypedDict):
    x: int
    y: int

# 函数式语法（动态场景）
from typing import TypedDict
Point = TypedDict("Point", {"x": int, "y": int})
```

**何时使用 `TypedDict` 而非普通 dict？** 

```
你的数据是什么样的？
      │
      ├── 字段结构固定（如 API 返回的 JSON） → TypedDict ✅
      ├── 字段名动态变化、不可预知            → dict[str, T]
      ├── 只有一两个字段                     → 也许不用 TypedDict
      └── 需要方法 + 数据一起封装             → 考虑 dataclass 或普通类
```

### 3.2 `Protocol`——鸭子类型的"静态签证"

Python 讲究鸭子类型（Duck Typing）："如果它走起来像鸭子，叫起来像鸭子，那它就是鸭子。" `Protocol` 就是这种哲学的类型注解翻译：

```python
from typing import Protocol

class Drawable(Protocol):
    """任何有 draw() 方法的对象，都是 Drawable"""
    def draw(self) -> None: ...

# 注意：Circle 和 Square 没有继承任何共同的父类！
class Circle:
    def draw(self) -> None:
        print("◯ 画圆")

class Square:
    def draw(self) -> None:
        print("□ 画方")

class Triangle:
    pass

def render(shape: Drawable) -> None:
    shape.draw()

render(Circle())   # ✅ Circle 有 draw()，符合协议
render(Square())   # ✅ Square 有 draw()，符合协议
render(Triangle()) # ❌ Triangle 没有 draw()，mypy 报错
```

这就是**结构性子类型（Structural Subtyping）**——类型兼容性由**结构**决定，而非**继承关系**。Java 和 C# 是名义类型系统（你必须写 `class Dog extends Animal` 才是子类型），Python 的 `Protocol` 支持结构类型系统（你有 `run()` 方法就是 `Runnable`）。

`Protocol` vs 抽象基类 `ABC` 的核心区别：

```
                    Protocol                      ABC
检查时间      →  静态（mypy/pyright）         运行时（isinstance）
是否需要继承  →  ❌ 不需要，有方法就行        ✅ 需要显式继承
运行时开销    →  零开销                      有 isinstance 开销
适合场景      →  类型标注、接口约定           运行时多态、插件系统
```

**实战用法——定义"数据仓库"接口**：

```python
from typing import Protocol

class UserRepository(Protocol):
    """任何满足这个协议的对象都可以作为用户数据源"""
    def find_by_id(self, user_id: int) -> dict | None: ...
    def find_by_email(self, email: str) -> dict | None: ...
    def save(self, user_data: dict) -> int: ...

# PostgreSQL 实现
class PostgresUserRepo:
    def find_by_id(self, user_id: int) -> dict | None: ...
    def find_by_email(self, email: str) -> dict | None: ...
    def save(self, user_data: dict) -> int: ...

# Redis 缓存实现
class RedisUserCache:
    def find_by_id(self, user_id: int) -> dict | None: ...
    def find_by_email(self, email: str) -> dict | None: ...
    def save(self, user_data: dict) -> int: ...

# get_user 可以接受任何满足协议的实现
def get_user(repo: UserRepository, user_id: int) -> dict | None:
    return repo.find_by_id(user_id)

# 两个都能用！
get_user(PostgresUserRepo(), 1)  # ✅
get_user(RedisUserCache(), 1)    # ✅
```

这就是依赖倒置原则的类型注解版本——高层模块（`get_user`）不依赖低层模块（`PostgresUserRepo`），二者都依赖抽象（`UserRepository` Protocol）。

### 3.3 `dataclass`——当数据也需要方法时

`TypedDict` 是纯数据容器，`Protocol` 定义行为契约。而 `dataclass` 则介于二者之间——它既是数据容器，又可以附带方法：

```python
from dataclasses import dataclass, field

@dataclass
class User:
    name: str
    age: int
    tags: list[str] = field(default_factory=list)  # 可变默认值要用 field()

    @property
    def is_adult(self) -> bool:
        return self.age >= 18

    def greet(self) -> str:
        return f"Hi, I'm {self.name}"

# 自动生成 __init__、__repr__、__eq__
user = User(name="Bob", age=25)
print(user)            # User(name='Bob', age=25, tags=[])
print(user.is_adult)   # True
```

选择策略速查：

| 需求 | 推荐方案 |
|------|----------|
| 纯数据，JSON 序列化/API 交互 | `TypedDict` |
| 纯行为，定义接口规范 | `Protocol` |
| 数据 + 方法，且需要 `__init__` 自动生成 | `dataclass` |
| 复杂状态，需要完全控制初始化/继承 | 普通类 |
| 不可变数据 | `NamedTuple` |

## 第四部分：泛型——让类型参数化

泛型是类型注解中最容易被"劝退"但实际最有用的部分。它的核心思想很简单：**不写死类型，把类型也变成一个"参数"**。

### 4.1 从具体到泛型：一个自然的过程

假设你写了一个简单的栈：

```python
class IntStack:
    def __init__(self) -> None:
        self._items: list[int] = []
    def push(self, item: int) -> None:
        self._items.append(item)
    def pop(self) -> int:
        return self._items.pop()
```

这个栈只支持 `int`。如果明天你需要一个 `str` 栈，你得把整个类复制一遍，把所有 `int` 换成 `str`。这太蠢了。

泛型的解决方案——**把元素类型变成一个参数**：

```python
# Python 3.12 新语法（PEP 695）
class Stack[T]:
    def __init__(self) -> None:
        self._items: list[T] = []
    def push(self, item: T) -> None:
        self._items.append(item)
    def pop(self) -> T:
        return self._items.pop()

# 使用时指定类型参数
int_stack = Stack[int]()
int_stack.push(1)      # ✅
# int_stack.push("hi") # ❌ 类型检查器报错

str_stack = Stack[str]()
str_stack.push("hello") # ✅
print(str_stack.pop())  # "hello"，IDE 知道它是 str！
```

`class Stack[T]` 中的 `[T]` 就是**类型参数列表**。`T` 在使用时被"填入"具体的类型（`int`、`str` 等），和函数参数 `def f(x)` 中 `x` 被填入具体的值是一个道理。

### 4.2 PEP 695 新语法与旧语法对比

Python 3.12 的 PEP 695 彻底改变了泛型的写法。以下是完整的对照：

**泛型类：**

```python
# 旧语法（Python 3.11 及之前）
from typing import TypeVar, Generic
T = TypeVar("T")
class Stack(Generic[T]):
    def __init__(self) -> None: ...
    def push(self, item: T) -> None: ...
    def pop(self) -> T: ...

# 新语法（Python 3.12+）
class Stack[T]:
    def __init__(self) -> None: ...
    def push(self, item: T) -> None: ...
    def pop(self) -> T: ...
```

**泛型函数：**

```python
# 旧语法
T = TypeVar("T")
def first(items: list[T]) -> T | None:
    return items[0] if items else None

# 新语法
def first[T](items: list[T]) -> T | None:
    return items[0] if items else None
```

**类型别名：**

```python
# 旧语法
from typing import TypeAlias
T = TypeVar("T")
Vector: TypeAlias = tuple[T, T, T]

# 新语法
type Vector[T] = tuple[T, T, T]   # type 在这里是软关键字
```

新语法的优势一目了然：**类型参数直接在函数/类的方括号里声明，不需要先定义 `TypeVar` 再引用**。这让泛型代码的读写和普通的参数化思维保持一致。

### 4.3 类型参数的约束：`T: SomeType`

有时候你不想接受所有类型——你只想接受"有某个属性的类型"：

```python
# 约束：T 必须是 HasName 的子类型
class HasName:
    name: str

class Registry[T: HasName]:
    """只存储有 name 属性的对象"""
    def __init__(self) -> None:
        self._items: dict[str, T] = {}
    def register(self, item: T) -> None:
        self._items[item.name] = item
    def get(self, name: str) -> T | None:
        return self._items.get(name)
```

`T: HasName` 的意思是"T 必须是 HasName 或者它的子类"。这样类型检查器知道 T 一定有 `.name` 属性，在 `self._items[item.name]` 这里就不会报错了。

**约束 vs 边界（bound vs constraints）——一个需要区分清楚的细节：**

```python
# bound（上界）：T 可以是该类型或其任意子类型
T = TypeVar("T", bound=float)  # T 可以是 float, int, 或 float 的子类

# constraints（约束）：T 只能是这几个具体的类型
T = TypeVar("T", int, str)     # T 只能是 int 或 str
```

PEP 695 的新语法支持这两种写法：

```python
# 上界（bound）
class Numeric[T: float]: ...            # T 必须是 float 或其子类

# 约束（constraints）
class TextOrNum[T: (str, int)]: ...     # T 只能是 str 或 int
```

### 4.4 Python 3.13：类型参数默认值

Python 3.13 进一步引入了**类型参数默认值**（PEP 696），让泛型更加方便：

```python
# 默认类型参数
class Box[T = int]:
    value: T | None = None

box_default = Box()       # 等价于 Box[int]()
box_custom = Box[str]()   # 显式指定为 str

# 泛型函数也可以有默认值
def merge[T = str](items: list[T], sep: str = ", ") -> str:
    return sep.join(str(i) for i in items)
```

### 4.5 `TypeVarTuple`——给"不定数量类型"建模

Python 3.11 引入了 `TypeVarTuple`（PEP 646），用来处理"任意数量的类型参数"：

```python
from typing import TypeVarTuple

Ts = TypeVarTuple("Ts")

class Tensor[*Ts]:
    """张量——可以接受任意数量的维度类型"""
    def shape(self) -> tuple[*Ts]:
        ...

# Tensor[int]          → 一维张量
# Tensor[int, int]     → 二维张量
# Tensor[int, int, int] → 三维张量
```

这主要用在科学计算（NumPy、PyTorch）和多维数组的场景。对大多数 Web/后端开发者来说，`TypeVarTuple` 算是"知道有这个东西就行"的级别。

## 第五部分：运行时的类型——从"标注"到"强制执行"

类型注解是静态的——Python 解释器不会因为它们而拒绝运行代码。但有一整套生态能在**运行时**利用类型注解做校验，让类型真正成为安全边界。

### 5.1 Pydantic——类型注解即校验规则

[Pydantic](https://docs.pydantic.dev/) 是最流行的 Python 数据校验库。它的核心哲学是：**你的类型注解就是你的校验规则**：

```python
from pydantic import BaseModel, Field
from typing import Annotated

class UserCreate(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    age: int = Field(ge=0, le=150)   # ge = greater or equal, le = less or equal
    email: str = Field(pattern=r"^[\w\.-]+@[\w\.-]+\.\w+$")

# 传入合法数据
user = UserCreate(name="Alice", age=25, email="alice@example.com")
print(user.model_dump())  # {'name': 'Alice', 'age': 25, 'email': 'alice@example.com'}

# 传入非法数据——Pydantic 抛出 ValidationError
try:
    UserCreate(name="", age=300, email="not-an-email")
except Exception as e:
    print(e)
    # 三个字段都有错误：name 太短、age 超出范围、email 格式不对
```

Pydantic v2 的核心用 Rust 重写（`pydantic-core`），校验速度比 v1 快了 5-50 倍。

### 5.2 FastAPI——类型注解驱动整个 Web 框架

[FastAPI](https://fastapi.tiangolo.com/) 把 Python 类型注解的威力发挥到了极致：

```python
from fastapi import FastAPI, Query
from pydantic import BaseModel
from typing import Annotated

app = FastAPI()

class Item(BaseModel):
    name: str
    price: float
    is_available: bool = True

@app.post("/items/")
async def create_item(item: Item) -> dict[str, str]:
    # FastAPI 在进入这个函数之前就完成了校验
    # item 一定是一个合法的 Item 实例
    return {"message": f"创建了 {item.name}，价格 {item.price}"}

@app.get("/search")
async def search(
    q: Annotated[str, Query(min_length=1, max_length=50)],
    page: Annotated[int, Query(ge=1)] = 1,
) -> list[Item]:
    # 查询参数会自动校验：q 不能为空且不超过 50 字，page 至少为 1
    ...
```

FastAPI 做的几件事全部基于类型注解：
1. **请求校验**——根据 `Item` 的字段类型自动校验 JSON body
2. **查询参数校验**——根据 `Annotated` 中的元数据校验 `q` 和 `page`
3. **自动生成 OpenAPI 文档**——`/docs` 的 Swagger UI 是根据类型注解自动生成的
4. **编辑器自动补全**——请求和响应的数据模型一目了然

这就是"类型即文档，类型即校验"的真正含义。

### 5.3 SQLAlchemy 2.0——类型注解写入 ORM

[SQLAlchemy 2.0](https://docs.sqlalchemy.org/en/20/) 全面拥抱类型注解：

```python
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy import String, Integer

class Base(DeclarativeBase):
    pass

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    name: Mapped[str] = mapped_column(String(100))
    age: Mapped[int | None] = mapped_column(Integer, nullable=True)
    # 类型注解直接映射到数据库列类型！
```

### 5.4 纯运行时的类型检查工具

如果你不需要 Pydantic 这样的大框架，也有一些轻量级选项：

```python
# 内置的 isinstance 检查（最基础）
def process(x: int | str) -> None:
    if not isinstance(x, (int, str)):
        raise TypeError(f"Expected int or str, got {type(x)}")

# typemapping 库（支持泛型检查）
from typemapping.type_check import extended_isinstance
extended_isinstance([1, 2, 3], list[int])   # True
extended_isinstance([1, 2, 3], list[str])   # False

# typeguard 库（装饰器一键检查）
from typeguard import typechecked

@typechecked
def add(a: int, b: int) -> int:
    return a + b

add(1, "2")  # 抛异常：expected int for argument 'b', got str
```

## 第六部分：工程化落地——把类型检查真正跑起来

类型注解写了一大堆，但如果不运行类型检查器，它们就只是美化了的注释。

### 6.1 mypy：最主流的 Python 类型检查器

```bash
# 安装
pip install mypy

# 检查单个文件
mypy app.py

# 检查整个项目
mypy src/
```

配置 `pyproject.toml`：

```toml
[tool.mypy]
python_version = "3.12"
strict = true                          # 开启所有严格检查
warn_return_any = true                 # 返回 Any 时警告
warn_unused_ignores = true            # 不需要的 type: ignore 也警告
disallow_untyped_defs = true          # 禁止不写类型注解的函数
disallow_incomplete_defs = true       # 禁止只写了部分注解的函数
```

**渐进式采用路径**——如果你在给一个老项目加类型注解，一次性全加完不现实。推荐分步推进：

```
阶段 1：新增代码必须带类型注解（靠团队约定）
阶段 2：核心模块的公开 API 全部标注
阶段 3：开启 mypy --strict 并加入 CI 流水线
阶段 4：逐步消灭剩余的 Any 和 type: ignore
```

### 6.2 pyright / Pylance：IDE 里的实时检查

[pyright](https://github.com/microsoft/pyright) 是微软开发的 TypeScript 风格的类型检查器，速度比 mypy 快，默认集成在 VS Code 的 Pylance 扩展中：

```json5
// .vscode/settings.json
{
    "python.analysis.typeCheckingMode": "strict",
    "python.analysis.diagnosticMode": "workspace"
}
```

pyright 的 `pyproject.toml` 配置：

```toml
[tool.pyright]
typeCheckingMode = "strict"
pythonVersion = "3.12"
reportAny = true
reportUnusedImport = true
```

**mypy vs pyright 怎么选？** mypy 生态更成熟，插件更多，对 PEP 新特性的支持相对稳健；pyright 速度更快，对前沿 PEP 的支持往往更早，VS Code 集成更好。很多团队的做法是：**开发中用 pyright/Pylance 实时反馈，CI 中用 mypy 做最终检查**——双重保险。

### 6.3 CI 集成示例（GitHub Actions）

jobs:

### 6.4 常见错误速查与排查

类型检查器报错时，新手最容易踩的坑：

| 错误信息 | 原因 | 修复 |
|----------|------|------|
| `Need type annotation for 'x'` | 你开启了 `disallow_untyped_defs` 但某变量没标注 | 给变量加类型注解 |
| `None has no attribute 'xxx'` | 你的函数可能返回 `None`，但你没处理 | 加 `if result is not None:` 守卫 |
| `Incompatible types in assignment` | 你把 `str` 赋给了 `int` 变量 | 检查赋值逻辑，或调整类型 |
| `Argument "x" to "f" has incompatible type "str"; expected "int"` | 参数类型错了 | 追踪传入值的来源，调整类型 |
| `"list" is not subscriptable` | Python ≤ 3.8 不支持 `list[int]` | 升级到 3.9+ 或用 `typing.List[int]` |
| `Name "xxx" is not defined` | 前向引用但没有 `from __future__ import annotations` | 在文件顶部加 import |

### 6.5 `from __future__ import annotations`——你几乎总是需要它

```python
from __future__ import annotations  # 放在文件最顶部，在所有 import 之前

class TreeNode:
    def get_children(self) -> list[TreeNode]:  # TreeNode 还没定义完？
        ...                                     # 没关系，注解被当作字符串延迟求值了
```

这个 import 让所有注解变成**延迟求值**——注解被当作字符串存起来，只在 `typing.get_type_hints()` 调用时才解析。好处是：
- 前向引用问题迎刃而解
- 导入时间略微加快（注解不需要在导入时求值）
- 是 Python 社区的普遍推荐做法

Python 3.14 引入了 `annotationlib` 模块，提供了比 `typing.get_type_hints()` 更可靠的运行时注解反射能力——当你在运行时真正需要解析类型注解时（比如实现一个自定义的序列化库），这是你需要的工具。

## 第八部分：常见反模式——给新手和老手的避坑指南

### 反模式 1：过度标注

```python
# ❌ 过度标注——没必要的标注只会增加噪音
def calculate(x: int, y: int) -> int:
    result: int = x + y           # result 的类型从 x + y 已经很明确了
    is_large: bool = result > 100 # 同理
    return result

# ✅ 合理标注——只标注公开 API
def calculate(x: int, y: int) -> int:
    result = x + y
    is_large = result > 100       # 类型检查器会自动推断
    return result
```

**原则：公开函数的参数和返回值必须标注。局部变量、私有方法的内部逻辑，让类型检查器自己推断。**

### 反模式 2：把 `Any` 当创可贴

```python
# ❌ Any 是类型系统的漏洞，它会传染
def get_user(id: Any) -> Any:
    ...

# ✅ 用泛型或具体类型
def get_user[T](id: T) -> dict[str, str] | None:
    ...
```

### 反模式 3：混用新旧语法

```python
# ❌ 混用——团队协作的噩梦
def process(items: list[str | int]) -> tuple[Union[int, str], ...]:
    ...

# ✅ 统一用新语法（Python 3.10+ 项目）
def process(items: list[str | int]) -> tuple[int | str, ...]:
    ...
```

### 反模式 4：忘记处理 `None`

```python
# ❌ 不处理 None
def find_user(user_id: int) -> dict | None:
    ...

user = find_user(1)
print(user["name"])  # mypy 报错：None 没有 __getitem__ 方法

# ✅ 加 None 守卫
user = find_user(1)
if user is not None:
    print(user["name"])   # mypy 会在这里自动窄化类型
else:
    print("用户不存在")
```

### 反模式 5：Pydantic 模型当 TypedDict 用

```python
# ❌ Pydantic 模型有校验开销，不适合只是"标注字典结构"的场景
from pydantic import BaseModel
class Config(BaseModel):      # 太重了
    host: str
    port: int

# ✅ 如果只是类型标注（不需要运行时校验），用 TypedDict
from typing import TypedDict
class Config(TypedDict):      # 零运行时开销
    host: str
    port: int
```

## 总结

Python 的类型注解体系经历了一个从"给函数贴标签"到"类型即文档、类型即契约"的进化。这篇文章覆盖了四个层次：

1. **基础标注**——`x: int`、`list[str]`、`int | None`：让你的函数不再"全靠猜"
2. **函数签名**——`Callable`、`@overload`、`ParamSpec`、`Self`：用类型精确描述函数的行为
3. **结构化类型**——`TypedDict`、`Protocol`、`dataclass`：把字典从黑洞变成白盒，用协议替代继承
4. **泛型**——`class Stack[T]`、类型约束、PEP 695 新语法：让类型也变成可以参数化的东西

理解类型注解不是为了"把 Python 写成 Java"——而是为了让你的代码**自文档化**。一个标注良好的 Python 函数，任何人（包括三个月后的你）看一眼就知道怎么用。

### 给不同角色的建议

**如果你是后端开发**：立即在你负责的 FastAPI/Flask/Django 项目的所有端点函数上添加类型注解。Pydantic 模型是你的第一优先级——它同时服务于类型检查、请求校验和 OpenAPI 文档生成，一份注解三份收益。

**如果你是数据工程师/科学家**：你写的 `pandas`/`numpy` 操作函数可以从类型注解中受益。在 Jupyter Notebook 中开启 Pylance（VS Code），你会立刻获得更好的 DataFrame 方法补全。对于需要交付给工程团队的 Python 包，类型注解是"专业交付"的标配。

**如果你是 DevOps/平台工程师**：在你的团队的 CI 流水线中加入 `mypy --strict`。不需要一夜之间覆盖所有代码——先对新增代码开启检查，再逐步提高覆盖率。一个类型安全的 Python 代码库的线上故障率，普遍低于无类型标注的同等规模项目。

**如果你是初学者**：先别急着学泛型和 Protocol。从给你的每一个函数加上 `参数: 类型` 和 `-> 返回值类型` 开始。熟悉之后再进阶到 `TypedDict` 和 `Callable`。类型系统是一个可以渐进采用的工具，不需要一步到位。
