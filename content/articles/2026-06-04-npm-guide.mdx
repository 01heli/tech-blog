## 一、从"拿到一个前端项目"说起

你刚入职一家公司，或者从 GitHub 上 clone 了一个开源项目。README 的第一行写着：

```bash
npm install
npm run dev
```

你照着敲了。终端里刷刷刷跑了一堆字，然后多出来一个叫 `node_modules` 的文件夹，里面有成百上千个文件夹。你心里犯嘀咕：这到底干了什么？为什么需要这么多东西？什么情况下该用 `npm install` 什么情况下用 `npm install -g`？`package.json` 里面那一堆 `^` 和 `~` 是什么意思？

这篇文章就是为这个时刻写的。我们不讲"包管理器的抽象定义"，而是从 npm 怎么来的、解决了什么问题、你每天会用到哪些命令、踩坑了怎么排查，一步步来。

## 二、没有 npm 的时代，前端是怎么分享代码的

### 2.1 2010 年以前：手动复制粘贴

在 npm 出现之前，JavaScript 开发者如果要复用别人的代码，有几种办法：

```
方法 1：去 jQuery 官网下载一个 .js 文件，丢到项目的 lib/ 目录里
方法 2：从 GitHub 上 clone 仓库，把需要的文件复制过来
方法 3：靠 CDN 引个 <script> 标签完事
```

这些办法有两个致命问题：

1. **版本管理靠人脑**。你用了 jQuery 1.4.2，三个月后 jQuery 出了 1.5.0 修了一个安全漏洞。除非你手动去官网看，否则你根本不知道。等项目上线一年后，已经没人记得当初用的是什么版本了。

2. **依赖的依赖靠运气**。你引了一个日期选择组件，它依赖了 moment.js。你必须手动确保 moment.js 也被引了，而且版本得是组件要求的那一版。万一两个组件依赖了同一个库的不同版本——比如 A 要 lodash 3.x，B 要 lodash 4.x——那就只能祈祷了。

### 2.2 2010 年 1 月 12 日

一个叫 Isaac Z. Schlueter 的开发者受够了。他是 Node.js 的早期核心贡献者，在参考了 PHP 的 PEAR 和 Perl 的 CPAN 之后，写了一个用 JavaScript 实现的包管理器，名字叫 **npm**。

npm 带来了三样东西，定义了此后十五年 JavaScript 世界的运作方式：

```
1. 一个中心仓库（Registry）——所有公开的包放到同一个地方，谁都能搜、谁都能装
2. 一个命令行工具（CLI）——敲一行命令就装好依赖，不需要手动下载
3. 一个描述文件（package.json）——记录项目用了哪些包、什么版本、怎么启动
```

> npm 的全称是什么？官方说法是 "npm is not an acronym"——一个递归缩写。这很 JavaScript 圈。

### 2.3 npm 到底解决了什么问题

```
没有 npm 的时代：                    有 npm 之后：

手动下载 jQuery                      npm install jquery
手动确保版本兼容                     package.json 里写 "^3.0.0"
手动处理依赖链                       npm 自动解析 lodash 3.x 和 4.x
换台机器要重新搞一遍                  npm install 一键复现
团队之间靠口头约定                    package-lock.json 锁死精确版本
```

简单说，npm 把 JavaScript 的代码复用从"手工作坊"变成了"流水线"。它是整个现代前端工程化——Webpack、Babel、React、Vue、TypeScript 工具链——能跑起来的地基。

## 三、第一个 npm 项目

### 3.1 确认 npm 装好了

npm 是 Node.js 的亲儿子，装 Node.js 的时候自动带上。打开终端：

```bash
node -v    # 比如 v20.11.0
npm -v     # 比如 10.2.4
```

如果没装，去 [nodejs.org](https://nodejs.org/) 下载 LTS 版本，一路下一步就行。

### 3.2 npm init：把目录变成项目

```bash
mkdir my-first-project
cd my-first-project
npm init -y    # -y 的意思是"全部用默认值，别问我了"
```

执行完后，目录里多了一个 `package.json`：

```json
{
  "name": "my-first-project",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}
```

这个文件就是项目的"身份证"。现在它是空的，但接下来所有操作都会写进这个文件。

### 3.3 package.json 各字段是什么意思

| 字段 | 干什么的 | 不写会怎样 |
|------|---------|-----------|
| `name` | 项目名，发布到 npm 时作为包名 | 只在本地用的话无所谓 |
| `version` | 当前版本号，用 SemVer 格式 | 不发布不用管 |
| `description` | 项目简介，npm 搜索时展示 | 不影响运行，但建议填 |
| `main` | 别人 `require('你的包')` 时默认加载哪个文件 | 如果是应用而非库，不关键 |
| `scripts` | 定义"快捷命令"，比如 `npm start` 实际执行什么 | 这是你每天都会碰的字段 |
| `dependencies` | 生产环境需要的包 | npm install 后自动生成 |
| `devDependencies` | 只在开发时需要的包（测试工具、打包器等） | 同上 |
| `private` | 设为 `true` 防止误发布到公开 registry | 公司内部项目务必设为 true |

### 3.4 装第一个包

```bash
npm install lodash
```

终端输出：

```
added 1 package, and audited 2 packages in 1s
```

再看 `package.json`，多了一行：

```json
{
  "dependencies": {
    "lodash": "^4.17.21"
  }
}
```

同时目录里多了 `node_modules/` 和 `package-lock.json`。三样东西的关系是：

```
package.json      → "我需要 lodash，大概是 4.x 版本就行"
package-lock.json → "当前实际装的是 lodash 4.17.21，依赖链如下..."
node_modules/     → lodash 的真实代码文件就放在这
```

`node_modules/` 不需要提交到 Git（加到 `.gitignore` 里）。但 `package-lock.json` 一定要提交——它保证同事和 CI 环境装出来的依赖树和你一模一样。

## 四、依赖管理：90% 的时间都在做的事

### 4.1 装什么

```bash
npm install react              # 装 react，写入 dependencies
npm install jest --save-dev    # 装 jest，写入 devDependencies（缩写 -D）
npm install typescript -g      # 全局装 TypeScript，任何目录都能用 tsc 命令
npm install lodash@4.0.0       # 指定安装 4.0.0 这个精确版本
npm install                     # 啥也不跟 = 读 package.json，把所有依赖装一遍
```

全局安装 vs 本地安装的判断标准很简单：**你要在命令行里直接敲这个工具的名字，就全局装；如果只是项目代码里 `import` 或 `require` 它，就本地装**。

```
全局装（-g）：typescript, nodemon, create-react-app, http-server
本地装：react, express, lodash, axios, jest, webpack
```

### 4.2 dependencies 和 devDependencies 的区别

假设你要做一个网站：

```
生产环境必须有的（dependencies）：       只在开发时需要（devDependencies）：
┌─────────────────────┐                 ┌─────────────────────┐
│ react               │                 │ jest（测试）         │
│ express             │                 │ webpack（打包）      │
│ axios               │                 │ eslint（代码检查）    │
│ lodash              │                 │ prettier（格式化）    │
└─────────────────────┘                 │ typescript（编译）    │
                                        └─────────────────────┘
```

当你部署到服务器时，可以跑：

```bash
npm install --production    # 只装 dependencies，跳过 devDependencies
```

这样做的好处是服务器上的 `node_modules` 更小，安装更快。

### 4.3 版本号那三个数字是什么意思

npm 用 **SemVer（语义化版本）**：`主版本.次版本.修订版`

```
lodash 4.17.21
       │  │  └── 修订版（patch）：修 bug，不改功能
       │  └───── 次版本（minor）：加新功能，但不破坏旧的
       └──────── 主版本（major）：不兼容的改动
```

`package.json` 里最常见的两个符号：

| 写法 | 含义 | 例子 |
|------|------|------|
| `^4.17.21` | 允许 4.x.x，但不允许 5.0.0 | `npm update` 可以升到 4.20.0，不会升到 5.0.0 |
| `~4.17.21` | 只允许 4.17.x | `npm update` 可以升到 4.17.30，不会升到 4.18.0 |
| `4.17.21` | 就这个版本，死锁 | 不自动升级 |

`^` 是 npm 的默认行为（`npm install` 时自动加上）。这个设计很巧妙：它信任库的作者遵守"minor 不改 API"的约定，在"自动获得 bug 修复"和"防止破坏性改动"之间取了平衡。但如果你追求绝对稳定（比如公司内部库），用精确版本更保险。

### 4.4 卸载和更新

```bash
npm uninstall lodash     # 删掉 lodash，同时从 package.json 里移除
npm update lodash        # 把 lodash 升到 ^ 范围内最新版
npm update               # 升级所有包
npm outdated             # 列出哪些包有新版本了
```

`npm outdated` 的输出长这样：

```
Package  Current  Wanted  Latest  Location
lodash    4.17.20  4.17.21  5.1.0  my-project
```

| 列 | 含义 |
|----|------|
| Current | 你现在实际装的是哪一版 |
| Wanted | 在你 `package.json` 的版本约束（比如 `^4.17.20`）下，最高能升到哪一版 |
| Latest | npm 仓库里最新的版本（可能是大版本，有破坏性改动） |

### 4.5 删除重装：万能重启大法

前端领域有一句名言："删了 `node_modules` 重装能解决 90% 的问题"。这不是玩笑——依赖树偶尔会因为各种原因（npm 版本不同、手动改过 `node_modules`、网络中断等）进入不一致状态。最直接的修复：

```bash
rm -rf node_modules package-lock.json
npm install
```

删掉整个 `node_modules` 和锁文件，让 npm 从零重新解析依赖树。这个过程通常不超过 30 秒。

## 五、scripts：把重复操作变成一行命令

### 5.1 为什么需要 scripts

假设你的项目有这些操作：

```bash
# 启动开发服务器
npx webpack serve --config webpack.dev.js --port 3000

# 跑测试
npx jest --coverage --verbose

# 构建生产版本
npx webpack --mode production && npx postcss dist/*.css --replace
```

每次都要敲这么长的命令，谁都受不了。`scripts` 字段就是来解决这个的：

```json
{
  "scripts": {
    "start": "webpack serve --config webpack.dev.js --port 3000",
    "test": "jest --coverage --verbose",
    "build": "webpack --mode production && postcss dist/*.css --replace"
  }
}
```

现在你只需要：

```bash
npm start       # 等同于 npm run start
npm test        # 等同于 npm run test
npm run build   # 自定义脚本需要加 run
```

注意：`start` 和 `test` 是 npm 内置的快捷指令（可以直接写 `npm start`），其他脚本必须写 `npm run <名字>`。

### 5.2 scripts 里不需要写 npx

在 `scripts` 里，npm 会自动把 `node_modules/.bin/` 加到 PATH 中。所以你可以直接写 `webpack` 而不是 `npx webpack` 或 `./node_modules/.bin/webpack`。这算是一个容易被忽略但很贴心的小设计。

### 5.3 生命周期钩子

npm 的 scripts 支持 `pre` 和 `post` 钩子：

```json
{
  "scripts": {
    "prebuild": "npm run lint",            // build 之前先检查代码
    "build": "webpack --mode production",
    "postbuild": "gzip -k dist/bundle.js"  // build 之后做 gzip 压缩
  }
}
```

运行 `npm run build` 时，`prebuild` → `build` → `postbuild` 会按顺序自动执行。这个机制很适合做"测试前启动数据库""部署前跑类型检查""打包后上传到 CDN"这类串联操作。

### 5.4 一个实际项目的 scripts 配置

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "lint": "eslint src/ --ext .js,.jsx,.ts,.tsx",
    "lint:fix": "npm run lint -- --fix",
    "test": "vitest run",
    "test:watch": "vitest",
    "type-check": "tsc --noEmit",
    "prepare": "husky install"
  }
}
```

观察几个要点：
- `dev` / `build` / `preview` 是 Vite 项目的标配，开发-构建-预览形成闭环
- `lint` 和 `lint:fix` 用冒号分隔"子命令"，这是一个很常见的命名约定
- `test` 跑一次，`test:watch` 持续监听文件变化自动重跑
- `prepare` 是 npm 的特殊钩子——`npm install` 之后自动执行，Husky 用它来装 Git hooks

## 六、npm install 和 npm ci 的区别

这是面试常考题，也是 CI/CD 环境里最容易搞混的点：

| 维度 | npm install | npm ci |
|------|------------|--------|
| 读取哪个文件 | 以 `package.json` 为主 | 严格按 `package-lock.json` |
| 如果锁文件和 package.json 不一致 | 自动更新锁文件 | **直接报错退出** |
| 会不会改锁文件 | 会 | 不会 |
| 速度 | 较慢 | 更快（跳过依赖解析） |
| 会先删 `node_modules` 吗 | 不会 | 会 |
| 适用场景 | 本地开发，加新依赖 | CI/CD，自动化部署 |

CI 环境必须用 `npm ci`。如果有人在 `package.json` 里加了新包但忘记提交锁文件，`npm ci` 会直接失败——这正是你想要的。如果用 `npm install`，它会静默更新锁文件，CI 构建出来的东西就和你本地不一样了。

## 七、npx：不用安装也能用

npm 5.2 开始自带了 `npx`。它的用途就一句话：**临时执行一个 npm 包，不永久安装它**。

```bash
# 用 create-react-app 创建一个新项目（执行完就"消失"，不留在全局）
npx create-react-app my-app

# 用 cowsay 印一句话（你肯定不想全局装这个东西）
npx cowsay "Hello, npm!"

# 查看某个包的版本（不用先 npm install）
npx depcheck    # 扫描项目里哪些依赖装了但没用到
```

什么情况下用 npx 而不是全局安装？

```
用 npx：偶尔用一次的工具（脚手架、代码生成器、一次性脚本）
用 npm install -g：每天都用的工具（typescript、nodemon、http-server）
```

## 八、安全：npm audit

2016 年发生了一件改变 npm 历史的事——**left-pad 事件**。一个只有 11 行代码的包，因为作者和 npm 公司发生争执被下架了，导致依赖它的 React、Babel 等数千个项目全部构建失败。

这件事之后，npm 加了 `npm audit` 命令：

```bash
npm audit          # 扫描所有依赖，列出已知的安全漏洞
npm audit fix      # 自动修复"能用兼容版本修复"的漏洞
npm audit fix --force   # 强制修复，可能引入破坏性改动（慎用）
```

输出示例：

```
# npm audit report

lodash  <4.17.21
Severity: high
Prototype Pollution - https://github.com/advisories/GHSA-xxx
fix available via `npm audit fix`
```

建议把 `npm audit` 加入 CI 流程，或者在每个月做一次依赖健康检查。GitHub 的 Dependabot 也能自动提 PR 来升级有漏洞的依赖。

## 九、npm vs pnpm vs Yarn：到底该选哪个

npm 不是唯一的选项。2016 年 Facebook 发布了 Yarn，2017 年开源社区推出了 pnpm，形成了三足鼎立的局面。到 2025 年，选型格局已经比较明朗了。

### 9.1 三者的核心差异

```
npm（2010）：
  node_modules 是扁平化的
  所有包都放在项目根目录的 node_modules 里
  问题：你可以 import 一个你没在 package.json 里声明的包（幽灵依赖）

pnpm（2017）：
  所有包存在全局的一个"内容寻址仓库"里（~/.pnpm-store）
  项目的 node_modules 里只有硬链接，不复制文件
  严格隔离：你在代码里只能 import 你声明过的包

Yarn（2016）：
  和 npm 思路类似，但更快、锁文件更严格
  Yarn v2 搞了 Plug'n'Play（不用 node_modules），但生态接受度不高
```

### 9.2 性能对比（2025 基准测试）

一个含 600+ 依赖的项目：

| 场景 | npm | Yarn | pnpm |
|------|-----|------|------|
| 冷启动安装（无缓存） | 30s | 22s | **7s** |
| CI 安装（有锁文件） | 12.5s | 5.4s | **1.3s** |
| 50 包的 monorepo 冷安装 | 127s | 98s | **38s** |
| 10 个项目磁盘占用 | 1.2GB | 980MB | **320MB** |

pnpm 为什么这么快？因为它不复制文件——全局仓库里只存一份 `lodash@4.17.21`，所有项目通过硬链接共享。npm 则是每个项目的 `node_modules` 里各存一份。

### 9.3 选型建议

```
新项目（个人或小团队）         → pnpm（快、省空间、幽灵依赖免疫）
大型 monorepo                  → pnpm（原生 workspace 支持最好）
需要最大兼容性、不折腾         → npm（哪都能跑，Node.js 自带）
团队已经用 Yarn v1 很久了      → 继续用，迁移有成本
CI 时间长、磁盘吃紧            → 换成 pnpm，效果立竿见影
```

迁移到 pnpm 的步骤非常简单：

```bash
npm install -g pnpm          # 全局装 pnpm
rm -rf node_modules package-lock.json   # 清理旧依赖
pnpm install                 # 自动生成 pnpm-lock.yaml
```

之后把 `pnpm-lock.yaml` 提交到 Git，原来的 `npm install` 换成 `pnpm install` 就行。命令几乎完全兼容（`pnpm add` = `npm install`，`pnpm run dev` = `npm run dev`）。

## 十、常见问题排查手册

### 10.1 "ERESOLVE unable to resolve dependency tree"

```
npm ERR! ERESOLVE unable to resolve dependency tree
npm ERR! Could not resolve dependency:
npm ERR! peer react@"^17.0.0" from some-package@2.0.0
```

这表示某个包的 peer dependency 和你的项目不兼容。比如你装了 React 18，但某个第三方组件要求 React 17。

**解决顺序**：
1. 看看报错里提到的是哪个包，去 npm 上查它的最新版本是否支持你的版本
2. 升级那个包：`npm install 那个包@latest`
3. 如果暂时没法升级：`npm install --legacy-peer-deps`（跳过 peer 检查，能跑但有风险）
4. 根本性解决：用 `npm install` 的 `--strict-peer-deps` 或升级到 pnpm（它的严格依赖模式天然避免这类问题）

### 10.2 "Cannot find module 'xxx'"

```
Error: Cannot find module 'express'
```

两种情况：

1. **你真的没装** → `npm install express`
2. **你装了但 node_modules 坏了** → `rm -rf node_modules && npm install`
3. **你全局装了但项目里没装** → 全局装不等于项目里能用。`require('express')` 必须从当前项目的 `node_modules` 里找。

### 10.3 package-lock.json 冲突

Git 合并时 `package-lock.json` 冲突是最常见的痛苦。

```
<<<<<<< HEAD
    "lodash": "4.17.20"
=======
    "lodash": "4.17.21"
>>>>>>> feature-branch
```

**正确做法**：不要手动编辑锁文件的冲突内容——它是一个自动生成的文件，里面的嵌套 JSON 你手动改错一个字符就完了。

```bash
# 接受某一方的 package.json（这才是源码），删掉锁文件，重新生成
git checkout --theirs package.json     # 或用 --ours
rm package-lock.json node_modules -rf
npm install
git add package-lock.json
```

### 10.4 node_modules 太大怎么办

```bash
# 看看谁占了最多空间
npx du -sh node_modules/* | sort -rh | head -10

# 清理没用的包
npx depcheck    # 列出装了但代码里没引用的包

# 用 pnpm 替代 npm（节省 60-91% 磁盘）
```

## 十二、总结与建议

npm 不是什么高深的技术，它就是一个"代码的物流系统"——管进货（install）、管库存（node_modules）、管账本（package.json 和 lock 文件）、管发货（publish）。理解了这四个角色，你就理解了 npm。

### 对于前端新手

1. **先理解 package.json 的三个核心字段**：`dependencies`（运行要用的）、`devDependencies`（开发要用的）、`scripts`（快捷命令）。这三个字段覆盖了 80% 的日常操作。
2. **不要怕 node_modules**。它很大、很乱、看起来吓人，但它只是"别人写的代码存在你电脑上的副本"。删了随时可以重装。
3. **遇到报错先读报错信息**。npm 的报错通常写得很清楚——缺了哪个包、哪个版本不对、哪个文件找不到。先看报错再 Google，能解决一半以上的问题。

### 对于后端转前端的开发者

1. npm 里的 `package.json` 相当于 Python 的 `requirements.txt` + `setup.py` 或 Java 的 `pom.xml` / `build.gradle`。概念是通的，只是写法不同。
2. `npm ci` = `pip install -r requirements.txt --require-hashes`，都是"严格按锁文件装"。
3. 全局安装（`-g`）要克制。Python 有虚拟环境、Java 有 Maven 的本地仓库，npm 的全局安装相当于把东西扔到 `/usr/local/bin`——各项目之间的版本隔离就没了。

### 对于团队负责人

1. **锁文件必须提交到 Git**。没有任何例外。这是保证"你本地跑得通、CI 也跑得通"的唯一手段。
2. **考虑从 npm 迁移到 pnpm**。在磁盘占用（省 60-91%）和安装速度（快 3-5 倍）上的收益是直接的，命令兼容性很好，迁移成本低。
3. **把 `npm audit` 加入 CI 流程**。或者在 GitHub 上开启 Dependabot，让机器自动帮你盯着依赖安全。人力盯不住成百上千个依赖的。
