## 你每天都在用 TCP 和 UDP，只是你不知道

打开这个网页的那一刻，你的浏览器至少建立了十几个 TCP 连接。微信收到一条消息——TCP。刷抖音看到一个直播——UDP。在《王者荣耀》里丢出一个技能——UDP。

**传输层的两个协议，撑起了整个互联网的应用生态。**

但它们到底有什么区别？为什么有的应用选 TCP，有的选 UDP？"TCP 可靠、UDP 快"这句人人会说的话背后，到底藏着多少精妙的设计？

这篇文章从零开始，把 TCP 和 UDP 的原理、机制、使用场景、调试方法讲透。不需要任何先验知识。

---

## 一、前置知识：数据是怎么在网络中传输的

### 1.1 五层模型（简化版）

在你刷网页的时候，数据经过了一条漫长的流水线：

```
┌──────────────────────────────────────┐
│  应用层    HTTP / DNS / WebSocket     │  ← "我要访问 baidu.com"
├──────────────────────────────────────┤
│  传输层    TCP / UDP                  │  ← 我们是这一层的主角
├──────────────────────────────────────┤
│  网络层    IP                         │  ← 负责"去哪"（IP 地址）
├──────────────────────────────────────┤
│  链路层    Ethernet / WiFi            │  ← 负责"下一跳给谁"（MAC 地址）
├──────────────────────────────────────┤
│  物理层    网线 / 光纤 / 无线电       │  ← 0101 的电信号
└──────────────────────────────────────┘
```

**传输层的职责**：把应用层的数据切块、编号、送到对端、按序组装。至于"走哪条路到达"是 IP 的事——传输层只管"发出去"和"确认收到"。

### 1.2 为什么不直接用 IP？

IP 层只负责"尽最大努力把包送到"，不保证任何事情：

- 包可能丢了 → IP 不管
- 包可能乱序到达 → IP 不管
- 包可能重复 → IP 不管
- 发送方可能发太快把接收方淹死 → IP 不管

**传输层就是在 IP 的"不可靠"之上，提供应用需要的保证。** 而 TCP 和 UDP 选择了两种完全不同的哲学来实现这件事。

## 二、TCP：给互联网上保险

### 2.1 一句话理解 TCP

> TCP 像寄挂号信：填单、签字、可查、可追溯、保证送到。

TCP（Transmission Control Protocol，传输控制协议）的设计目标就是**可靠**。为此它付出了大量"开销"——建立连接、维护状态、确认应答、重传丢失、控制速率。

### 2.2 三次握手：为什么是三次？

在发送任何数据之前，TCP 必须先建立连接。这个过程叫**三次握手**（Three-Way Handshake）：

```
  客户端                                    服务器
    │                                        │
    │  ──── SYN (seq=x) ────────────────▶    │  ① "在吗？这是我的初始序号 x"
    │                                        │
    │  ◀─── SYN+ACK (seq=y, ack=x+1) ────    │  ② "在，我的初始序号是 y，收到你的 x 了"
    │                                        │
    │  ──── ACK (ack=y+1) ──────────────▶    │  ③ "收到，那我们开始吧"
    │                                        │
  ESTABLISHED                          ESTABLISHED
```

**为什么不是两次？** 为了防止已失效的连接请求突然到达服务器。

想象这个场景：客户端发了一个 SYN，但网络拥堵，这个 SYN 在路上卡了很久。客户端以为丢了，又发了一个新的 SYN，成功建立连接、传完数据、关闭连接。这时，第一个卡了很久的 SYN 终于到达服务器——服务器以为客户端又想建一个新连接，回复 SYN+ACK。如果只有两次握手，服务器就傻傻地以为连接已建立，分配资源干等着。三次握手中，客户端收到这个"迟到"的 SYN+ACK 后不会回复 ACK，服务器等不到第三个包就知道这个请求是无效的。

**为什么不是四次？** 其实在三次握手之后，连接已经可以开始传输数据了。再多一次纯属浪费。

### 2.3 四次挥手：优雅地分手

关闭连接比建立连接多一步，因为 TCP 是全双工的——双方都能同时收发数据：

```
  客户端                                    服务器
    │                                        │
    │  ──── FIN ────────────────────────▶    │  ① "我说完了，准备关"
    │                                        │
    │  ◀─── ACK ────────────────────────     │  ② "知道了"（但服务器可能还有数据要发）
    │                                        │
    │  ◀─── FIN ────────────────────────     │  ③ "我也说完了，准备关"
    │                                        │
    │  ──── ACK ────────────────────────▶    │  ④ "知道了，拜拜"
    │                                        │
    │  ⏳ TIME_WAIT (2MSL ≈ 1-4 分钟)        │
    └────────────────────────────────────────┘
```

**TIME_WAIT 为什么等 2MSL？**

TCP 连接关闭后，客户端进入 TIME_WAIT 状态，等 **2 倍 MSL**（Maximum Segment Lifetime，最大报文生存时间，通常是 30-120 秒）。原因有两个：

1. **确保最后一个 ACK 能到达服务器**。如果这个 ACK 丢了，服务器会重发 FIN，客户端需要在这个时间内能重新回复 ACK。
2. **让旧连接的所有包在网络中彻底消失**。防止同一对 IP+端口的新连接收到旧连接的"幽灵包"。

> 💡 服务器上 TIME_WAIT 大量的连接通常意味着短连接过多，可以考虑连接池、长连接，或调整内核参数。

### 2.4 可靠性引擎：四大支柱

TCP 的可靠性建立在四个机制之上：

#### 支柱一：分段与序号

应用层的数据（比如一个 100KB 的 HTML 文件）被 TCP 切成一段一段的**报文段**（Segment），每个段有一个 **32 位的序号**（Sequence Number）。

```
一个大文件被切成 N 个段：
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ 8 │   ← 每个段都有唯一序号
└───┴───┴───┴───┴───┴───┴───┴───┘
```

接收方按序号重新组装。即使段 3 比段 2 先到了也没关系——看序号就知道谁该排前面。

#### 支柱二：确认应答（ACK）

每收到一个段，接收方就回一个 ACK（Acknowledgment），告诉发送方"序号 N 之前的数据我都收到了"。

```
发送方                              接收方
  │ ───── seq=1: "Hel" ─────▶        │
  │ ◀──── ack=4 ────────────         │  "前 4 个字节收到了"
  │ ───── seq=4: "lo W" ─────▶        │
  │ ◀──── ack=8 ────────────         │
```

#### 支柱三：超时重传

如果发送方在指定时间内没收到 ACK，就认为这个段丢了，重新发送。

```
发送方                              接收方
  │ ───── seq=100 ───────────▶        │  (这个包丢了)
  │         ... 等了好久 ...          │
  │ ⏰ 超时!                          │
  │ ───── seq=100 (重传) ──────▶        │  ✅ 收到!
  │ ◀──── ack=200 ────────────         │
```

**如何设定超时时间？** TCP 动态计算 RTO（Retransmission Timeout）：
- 持续测量每个包的 RTT（Round Trip Time，往返时间）
- 取平滑值：`SRTT = α × SRTT + (1-α) × 最新RTT`
- RTO = SRTT + 4 × RTT 的偏差

这样当网络抖动变大时，超时阈值自动放宽。

#### 支柱四：快速重传（Fast Retransmit）

超时重传的问题是"太慢"——可能要等几百毫秒到几秒。

**快速重传**解决了这个问题：如果发送方**连续收到 3 个相同的 ACK**（说明有包丢了但后面的包到了），不等超时，直接重传那个丢失的包。

```
发送方                              接收方
  │ ───── seq=1 ──────────────▶       │  ✅
  │ ───── seq=2 ──────────────▶       │  ❌ (丢了)
  │ ───── seq=3 ──────────────▶       │  ✅  ack=2  (还差 2)
  │ ───── seq=4 ──────────────▶       │  ✅  ack=2  (还差 2)
  │ ───── seq=5 ──────────────▶       │  ✅  ack=2  (还差 2)  ← 第 3 个重复 ACK!
  │                                    │
  │ ⚡ 收到 3 个重复 ACK，立即重传 seq=2 │
  │ ───── seq=2 (快速重传) ──────▶      │  ✅  ack=6  (全齐了!)
```

## 三、滑动窗口：TCP 的吞吐量引擎

### 3.1 为什么需要窗口？

如果每发一个包都要等 ACK 才能发下一个，那就是**停等协议**（Stop-and-Wait），效率极低：

```
停等协议：
发送方: 发1 → 等ACK → 发2 → 等ACK → 发3 → 等ACK ...
         |---- RTT ----|     |---- RTT ----|
```

假设 RTT = 30ms，每个包 1KB，停等协议的吞吐量只有 `1KB / 30ms ≈ 33KB/s`，连拨号上网都不如。

**滑动窗口**的方案是：不等 ACK，一次性发送多个包。

```
滑动窗口：
发送方: 发1 ─┐
        发2  ├── 一个窗口内的包同时发出，不等逐包 ACK
        发3 ─┘
         ◀── ack=4 ──  (一个 ACK 确认前面所有包)
        发4 ─┐
        发5  ├── 窗口往前滑动
        发6 ─┘
```

```
窗口示意图：
[已确认] [已发送未确认│可发送未发送] [还不能发送]
         ◀──── 窗口大小 ────▶
```

**窗口大小 = 不需要等 ACK、可以直接发出去的最大数据量**。每收到一个 ACK，窗口就往前"滑动"，腾出空间发送新的包。

### 3.2 发送窗口由谁决定？

发送窗口 = **min(拥塞窗口, 接收方通告窗口)**

两个限制，缺一不可：
- **接收方限制（rwnd）**：接收方在 ACK 里告诉发送方"我的缓冲区还剩这么多"
- **网络限制（cwnd）**：发送方自己探测出来的"网络能承受多少"

### 3.3 流量控制：接收方说了算

接收方的缓冲区是有限的。如果发送方不管不顾拼命发，接收方的缓冲区满了，后续的包只能丢弃——这就白费了前面的传输。

所以接收方在每个 ACK 里附带一个 **窗口大小字段**，告诉发送方：

> "我的缓冲区还剩 X 字节，你最多发这么多。"

如果缓冲区满了，窗口大小 = 0，发送方暂停。发送方会定期发**窗口探测包**（不含数据）询问"你又有空间了吗？"

### 3.4 一个直观类比

想象一个快递员给一家小商店送货：

- **停等协议**：送一箱 → 等老板打电话确认收到 → 送下一箱。一天送 100 箱。
- **滑动窗口（批量发送）**：一次送 10 箱 → 老板确认"前 10 箱收到了" → 再送 10 箱。一天送 1000 箱。
- **流量控制**：老板说"我仓库只剩 5 箱的空间了" → 快递员只送 5 箱，不把仓库撑爆。

## 四、拥塞控制：TCP 的智能调速器

### 4.1 流量控制 ≠ 拥塞控制

- **流量控制**：接收方说"我受不了了，慢点" → 它是**端到端**的
- **拥塞控制**：网络说"这条路堵了，慢点" → 它是**全局**的

即收发两端之间还有无数路由器、交换机。中间任何一个节点处理不过来，就会发生拥塞——包排队、延迟剧增、大量丢包。

**拥塞控制就是 TCP 感知网络拥堵并自动降速的能力。**

### 4.2 传统算法：CUBIC（基于丢包）

Linux 内核默认的拥塞控制算法。核心思路很简单：**没丢包就加速，丢包了就减速。**

```
拥塞窗口大小
     ↑
     │       /\    /\           ← 锯齿形
     │      /  \  /  \            不断试探上限
     │     /    \/    \
     │    /            \
     │   /              \___
     │____________________________→ 时间
      慢启动   拥塞避免   丢包减半
```

**四个阶段：**

| 阶段 | 窗口增长方式 | 说明 |
|------|-------------|------|
| **慢启动** | 指数增长（每 RTT 翻倍） | 初始窗口很小，快速探测带宽 |
| **拥塞避免** | 线性增长（每 RTT +1） | 接近上限后谨慎试探 |
| **快速重传** | 收到 3 个重复 ACK 立即重传 | 不等超时 |
| **快速恢复** | 窗口减半，线性恢复 | 轻微拥塞，不回到慢启动 |

CUBIC 对 Reno 的改进：用**三次函数**代替线性增长，在大带宽场景下更快地恢复到丢包前的速率。

### 4.3 CUBIC 的问题：Bufferbloat

CUBIC 依赖丢包作为"网络满了"的信号。但丢包发生在什么时候？发生在瓶颈路由器的**缓冲区被填满**的时候。

这带来了一个恶性循环：
```
发送方不知道网络快满了 → 继续加速 → 填满缓冲区 → 排队延迟飙升 → 终于丢包 → 才减速
```

**缓冲区越大，排队延迟越高**——这就是 Bufferbloat（缓冲区膨胀）问题。当丢包率仅为 0.1% 时，CUBIC 的吞吐量可能降到原来的 1/10。

### 4.4 BBR：Google 的革命性算法

BBR（Bottleneck Bandwidth and Round-trip propagation time）不再把丢包当信号，而是**直接测量网络的两个核心参数**：

| 参数 | 含义 | 如何测量 |
|------|------|----------|
| **BtlBw**（瓶颈带宽） | 路径上最窄处的带宽 | 10 个 RTT 内的最大交付速率 |
| **RTprop**（物理往返延迟） | 链路本身的最小 RTT（不含排队时间） | 10 秒内的最小 RTT 值 |

然后计算 **BDP（带宽时延积）**：

```
BDP = BtlBw × RTprop
```

**BDP 就是"飞行中的数据量"的最佳值**——刚好用满带宽，又不产生排队。

```
吞吐量
  ↑
  │              ★ BBR 工作点          ← 最大吞吐 + 最低延迟
  │            /          \
  │          /              \
  │        /                  \
  │      /                      \
  └────────────────────────────────────→ 飞行中的数据量
     ↑ 延迟低             延迟高 ↑
     (队列空)              (队列满 → 丢包)
```

**BBR 的工作方式是周期性探测**：

```
阶段:  [加速探测] → [排空队列] → [平稳发送] →
增益:    1.25          0.75           1.0
```

- **1.25 倍**：多发送 25% 探测是否有更多带宽
- **0.75 倍**：如果造成了排队，减少发送量排空队列
- **1.0 倍**：按测得的真实带宽平稳发送

### 4.5 CUBIC vs BBR 对比

| 维度 | CUBIC | BBR |
|------|-------|-----|
| **依赖信号** | 丢包（被动） | 带宽+RTT（主动测量） |
| **缓冲区** | 填满 → 丢包 → 减速 | 不填满 → 低延迟 |
| **对丢包的容忍** | 极低，0.1% 丢包吞吐量暴跌 | 极高，5% 丢包才开始明显下降 |
| **公平性** | 较好 | 可能挤占 CUBIC 流量的带宽 |
| **适用场景** | 通用 | 长肥网络、视频/CDN、跨境传输 |
| **WiFi/抖动** | 尚可 | RTT 测量不准，表现不佳 |

> 💡 BBRv3 是目前的最新版本，重点改进了与 CUBIC 共存的公平性和 WiFi 环境下的表现。

## 五、UDP：不穿盔甲，所以跑得快

### 5.1 一句话理解 UDP

> UDP 像寄明信片：写上地址就扔邮筒，不挂号、不追踪、丢了拉倒。

UDP（User Datagram Protocol，用户数据报协议）的设计哲学是**极简**。它不建立连接、不维护状态、不保证送达、不保证顺序。

### 5.2 UDP 的包头：只有 8 字节

```
 0      7 8     15 16    23 24    31
┌─────────┬─────────┬─────────┬─────────┐
│  源端口  │ 目的端口 │  长度   │  校验和  │
│ (2字节) │ (2字节) │ (2字节) │ (2字节) │
├─────────┴─────────┴─────────┴─────────┤
│              数据 (可变长)              │
└──────────────────────────────────────┘
```

就这。对比 TCP 的 20+ 字节包头，UDP 的包头只有 **4 个字段、8 个字节**。而且校验和还是**可选的**——可以设为 0 表示不校验。

没有序号，没有 ACK 号，没有窗口，没有标志位，没有任何复杂的机制。

### 5.3 UDP 的"不"字清单

| TCP 做的事 | UDP |
|------------|-----|
| 建立连接（三次握手） | ❌ 不建 |
| 确认应答（ACK） | ❌ 不应 |
| 超时重传 | ❌ 不重 |
| 保序（序号重组） | ❌ 不排 |
| 流量控制（窗口） | ❌ 不控 |
| 拥塞控制 | ❌ 不管 |
| 连接状态（LISTEN/ESTABLISHED...） | ❌ 无状态 |

UDP 的"不可靠"不是 bug，是**设计取舍**。它把所有这些事情都交给**应用层**去处理——如果应用需要的話。

### 5.4 UDP 为什么快？

1. **无握手延迟**：数据直接发，零 RTT 开销
2. **无状态维护**：内核不需要维护连接表，省内存
3. **无 ACK 等待**：发完就忘，不需要等对端确认
4. **无流控阻塞**：发送速率完全由应用决定

用一个具体的例子：

```
DNS 查询如果用 TCP：             DNS 查询用 UDP：
  三次握手 (1.5 RTT)              发送请求 (0 RTT)
  + 发送请求 (1 RTT)              + 接收响应 (1 RTT)
  + 四次挥手 (2 RTT)               ────────────────
  ────────────────                 总计: ~30ms
  总计: ~135ms
```

DNS 本身就有"超时重试"机制，所以根本不需要 TCP 在传输层再做一遍重传。

## 六、对比总结

| 维度 | TCP | UDP |
|------|-----|-----|
| **中文名** | 传输控制协议 | 用户数据报协议 |
| **连接方式** | 面向连接（三次握手） | 无连接（直接发） |
| **可靠性** | 保证送达、保序、不重复 | 不保证任何事 |
| **传输速度** | 较慢（握手、ACK、流控开销） | 快（最小开销） |
| **包头大小** | 20~60 字节 | 8 字节 |
| **流控 / 拥塞控制** | 内置（滑动窗口 + CUBIC/BBR） | 无（应用层自己实现） |
| **适用场景** | 网页、邮件、文件传输、数据库 | 直播、语音、游戏、DNS |
| **广播 / 多播** | 不支持 | 支持 |
| **双工方式** | 全双工 | 全双工 |
| **状态** | 有状态（LISTEN/ESTABLISHED/...） | 无状态 |

### 一句话选型指南

> 数据不能错 → TCP。延迟不能高 → UDP。

## 七、什么时候用哪个？真实世界的协议选择

### 7.1 TCP 的典型场景

| 协议/应用 | 为什么必须用 TCP |
|-----------|----------------|
| **HTTP/1.1, HTTP/2** | 网页必须完整加载，CSS/JS/图片缺一不可 |
| **SMTP / IMAP / POP3** | 邮件内容一个字都不能丢 |
| **FTP / SFTP** | 文件传输零容忍损坏 |
| **SSH** | 每个按键都必须可靠送达 |
| **MySQL / PostgreSQL** | 数据库查询必须可靠 |
| **HTTPS (TLS)** | 加密通道需要可靠的字节流 |

### 7.2 UDP 的典型场景

| 协议/应用 | 为什么用 UDP |
|-----------|-------------|
| **DNS** | 查询 < 512 字节，一包一问一答，超时重试就够了 |
| **DHCP** | 设备启动时获取 IP，此时还没有 TCP 栈需要的完整网络配置 |
| **VoIP（语音通话）** | 丢掉 50ms 的声音比等重传好——重传回来时那句话早过了 |
| **视频直播（RTMP 推流后）** | 延迟比清晰度更重要，掉几帧看不出 |
| **在线游戏** | 你的位置数据每 16ms 发一次，上一帧丢了新的马上就到 |
| **NTP（时间同步）** | 对时请求极简，重传反而导致时间不准 |
| **RIP / OSPF 等路由协议** | 周期性广播路由信息，不差偶尔丢一个包 |

### 7.3 边界模糊地带

**DNS 大响应**：如果响应超过 512 字节，DNS 会 fallback 到 TCP（端口 53 同时监听 TCP 和 UDP）。

**QUIC / HTTP/3**：Google 把可靠性建在 UDP 之上，兼顾速度与可靠——下一节详聊。

## 八、QUIC：用 UDP 重新发明 TCP

### 8.1 TCP 的阿克琉斯之踵

TCP 有一个设计之初没考虑到的问题：**队头阻塞**（Head-of-Line Blocking）。

HTTP/2 在一条 TCP 连接上复用多个请求流：

```
TCP 连接
├── 流 1: index.html  (丢了一个包 → 整条 TCP 连接卡住!)
├── 流 2: style.css   (被流 1 阻塞)
├── 流 3: app.js      (被流 1 阻塞)
└── 流 4: logo.png    (被流 1 阻塞)
```

因为 TCP 严格保序："序号 N 没到，N+1 及之后的都不能交给应用层"。流 1 丢了一个包，**所有流全部阻塞**，即使它们的包已经到了。

### 8.2 QUIC 的解法

QUIC 在 UDP 之上实现了独立的流：

```
UDP 连接
├── 流 1: index.html  (丢包 → 只影响流 1)
├── 流 2: style.css   (不受影响，继续)
├── 流 3: app.js      (不受影响，继续)
└── 流 4: logo.png    (不受影响，继续)
```

QUIC 的架构：

```
HTTP/3
  ↕
QUIC (用户空间：多流复用、可靠性、加密、拥塞控制)
  ↕
UDP  (内核空间：纯数据报传输)
  ↕
IP
```

### 8.3 QUIC 的三大杀招

**杀招一：0-RTT 连接建立**

首次连接：1-RTT（TLS 1.3 握手和 QUIC 握手合并）
再次连接：0-RTT（直接用缓存的密钥加密数据发出）

```
TCP + TLS 1.3 (首次):        QUIC 首次:           QUIC 再次 (0-RTT):
  1 RTT: TCP 握手              1 RTT: 密钥协商       0 RTT: 直接发数据!
  +                              +                     +
  1 RTT: TLS 握手              
  ────────────                 ────────────          ────────────
  总计 2 RTT                   总计 1 RTT            总计 0 RTT
```

**杀招二：连接迁移**

TCP 用四元组（源 IP + 源端口 + 目的 IP + 目的端口）标识一条连接。WiFi 切 4G → IP 变了 → TCP 连接断。

QUIC 用 **Connection ID**（一个随机生成的 64 位数字）标识连接。IP 变了 → Connection ID 不变 → 连接无缝继续。

```
WiFi (10.0.0.5) → 切到 4G (100.200.50.1)
TCP:  ❌ 连接断开，需要重新握手
QUIC: ✅ Connection ID 不变，继续传输
```

**杀招三：用户空间实现**

TCP 实现在内核里，升级拥塞控制算法需要改内核（甚至重启服务器）。QUIC 跑在用户空间，升级只需要更新库文件。

### 8.4 QUIC 意味着什么

QUIC 证明了"UDP 加应用层可靠性"这条路是可行的——事实上，比 TCP 更好。它不是要取代所有 TCP 的使用场景，但它模糊了 TCP 和 UDP 之间的"可靠 vs 快速"二分法：

> **现在你可以在 UDP 上获得 TCP 的可靠性，还不受 TCP 队头阻塞的限制。**

## 九、Socket 编程：亲手操纵 TCP 和 UDP

理论讲得差不多了，来看代码。

### 9.1 TCP Socket 的编程模式

TCP 的服务端和客户端模式截然不同：

```
服务端                              客户端
  │                                  │
  socket()                           socket()
  ↓                                  ↓
  bind()  ← 绑定端口                 (无需 bind，系统自动分配)
  ↓
  listen() ← 开始监听
  ↓
  accept() ← 阻塞等待连接 ─────────→ connect() ← 发起三次握手
  ↓                                  ↓
  │ ←──────── 连接建立 ──────────→  │
  ↓                                  ↓
  recv() / send()                send() / recv()
  ↓                                  ↓
  close()                           close()
```

**Python 示例——TCP 服务端（最简单的 echo server）：**

```python
import socket

# 1. 创建 socket
server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # SOCK_STREAM = TCP
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

# 2. 绑定地址和端口
server.bind(('0.0.0.0', 8888))

# 3. 开始监听
server.listen(5)
print('TCP Echo Server 监听在 8888 端口...')

while True:
    # 4. 接受连接（阻塞直到有客户端连进来）
    client, addr = server.accept()
    print(f'客户端 {addr} 已连接')

    # 5. 收发数据
    data = client.recv(1024)       # 最多收 1024 字节
    print(f'收到: {data.decode()}')

    client.sendall(data)            # 原样返回
    client.close()
```

**Python 示例——TCP 客户端：**

```python
import socket

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(('127.0.0.1', 8888))    # 发起三次握手
client.sendall(b'Hello, TCP!')         # 发送数据
response = client.recv(1024)           # 接收响应
print(f'收到回复: {response.decode()}')
client.close()
```

### 9.2 UDP Socket 的编程模式

UDP 没有"连接"的概念——服务端和客户端的代码几乎一样：

```
UDP 服务端                           UDP 客户端
  │                                   │
  socket()                           socket()
  ↓                                  ↓
  bind()  ← 绑定端口                (无需 bind)
  ↓                                  ↓
  recvfrom() ← 收 + 知来处          sendto() ← 发 + 指去处
  ↓                                  ↓
  sendto()  ← 回复                  recvfrom() ← 收回复
  ↓                                  ↓
  close()                           close()
```

**Python 示例——UDP 服务端：**

```python
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)  # SOCK_DGRAM = UDP
server.bind(('0.0.0.0', 9999))
print('UDP Server 监听在 9999 端口...')

while True:
    data, addr = server.recvfrom(1024)  # 收数据 + 得知发送方地址
    print(f'收到来自 {addr} 的消息: {data.decode()}')
    server.sendto(data, addr)            # 原样返回
```

**Python 示例——UDP 客户端：**

```python
import socket

client = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
client.sendto(b'Hello, UDP!', ('127.0.0.1', 9999))   # 直接发送，无连接
data, addr = client.recvfrom(1024)                    # 接收回复
print(f'收到来自 {addr} 的回复: {data.decode()}')
client.close()
```

### 9.3 TCP vs UDP 编程的关键区别

| | TCP Socket | UDP Socket |
|---|-----------|-----------|
| **类型** | `SOCK_STREAM` | `SOCK_DGRAM` |
| **连接** | 必须先 `connect` / `accept` | 不需要，直接 `sendto` |
| **收发函数** | `send` / `recv`（字节流） | `sendto` / `recvfrom`（数据报） |
| **对方地址** | 连接后不需要每次指定 | 每次收发都要指定 |
| **数据边界** | 无边界（字节流，可能粘包） | 有边界（每个数据报独立） |
| **可靠性** | 保证送达、保序 | 不保证 |

> ⚠️ **TCP 粘包问题**：TCP 是字节流，多次 `send` 的数据可能在接收方被合并为一次 `recv`，也可能一次 `send` 被拆成多次 `recv`。你需要自己设计**消息边界**——比如用长度前缀、分隔符，或定长消息。

## 十、实战调试：看清你的网络连接

### 10.1 `ss`：现代版的 netstat

`ss`（Socket Statistics）直接读取内核的 socket 数据结构，比老旧的 `netstat` 快得多。

```bash
# 查看所有 TCP 连接
ss -tan
# 输出示例：
# State      Recv-Q Send-Q Local Address:Port   Peer Address:Port
# LISTEN     0      128    0.0.0.0:22           0.0.0.0:*
# ESTAB      0      0      192.168.1.5:45678    142.250.80.1:443
# TIME-WAIT  0      0      192.168.1.5:45680    10.0.0.3:8080

# 查看所有监听端口（TCP + UDP）
ss -tuln

# 查看带进程名的连接（需要 sudo）
sudo ss -tnp

# 只看 LISTEN 状态
ss -tln

# 查看 UDP 连接
ss -uan

# 统计各状态的连接数
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn
```

### 10.2 关键字段解读

| 字段 | 含义 | 值得关注的情况 |
|------|------|---------------|
| **Recv-Q** | 已收到但应用还没读的字节数 | 非零 → 应用读得太慢 |
| **Send-Q** | 已发出但未被对端 ACK 的字节数 | 非零 → 网络拥塞或对端处理慢 |
| **State** | 连接状态 | 见下方 |
| **Local Address:Port** | 本地 IP:端口 | |
| **Peer Address:Port** | 对端 IP:端口 | |

### 10.3 常见的 TCP 状态诊断

```bash
# 查看有多少 TIME_WAIT 连接（太多说明短连接过多）
ss -tan state time-wait | wc -l

# 查看有多少 SYN_RECV（被洪水攻击的迹象）
ss -tan state syn-recv | wc -l

# 按对端 IP 统计连接数（找到异常 IP）
ss -tan state established | awk 'NR>1{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head -10
```

### 10.4 实时监控

```bash
# 每秒刷新连接数
watch -n 1 'ss -tan | wc -l'

# 监控 TCP 重传统计
watch -n 2 'netstat -s | grep retransmitted'

# 持续追踪特定端口
watch -n 1 'ss -tnp state established "sport = :443 or dport = :443"'
```

### 10.5 `tcpdump`：抓包看看 TCP 到底在干什么

```bash
# 抓取本机 8888 端口的 TCP 流量
sudo tcpdump -i lo port 8888 -A

# 抓取 TCP 三次握手（只抓 SYN 包）
sudo tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn) != 0'

# 抓取并保存到文件（后续用 Wireshark 分析）
sudo tcpdump -i eth0 port 443 -w capture.pcap
```

### 10.6 几个实用的 Wireshark 过滤表达式

```
# 只看某个 IP 的 TCP 流量
ip.addr == 192.168.1.100 && tcp

# 只看 TCP 重传包
tcp.analysis.retransmission

# 只看 TCP 三次握手
tcp.flags.syn == 1 && tcp.flags.ack == 0

# 只看 UDP 包
udp

# 分析 TCP 流
tcp.stream eq 0
```

## 十一、内核参数调优速查

### 11.1 TCP 常用内核参数

```bash
# 查看当前参数
sysctl net.ipv4.tcp_congestion_control   # 拥塞控制算法
sysctl net.ipv4.tcp_rmem                 # TCP 读缓冲区
sysctl net.ipv4.tcp_wmem                 # TCP 写缓冲区
sysctl net.ipv4.tcp_tw_reuse             # TIME_WAIT 复用
```

```bash
# /etc/sysctl.conf 常用优化项

# 启用 TCP Fast Open（客户端和服务端）
net.ipv4.tcp_fastopen = 3

# 允许 TIME_WAIT 状态的 socket 被复用
net.ipv4.tcp_tw_reuse = 1

# 增大半连接队列（防范 SYN Flood 的同时不影响正常连接）
net.ipv4.tcp_max_syn_backlog = 8192

# TCP 缓冲区：最小值 / 默认值 / 最大值（字节）
net.ipv4.tcp_rmem = 4096 131072 6291456
net.ipv4.tcp_wmem = 4096 65536 4194304

# 启用 BBR 拥塞控制（需要内核 >= 4.9）
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
```

### 11.2 验证 BBR 是否生效

```bash
# 查看当前使用的拥塞控制算法
sysctl net.ipv4.tcp_congestion_control
# 输出: net.ipv4.tcp_congestion_control = bbr  ✅

# 查看 BBR 是否真的有在管理连接
ss -tin | grep bbr
```

## 十二、进阶话题

### 12.1 DNS：为什么要同时监听 TCP 和 UDP 端口 53？

- **UDP（默认）**：普通查询和响应，< 512 字节（EDNS 可扩展到 4096 字节）
- **TCP（fallback）**：响应超过 UDP 包上限时（TC 标志位被设置），客户端用 TCP 重新查询
- **区域传输**（AXFR）：主从 DNS 服务器之间同步整个区域文件，数据量大，必须用 TCP

### 12.2 WebRTC：UDP 上的实时通信栈

WebRTC 用了一系列基于 UDP 的协议：

```
网页视频通话的协议栈:
┌──────────────────────────┐
│  DataChannel   音视频     │
│    ↕           ↕         │
│ SCTP over    SRTP (RTP)  │
│   DTLS         ↕         │
│    ↕       DTLS-UDP      │
│    └─────────┬───────────┘
│              ↕           │
│       UDP (NAT 穿越)     │
│              ↕           │
│     ICE (STUN/TURN)      │
└──────────────────────────┘
```

WebRTC 的核心挑战是 NAT 穿越——两个都在路由器后面的浏览器如何直接通信？ICE 协议使用 STUN（获取公网地址）和 TURN（中继服务器，最后手段）来解决。

### 12.3 游戏网络：选择性可靠性

游戏的数据包分为两类：

| 类型 | 要求 | 用哪种传输方式 |
|------|------|---------------|
| **位置 / 动作** | 低延迟，丢一帧马上有下一帧 | 不可靠（fire-and-forget） |
| **聊天 / 购买 / RPC** | 必须可靠送达 | 可靠（ACK + 重传） |

所以游戏网络库（比如 Valve 的 GameNetworkingSockets、腾讯的 GCloud）在 UDP 之上实现了**选择性可靠性**——同一连接上，有些消息可靠、有些不可靠。这比纯 TCP（全部可靠）或纯 UDP（全部不可靠）都更灵活。

### 12.4 MPTCP：多条网络路径同时用

手机同时有 WiFi 和 4G 两条链路。传统 TCP 只能用其中一条。MPTCP（Multipath TCP）允许一个 TCP 连接**同时利用多条路径**：

```
         ┌─ WiFi  (192.168.1.5) ────┐
手机      │                          ├── 服务器
         └─ 4G   (100.200.50.1) ────┘
```

目前 iOS/macOS 已内置 MPTCP 支持（用于 Apple Music、Siri 等服务）。

## 十三、总结：给不同角色的建议

### 如果你是一个后端开发者

- 理解 TIME_WAIT 和 CLOSE_WAIT 的含义，会排查连接泄露
- 熟练使用 `ss` / `netstat` / `tcpdump` 定位网络问题
- 知道 BBR 是什么，能在长肥网络上启用它
- Web 服务做长连接（Keep-Alive），数据库用连接池，避免短连接风暴
- 写 TCP 程序时处理粘包/半包问题

### 如果你是一个前端开发者

- 知道 HTTP/1.1（TCP）和 HTTP/3（QUIC over UDP）的区别
- 了解 WebRTC 为什么基于 UDP
- 理解页面同时只能开 6 个同域名 TCP 连接（浏览器限制）的原因
- 在 DevTools 的 Network 面板看协议列（h2 = HTTP/2 over TCP，h3 = HTTP/3）

### 如果你是一个 SRE / 运维

- BBR 是你的朋友，尤其在跨境 / 卫星链路场景
- 监控 TCP 重传率和 TIME_WAIT 连接数
- 理解 SYN Flood 攻击和相应的内核防护参数
- CDN 边缘节点到源站用 QUIC 可以减少一次握手延迟

### 如果只记一句话

> **TCP 给数据买保险，UDP 给数据买跑鞋。选哪个，取决于你的数据怕丢还是怕慢。**
