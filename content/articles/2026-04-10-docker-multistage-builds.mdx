## 从一个真实案例说起

一个 Go 微服务的 Docker 镜像，初始构建大小为 **1.2GB**。经过多阶段构建、优化基础镜像选择、消除无用依赖后，最终镜像体积缩减至 **15MB**，缩小了近 100 倍。

这不仅仅是存储空间的节省。更小的镜像意味着更快的推拉速度、更短的 Pod 启动时间、更小的攻击面。在 Kubernetes 环境下，镜像大小直接影响扩容速度——秒级还是分钟级的差别。

## 多阶段构建的核心思想

传统的 Dockerfile 中，构建工具链（编译器、依赖库、头文件）和运行时产物混在一起。多阶段构建的核心理念是：**在一个 Dockerfile 中使用多个 FROM 指令，编译阶段使用完整工具链，运行阶段只复制最终产物**。

### Go 应用示例：从 800MB 到 15MB

```dockerfile
# Stage 1: 编译阶段 — 包含 Go 工具链、依赖、源码
FROM golang:1.22-alpine AS builder

WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app/server .

# Stage 2: 运行阶段 — 只有最终二进制 + CA 证书
FROM scratch

COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /app/server /server

EXPOSE 8080
ENTRYPOINT ["/server"]
```

关键点：
- `-ldflags="-s -w"` 去除调试信息，进一步缩减二进制体积
- `CGO_ENABLED=0` 编译静态链接的二进制，不依赖任何系统库
- `FROM scratch` 是 0 字节的空基础镜像，最终镜像只有你的二进制 + 证书

### Node.js 应用示例：Next.js 从 1.5GB 到 150MB

```dockerfile
# Stage 1: 安装依赖
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --frozen-lockfile

# Stage 2: 构建
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

# Stage 3: 运行
FROM node:20-alpine AS runner
WORKDIR /app

RUN addgroup --system --gid 1001 nodejs && \
    adduser --system --uid 1001 nextjs

COPY --from=builder /app/public ./public
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static

USER nextjs
EXPOSE 3000
CMD ["node", "server.js"]
```

注意这里使用了**三个阶段**：deps → builder → runner。将依赖安装单独分离出来，当只有源码变更时，依赖层依然被缓存。

### Python 应用示例：从 800MB 到 120MB

```dockerfile
# Stage 1: 构建虚拟环境
FROM python:3.12-slim AS builder

RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential gcc \
    && rm -rf /var/lib/apt/lists/*

RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Stage 2: 运行
FROM python:3.12-slim AS runner

RUN groupadd -r appuser && useradd -r -g appuser appuser

COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

COPY --chown=appuser:appuser . .
USER appuser
CMD ["python", "app.py"]
```

Python 的虚拟环境天然适合多阶段构建——整个 `/opt/venv` 目录可以直接复制到运行镜像中。

## 构建缓存的正确姿势

Docker 的层缓存机制是按指令顺序生效的——一旦某一层发生变更，后续所有层都会重新构建。因此，**COPY 指令的顺序直接决定了缓存命中率**：

```dockerfile
# ✅ 好的顺序：依赖文件单独 COPY，变动频率低
COPY package.json package-lock.json ./
RUN npm ci --frozen-lockfile     # 这层被缓存，除非 package.json 变化
COPY . .                          # 这层因源码变化而 rebuild
RUN npm run build

# ❌ 差的顺序：源码和依赖一起 COPY，每次源码变化都重装依赖
COPY . .
RUN npm install                   # 每次都重新执行
RUN npm run build
```

这个简单的顺序调整，在 CI/CD 中可以将构建时间从 5 分钟降到 30 秒（缓存命中时）。

### BuildKit 缓存挂载

Docker BuildKit 提供了更精细的缓存控制：

```dockerfile
# syntax=docker/dockerfile:1

# 使用缓存挂载，npm 缓存跨构建持久化
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --frozen-lockfile
```

启用 BuildKit：`DOCKER_BUILDKIT=1 docker build .` 或在 `docker buildx` 中默认启用。

## 基础镜像的选择

| 基础镜像 | 大小 | 特点 | 适用场景 |
|----------|------|------|----------|
| `scratch` | 0B | 完全空，无 shell、无工具 | Go/Rust 纯静态二进制 |
| `alpine:3.20` | ~7MB | musl libc + apk 包管理 | 需要 shell 的通用场景 |
| `distroless` | ~15MB | 无 shell、无包管理器，安全性最高 | 严格要求安全的 Java/Go/Python 应用 |
| `debian:slim` | ~70MB | glibc + 基础工具 | 需要 glibc 兼容性 |
| `ubuntu:22.04` | ~77MB | 完整系统环境 | 需要完整系统包的场景 |

选择原则：**够用就行，越小越好**。

Alpine 需要注意一个坑：它使用 musl libc 而非 glibc。一些 C 扩展或使用了 glibc 特定行为的程序可能需要适配。遇到 DNS 解析或性能问题时，考虑切回 slim 镜像。

## 减少层数 vs 可读性

每个 `RUN`、`COPY`、`ADD` 指令都会创建一个镜像层。旧的最佳实践强调合并 RUN 指令以减少层数：

```dockerfile
# 旧式做法：合并所有命令到一层
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl ca-certificates && \
    rm -rf /var/lib/apt/lists/* && \
    curl -fsSL https://example.com/script.sh | sh && \
    rm script.sh
```

在现代 Docker（overlay2 存储驱动）下，层数对性能的影响已经很小。**可读性和可维护性比减少层数更重要**。每层做一件事，让人一眼能看懂 Dockerfile 做了什么。

## 安全检查清单

多阶段构建天然减少了攻击面（编译器、构建依赖不会出现在运行镜像中），但还需要做好以下几点：

1. **使用非 root 用户运行** — `USER` 指令，在 runner 阶段创建专用用户
2. **锁定基础镜像版本** — `FROM node:20-alpine` 而不是 `FROM node:latest`
3. **不要 COPY . 整个上下文** — 使用 `.dockerignore` 排除 `.git`、`.env`、`node_modules`
4. **扫描镜像漏洞** — 集成 Trivy 或 Snyk 到 CI 流水线
5. **添加 HEALTHCHECK** — 让编排系统知道容器真实状态

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/api/health || exit 1
```

## .dockerignore 的力量

构建上下文越大，docker build 的第一步（发送上下文到 daemon）就越慢。一个 `.dockerignore` 文件可以显著加速构建：

```
.git
.github
node_modules
.next
.env
.env.*
*.md
.gitignore
Dockerfile
docker-compose.yml
```

## 镜像优化的完整检查清单

1. 使用多阶段构建，编译环境和运行环境严格分离
2. 选择最小化的基础镜像（scratch > alpine > distroless > slim）
3. 合理排列 COPY 顺序，先复制依赖文件再复制源码
4. Go: `CGO_ENABLED=0 -ldflags="-s -w"`
5. Node: `npm ci --frozen-lockfile`，生产环境 `--only=production`
6. Python: 在 builder 阶段创建 venv，直接复制到 runner
7. 同一层内做清理（`apt-get install && rm -rf /var/lib/apt/lists/*`）
8. 使用 `.dockerignore` 排除不必要文件
9. 使用非 root 用户运行
10. 添加 HEALTHCHECK

优化后的镜像不仅节省了存储和带宽——更重要的是**缩短了部署和扩容的时间窗口**。当你的服务需要紧急扩容时，30 秒和 3 分钟的差别就是事故等级的分界线。
