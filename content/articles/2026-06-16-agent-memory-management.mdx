# AI Agent 的记忆系统：从"每次醒来都是新的一天"到"它比我还了解项目"

你用过 AI 编程助手吗？不管是 Claude Code、Cursor 还是 Copilot，你一定经历过这个场景：

> 昨天花了一下午让 AI 帮你重构了那个 3000 行的认证模块，它理解了你的设计意图，知道你对 JWT token 的命名习惯，甚至学会了你的代码风格。今天早上打开，说了一句"Hello"——
> 
> **它完全不记得昨天发生过什么。**

这就是 AI Agent 的**"金鱼记忆"问题**——每一次新对话都是一张白纸。更糟的是，即使在同一个对话中，随着你不断追加需求、贴入日志、讨论设计，上下文窗口也会慢慢被"淹没"，早期的关键指示沉入 token 海洋的底部，AI 开始"忘记"自己为什么要这么写。

这篇博客，我们就来彻底搞懂 AI Agent 的记忆系统。

## 先讲清楚一个类比：RAM 和硬盘

理解 Agent 记忆的第一步，是放弃"记忆就是记忆"的模糊想法。我们用一个你熟悉的类比：

```
你的电脑：
┌──────────┐    ┌──────────────┐
│   RAM    │ ←→ │   硬盘/SSD    │
│  快，小   │    │  慢，大，持久  │
│  断电即丢  │    │  关机后还在    │
└──────────┘    └──────────────┘

AI Agent 的记忆：
┌──────────┐    ┌──────────────┐
│ 上下文窗口 │ ←→ │  持久化记忆层   │
│  ~200K    │    │  无限，持久     │
│  会话结束即丢│   │  跨会话保留     │
└──────────┘    └──────────────┘
```

- **上下文窗口（Context Window）** 就是 Agent 的 RAM。它装的是当前任务正在"想"的东西：系统提示词、对话历史、工具调用结果。它很快（模型直接读取），但容量有限，会话结束就清空。
- **持久化记忆层（Persistent Memory）** 就是 Agent 的硬盘。它存的是应该长期保留的东西：你的偏好、项目的架构决策、上次踩过的坑。

这个类比之所以重要，是因为当前大多数 Agent 系统的故障都源于同一个根本性错误：**把上下文窗口当成了数据库来用**。

2025-2026 年的多项研究发现：当你把关键指令放在上下文窗口的底部（也就是早期对话中），随着会话增长，AI 遵守这些指令的概率会断崖式下降。一项针对 GPT-4 和 Claude 的研究（Gamage, 2026）跟踪了 10 个生产级 Agent 在 500 次任务中的表现，发现：

```
限制遵守率 (%)
 100 ┤
  80 ┤  █████
  60 ┤      ████████
  40 ┤              ████████████
  20 ┤                          ████████████████
   0 ┤
      └─────┬─────┬─────┬─────┬─────┬─────┬─────
            5     8    11    14    17    20
                    会话轮次 (turn)
```

到第 16 轮时，约束遵守率从初始的 74% 左右下降到约 33%。这不是模型变笨了——是早期的关键信息被后来的内容"挤出"了注意力范围。

## Agent 记忆的四种形态

借鉴人类认知科学的分类，现代 Agent 记忆系统通常划分为四个层次：

```
                      ┌──────────────────────┐
                      │   Procedural Memory   │ ← "我知道怎么做"
                      │   (技能 / 工作流)      │    从成功/失败中学到的策略
                      │   最慢形成，最有价值    │
                      ├──────────────────────┤
                      │   Episodic Memory     │ ← "我记得那次..."
                      │   (事件 / 经历)        │    上次修复bug的记录
                      │   跨会话持久化         │
                      ├──────────────────────┤
                      │   Semantic Memory     │ ← "我知道是什么"
                      │   (事实 / 偏好)        │    用户偏好TypeScript
                      │   最成熟，最常用       │
                      ├──────────────────────┤
    ┌─────────┐       │   Working Memory      │ ← 当前上下文窗口
    │  LLM    │ ←──── │   (当前任务状态)       │    对话历史 + 工具结果
    └─────────┘       └──────────────────────┘
```

### 1. 工作记忆（Working Memory）

这就是上下文窗口本身——当前对话中的所有内容。它是最"鲜活"的记忆层，LLM 可以直接"看见"。

**存储内容**：当前任务的状态（"后端初始化了，前端还在跑"）、最近的对话轮次、工具返回结果。

**关键挑战**：容量有限 + 信息衰减。200K 的窗口听起来很大，但在一个复杂任务中——API 文档 + 16 轮对话 + 8 次工具调用结果——很快就填满了。更糟的是，LLM 对窗口中间位置的内容注意力最弱，这被称为"中间丢失"效应。

### 2. 语义记忆（Semantic Memory）

最成熟、最常用的持久化记忆形态。它存储的是事实和概念——**是什么**。

```
"用户更喜欢用 TypeScript"          → 向量数据库
"数据库用的是 PostgreSQL 16"       → 知识图谱
"项目采用 monorepo 结构"           → 结构化元数据
```

检索方式通常是 RAG（检索增强生成）：把用户偏好、项目事实存到向量数据库里，每次构建 prompt 前先做相似度搜索，把最相关的信息注入上下文。

**优点**：实现简单，生态成熟（向量数据库几乎成了标配）。
**缺点**：只能记住"静态事实"，无法捕捉"过程知识"。

### 3. 情景记忆（Episodic Memory）

比语义记忆更高一层的记忆形态。它存储的是**发生过什么**——具体的交互事件、决策过程和它们的时间线。

```
"2026年3月15日，我们尝试用 Redis 做缓存，但因为内存不够放弃了"
"上次修复 CI 超时的策略是：把 docker-compose 的 build 改成 pull"
```

情景记忆让 Agent 不只是"知道一个事实"，而是能"回忆一次经历"。实现方式通常是在每次会话结束时做一次反思提取（reflection extraction），把关键发现和决策写入带有时间戳的记忆日志。

**这是目前 Agent 记忆研究中被公认"最有价值但最不成熟"的领域。**

### 4. 程序记忆（Procedural Memory）

最高级的记忆形态。它存储的是**怎么做的技能**——从多次成功和失败中抽象出来的可复用策略。

```
问题: "LD 链接器缓存损坏"
解决: "清理 build 缓存 → 重新配置 CMake → 增量编译"
成功率: 87% (7/8次尝试)
```

程序记忆让 Agent 真正具备了学习能力——它不只记住信息，还通过不断的试错和经验积累，形成可复用的技能。目前这个领域还在早期阶段，Acontext 和 Hindsight 是两个先行者。

## 灵魂问题：记忆存在哪里？

前面讲了四种记忆形态，但具体怎么存、存在哪？这取决于你用的是**托管模型**（Claude、GPT）还是**开源模型**。

### 如果你用托管 API（90% 开发者的现实）

你只能做**Token 级别的记忆**——数据库里存文本、偏好、事实摘要。每次构建 prompt 时，检索相关内容注入上下文。这是"用 RAG 模拟记忆"的思路。

优势是即插即用，不依赖模型内部。缺点也很明显：每次检索都可能漏掉相关内容（召回率问题），所有记忆内容都要消耗 token 预算。

### 如果你有开源模型权限

就可以探索另外两种形态：

- **Latent Memory（隐式记忆）**：把 KV cache 或压缩的隐藏状态保存下来，下次直接加载，让模型"接着上次的思考继续想"。不需要重新编码所有上下文。
- **Parametric Memory（参数记忆）**：通过微调（LoRA、QLoRA）把用户偏好"刻入"模型权重。但这是批量操作，不能增量更新，所以不适合需要实时学习的 Agent。

对于绝大多数人来说，Token 级别的记忆就是你能接触到的全部，好消息是它已经足够实用了——只要设计得当。

## 经典方案：MemGPT——把 LLM 当成操作系统

2023 年，MemGPT 论文的发表标志着一个转折点。它提出了一个至今仍在指导 Agent 记忆设计的思想：**把 LLM 的上下文窗口当成操作系统的 RAM 来管理**。

```
┌─── MemGPT 的记忆架构 ──────────────────────────────┐
│                                                    │
│   ┌────────── 主上下文 (RAM) ──────────┐           │
│   │  System Instructions (只读)         │           │
│   │  ┌──────────────────────────┐      │           │
│   │  │ Core Memory (可读写)      │      │           │
│   │  │ · Human   (用户画像)      │      │           │
│   │  │ · Persona (Agent人设)    │      │           │
│   │  └──────────────────────────┘      │           │
│   │  ┌──────────────────────────┐      │           │
│   │  │ FIFO Queue (对话历史)     │      │           │
│   │  │ · 最近的 N 轮对话        │      │           │
│   │  └──────────────────────────┘      │           │
│   └────────────────────────────────────┘           │
│                  ↕ 自主换入换出                     │
│   ┌────────── 外部上下文 (硬盘) ─────────┐         │
│   │  Recall Memory     │  Archival Memory │         │
│   │  完整对话历史备份    │  长期知识库       │         │
│   │  关键词/时间戳检索   │  语义向量检索     │         │
│   └────────────────────────────────────┘           │
└────────────────────────────────────────────────────┘
```

这套架构的核心创新不是分层本身——分层存储是操作系统教科书第一章的内容。创新在于 **Agent 自主管理**：不是外部代码决定什么该换入什么该换出，而是 LLM 自己通过工具调用来管理记忆。

### 三个关键机制

**1. 自我编辑记忆（Self-Editing Memory）**

Agent 可以通过 `core_memory_append` 和 `core_memory_replace` 这两个工具，主动修改自己的 Core Memory。当它判断某个信息很重要时，就自己写进核心记忆里；当某个旧信息不再对时，就自己替换掉。

```
Agent: 我注意到用户一直在用 Express 风格写路由。
       → 调用 core_memory_append("用户偏好 Express.js 风格的路由定义")
```

**2. 队列管理器（Queue Manager）**

对话历史不是永久保留在主上下文中的。当 FIFO 队列塞满时（达到 token 阈值），旧消息被移出。但不是直接丢弃——先用递归摘要压缩成一段话，存入 Recall Memory。这样既释放了 token 空间，又保留了后续可能需要的信息。

**3. 心跳机制（Heartbeat）**

Agent 在每次工具调用时可以附带 `request_heartbeat` 标志。如果设为 true，LLM 的这次回复会被当作一个"未完待续"的信号——框架收到后自动发起下一轮推理，Agent 继续执行。这让单次用户输入能触发一连串自主操作。

### 现实效果

MemGPT 让 7B 参数的模型在长对话任务中达到了接近 GPT-4 的表现。在被设计用来彻底暴露记忆短板的多会话测试中，MemGPT 大幅减少了"遗忘"和"上下文漂移"。

## 2026 年的方案光谱：从 MemGPT 到 Claude Code

MemGPT 证明了"分层自主记忆管理"这条路是对的。随后的两年里，这个方向爆发了大量实践和产品：

```
                    记忆管理的实现光谱
                    
  简单/够用 ←──────────────→ 复杂/强大
  
  OpenAI Memory    LangMem    MemGPT/Letta    Mem0    Hindsight
  (内置黑盒)      (开发者可控)  (OS式分层)    (多信号检索) (仿生记忆)
```

### Mem0：当前准确率之王

Mem0 是目前在记忆质量基准测试中表现最好的系统之一。它的核心设计理念是 **ADD-only 提取**——每次只需一次 LLM 调用就完成添加，不需要设计复杂的删除或替换操作；如果旧记忆过时了，依靠检索层的 **智能排序** 自然让它沉底。

在 2026 年 4 月的算法更新后，Mem0 在 LoCoMo（跨会话记忆测试）上拿到了 **91.6 分**，在 LongMemEval（长对话记忆质量）上拿到了 **93.4 分**。

它的检索逻辑不是简单的向量相似度，而是**三路信号融合**：

```
查询 → ┌─ 语义向量搜索 (Dense Embedding)
       ├─ BM25 关键词搜索 (Sparse/Lexical)
       └─ 实体链接 (Entity Graph)
           ↓
       加权融合 (RRF) → 排序结果
```

纯向量搜索在找"跟 X 差不多的东西"时很强，但在找**精确的代码片段**、**电话号码**或**人名**时，关键词匹配远胜向量。实体链接则解决了"同一个人的不同叫法"（CEO / 张总 / Zhang）的关联问题。

### Claude Code 的记忆生态

以 Claude Code 为例，2025-2026 年涌现了大量记忆方案。它们大多基于 **MCP（Model Context Protocol）** 协议，通过暴露工具让 Agent 主动读写记忆：

```
SessionStart Hook ─→ 注入上次会话的摘要和关键决策
      ↓
PostToolUse Hook ─→ 每 N 次工具调用后自动保存增量
      ↓
PreCompact Hook  ─→ 上下文压缩前提取最重要的知识
      ↓
SessionEnd Hook  ─→ 反思提取，写入持久存储
```

这个生态中最值得关注的几个方向：

| 方案 | 核心思路 | 存储 | 特色 |
|------|---------|------|------|
| **Claude Remember** | Hook 驱动的完整生命周期 | Markdown | Haiku 做廉价压缩，约 $0.01/次 |
| **memsearch** (Zilliz) | 跨平台统一记忆层 | Markdown + Milvus | 一份记忆跑在 Claude Code + Codex + OpenCode |
| **YesMem** | 完整本地连续性 | SQLite + 向量 | Ebbinghaus 遗忘曲线，知识点自动加强/衰退 |
| **agent-memory** | 极简单二进制 | SQLite | 11MB，零依赖，FTS5 全文搜索 |

一个很有趣的现象是：几乎所有方案都选择了 **本地优先（local-first）**——数据存在用户的磁盘上，SQLite + Markdown 是最常见的组合，MCP 是统一的通信协议。这与 2024 年流行的"上传到云端向量数据库"思路形成了鲜明对比。

### 硬约束钉死：一个四两拨千斤的技巧

在所有这些复杂系统之外，有一个简单到容易被忽视的模式，却能解决最大比例的问题：

> **把关键的、不应变的约束从持久化记忆中提取出来，在每次 LLM 调用时注入到系统提示词的最顶部。**

这就是"硬约束钉死"。顶部的系统提示词是注意力最集中的位置，不受后续对话淹没的影响。例如：

```
System Prompt (top):
  你是 TechBlog 的开发助手。
  硬约束：
  - 数据库 URL 永远用环境变量 DATABASE_URL，不要硬编码
  - 每次修改后必须运行 npm run build 验证
  - 用户偏好 TypeScript strict mode，不要用 any
  
  [动态注入的偏好...]
  
  [当前任务...]
```

这个模式不需要任何外部工具或数据库。它唯一的代价是你在每个会话开始时需要手动注入这些约束——但效果远远好于把它们写在对话的第二轮中。

## 动手实践

理论讲完了，我们来看两个可以直接跑的例子。

### 示例 1：用 Claude Code 的文件系统做记忆

这是最简单的入门方案——不用任何外部工具，就用 Markdown 文件 + `MEMORY.md` 索引。

```
项目目录/.claude/
├── MEMORY.md              ← 总索引，每行一条记忆链接
└── memory/
    ├── user-prefs.md      ← "用户偏好 TypeScript strict mode"
    ├── project-arch.md    ← "项目用了 Prisma + SQLite"
    ├── known-issues.md    ← "Docker build 时 sql.js WASM 加载失败"
    └── fix-strategies.md  ← "CI 超时的修复策略：拆 build 和 pull"
```

每条记忆一个文件，带 YAML frontmatter：

```yaml
---
name: docker-build-wasm-fix
description: Docker 构建时 sql.js WASM 加载失败的修复策略
metadata:
  type: project
  tags: [docker, sqljs, build]
---

## 问题
在 node:20-slim 镜像中，sql.js 的 WebAssembly.instantiate 失败。

## 根因
sql.js 的 locateFile 回调没有正确使用 scriptDir 参数。

## 解决方案
1. 在 locateFile 回调中使用第二个参数 scriptDir
2. 或者对依赖 WASM 的页面标记 force-dynamic
```

每次会话开始时，Claude 会把 `MEMORY.md` 的内容注入上下文。虽然简单，但对于个人项目来说完全够用。

### 示例 2：用 Mem0 做智能记忆

如果你想要更智能的自动提取和检索，用 Mem0：

```python
from mem0 import Memory

# 初始化（支持本地 Qdrant 或云端）
m = Memory()

# 添加记忆——Mem0 自动提取关键信息
m.add("用户要求所有 API 都用 Express 风格路由，不要用 Koa", user_id="dev_01")
m.add("上周修复了 Docker 构建超时，把 docker compose up --pull always 拆成了 pull + up", user_id="dev_01")
m.add("项目数据库从 MySQL 迁移到了 PostgreSQL 16", user_id="dev_01")

# 查询——三路信号融合
results = m.search("构建超时怎么修", user_id="dev_01")
# → 返回：关于 Docker pull/up 拆分的那条记忆

# 钉死关键约束
constraints = m.search("数据库配置", user_id="dev_01")
# → 返回：PostgreSQL 16 的那条记忆
```

重点在于 **user_id 过滤 + 多信号检索**。不依赖单一的向量相似度，当你的"构建超时"搜索词和记忆中的"Docker pull up 拆分"没有高语义相似度时（实际上它们确实不太像），BM25 关键词匹配可以兜底。

## 对各类开发者的建议

| 角色 | 策略 |
|------|------|
| **个人开发者** | 用 `.claude/MEMORY.md` 或 `.cursor/rules` 就够了。每次会话开始前花 30 秒更新一下已知问题列表，效果远超不管理 |
| **小团队** | 引入 Mem0 / memsearch，一套记忆服务同时供 Claude Code、Copilot、Codex 使用。关键是把**团队约定**钉死在系统提示词顶部 |
| **平台开发者** | 部署独立的持久化记忆层，至少支持语义 + 关键词 + 时间衰减三路检索。记忆不是存越多越好——设计**遗忘策略**比设计存储策略更重要 |
| **研究者** | 关注情景记忆和程序记忆的前沿。当前最成熟的语义记忆只解决了"记住事实"，但 Agent 真正需要的"从错误中学习"才刚刚起步 |

## 三个核心原则

兜了一大圈，总结下来就是三句话：

1. **上下文窗口是 RAM，不是硬盘。** 别把所有信息都塞进去，每次构建 prompt 前做按需检索。
2. **记忆不是越多越好，遗忘是一种能力。** 2025 年的研究发现"全量添加"会导致性能持续衰退。智能衰减、定期清理、把低频知识提炼为摘要后再删除——这些都是比"存更多"更重要的工程问题。
3. **可观测性比存储引擎更重要。** 你应该能回答"Agent 在这一步看到了什么记忆？为什么检索出了这一条而不是那一条？"如果无法回答，再强大的记忆系统也是黑盒。
