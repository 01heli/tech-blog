## 一、Pod 是临时的，数据怎么办？

回忆一下 Pod 的生命周期：Pod 会被创建、删除、重新调度到其他节点。每次重新创建，里面的文件系统都是从镜像重新开始的——之前写入的数据全没了。

```
Pod A（PostgreSQL，运行在 Node 1）
  /var/lib/postgresql/data/   ← 写入了 50GB 数据
  │
  ▼  Node 1 挂了，Pod 被调度到 Node 2
  │
  ▼
Pod B（PostgreSQL，运行在 Node 2）
  /var/lib/postgresql/data/   ← 空的！数据丢了！
```

这就是 **存储分离** 的必要性：**计算（Pod）和存储（数据）不能绑在一起，它们应该是独立的、可以分别调度的资源。**

K8s 用三层抽象来解决这个问题：

```
PersistentVolume (PV)      ← 集群级别的存储块（管理员创建）
        ↕
PersistentVolumeClaim (PVC) ← 用户的"存储申请单"（开发者创建）
        ↕
Pod (挂载 PVC)
```

## 二、PV 与 PVC：K8s 的存储供需模型

### 2.1 基本概念

用类比来理解：

> PV 是仓库里已经准备好的货架，PVC 是你提交的"我要一个货架"的申请单。K8s 收到 PVC 后，在已有的 PV 里找一个符合条件（大小、访问模式）的，然后把它"绑定"给你。Pod 通过 PVC 使用 PV，而不直接引用 PV。

```
管理员（创建 PV ── 提供存储容量）
    │
    │  PV-1: 10Gi, RWO, SSD
    │  PV-2: 100Gi, RWX, HDD
    │  PV-3: 50Gi, RWO, SSD
    │
    ▼
开发者（创建 PVC ── 申请存储容量）
    │
    │  PVC: 需要 10Gi, RWO, SSD
    │
    ▼
K8s 匹配 PV-1 → PVC → Pod 挂载
```

### 2.2 静态供给实操

**第 1 步：管理员创建 PV**

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-ssd-10g
spec:
  capacity:
    storage: 10Gi
  accessModes:
  - ReadWriteOnce      # 只能被一个 Node 上的 Pod 以读写方式挂载
  persistentVolumeReclaimPolicy: Retain   # PVC 删除后 PV 保留数据
  storageClassName: manual
  hostPath:            # 注意：hostPath 仅用于演示，生产环境不要用
    path: /data/pv001
```

**第 2 步：开发者创建 PVC**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi      # K8s 会找一个 >= 10Gi 的 PV
  storageClassName: manual
```

**第 3 步：Pod 挂载 PVC**

```yaml
spec:
  containers:
  - name: postgres
    image: postgres:16
    volumeMounts:
    - name: pgdata
      mountPath: /var/lib/postgresql/data
  volumes:
  - name: pgdata
    persistentVolumeClaim:
      claimName: db-pvc
```

> **重要：** 上面例子用了 `hostPath` 做演示，但 **`hostPath` 只适合本地测试**。生产环境需要的是网络存储——云厂商的块存储（AWS EBS、GCP Persistent Disk）、NFS、Ceph、GlusterFS 等。这些存储不依赖任何一台物理机器，Pod 迁移到其他 Node 也能正常访问。

### 2.3 访问模式与回收策略

| 访问模式 | 缩写 | 含义 |
|---------|------|------|
| ReadWriteOnce | RWO | 单节点读写（最常见） |
| ReadOnlyMany | ROX | 多节点只读 |
| ReadWriteMany | RWX | 多节点读写（需要网络文件系统） |
| ReadWriteOncePod | RWOP | 单个 Pod 独占读写（K8s 1.22+） |

| 回收策略 | 含义 |
|---------|------|
| **Retain** | PVC 删除后 PV 保留数据和状态，需管理员手动清理 |
| **Delete** | PVC 删除后 PV 和后端存储一起删除（云环境常用） |
| **Recycle** | 已废弃，简单清除数据后重新可用 |

## 三、StorageClass：动态供给——别手工创建 PV 了

手工创建 PV 的问题是明显的：每有新需求就得找管理员创建 PV。StorageClass 让这一切自动化——**开发者创建 PVC，K8s 自动创建 PV**。

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs    # 云厂商的存储插件
parameters:
  type: gp3                            # AWS GP3 SSD
  encrypted: "true"
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer   # 等 Pod 真的要用时才创建（避免跨可用区绑死）
allowVolumeExpansion: true               # 允许在线扩容
```

使用动态供给时，开发者只需要创建 PVC 并指定 `storageClassName`：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 50Gi
  storageClassName: fast-ssd      # 自动触发动态创建 PV
```

**本地开发环境（minikube/kind）自带 `standard` StorageClass，可以直接用动态供给。** 不需要手动创建 PV。

## 四、StatefulSet：为有状态应用设计的工作负载

Deployment 是为无状态应用（Web Server、API 服务）设计的——Pod 之间没区别，名字是随机后缀，随便杀随便建。

StatefulSet 是为有状态应用（数据库、消息队列、分布式存储）设计的——每个 Pod 有唯一的身份（名字是固定的 `name-0`、`name-1`、`name-2`），启动顺序可控制，每个 Pod 绑定独立的 PVC。

```
Deployment:           StatefulSet:
web-7d4f8b9c7-abc     db-0  ─── PVC-db-0 → PV-A  (主副本)
web-7d4f8b9c7-def     db-1  ─── PVC-db-1 → PV-B  (从副本，从 db-0 同步)
web-7d4f8b9c7-ghi     db-2  ─── PVC-db-2 → PV-C  (从副本)

Pod 名字随机            Pod 名字固定
删除重建名字会变        删除重建名字不变
共享同一个 PVC 不行    每个 Pod 有专属 PVC
```

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-headless    # 必须有一个 Headless Service
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:16
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:             # 每个 Pod 自动创建独立的 PVC
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 100Gi
```

StatefulSet 有三个关键行为：
1. **有序启动**：`postgres-0` 先启动，Ready 后才启动 `postgres-1`，以此类推（`podManagementPolicy: OrderedReady` 默认行为）
2. **有序终止**：倒序停止，`postgres-2` → `postgres-1` → `postgres-0`
3. **稳定网络标识**：每个 Pod 的 DNS 名是 `postgres-0.postgres-headless.default.svc.cluster.local`，这是固定的

## 五、数据库跑在 K8s 上，到底靠不靠谱？

这是社区争论了多年的话题。到今天（2026 年），答案已经比较清晰了：

| 场景 | 建议 |
|------|------|
| 开发/测试环境 | 完全可以在 K8s 上跑，StatefulSet + PVC 足够 |
| 生产环境 — 小规模（< 100GB 数据） | 可以。用云厂商的块存储（gp3/io2）+ 备份 CronJob + VPA |
| 生产环境 — 中等规模（100GB - 1TB） | 需要 Operator（如 CloudNativePG、Zalando Postgres Operator、Percona Operator for MongoDB）管理复制、故障转移、备份恢复 |
| 生产环境 — 大数据量 / 高 SLA | 建议用托管服务（RDS、Cloud SQL），把数据库放在 K8s 外面。K8s 的 Service 通过 ExternalName 指向它 |

> **一个务实的立场：** 不要因为"K8s 能跑数据库"就把一切搬到 K8s 上。K8s 的强项是管理无状态应用的声明式编排。数据库需要的是稳定的 I/O 性能、可靠的备份与恢复、对抗网络分区的一致性协议——这些不是 K8s 的原生能力，需要大量 Operator 代码来填补。如果团队没有专人维护 K8s 上的数据库 Operator，托管服务是更安全的选择。
