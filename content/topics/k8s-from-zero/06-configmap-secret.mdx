## 一、不要把你的配置写死在镜像里

Docker 的最佳实践里有一条黄金法则：**镜像应该是不可变的、与环境无关的。** 同一个镜像，在开发环境应该能跑，在生产环境也能跑——区别只在于注入的配置不同。

如果配置写死在镜像里，会有什么后果？

```
┌─────────────────────────────────────────────┐
│  镜像: myapp:v1                              │
│  内部 /app/config.yml 硬编码了：              │
│    DB_HOST=dev-db.internal                   │
│    REDIS_HOST=dev-redis.internal            │
│    LOG_LEVEL=debug                           │
│                                              │
│  要部署到生产环境？                            │
│  → 得重新构建一个镜像                          │
│  → 换了一个环境就要构建一次                     │
│  → 镜像和环境强绑定，违背了容器化的初衷          │
└─────────────────────────────────────────────┘
```

正确的做法是：**镜像只包含代码和依赖，配置在运行时注入。** K8s 提供了两个专门的资源来实现这一点——ConfigMap（非敏感配置）和 Secret（敏感配置）。

## 二、ConfigMap：普通配置的容器

### 2.1 创建 ConfigMap

```bash
# 方式 1：从字面量创建
kubectl create configmap app-config \
  --from-literal=DB_HOST=postgres-prod \
  --from-literal=LOG_LEVEL=info \
  --from-literal=CACHE_SIZE=256

# 方式 2：从文件创建
kubectl create configmap app-config --from-file=config.yaml

# 方式 3：从目录创建（目录下所有文件各成为一个 key）
kubectl create configmap app-config --from-file=./configs/
```

```bash
# 查看
kubectl get configmap app-config        # 列表
kubectl describe configmap app-config   # 详细内容
```

### 2.2 注入到 Pod 的三种方式

**方式一：环境变量**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
  - name: app
    image: myapp:latest
    envFrom:
    - configMapRef:
        name: app-config             # 把整个 ConfigMap 的所有 key 都变成环境变量
    env:
    - name: SPECIFIC_KEY
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: DB_HOST               # 只取其中一个 key
```

**方式二：挂载为文件**

```yaml
spec:
  containers:
  - name: app
    image: myapp:latest
    volumeMounts:
    - name: config-volume
      mountPath: /etc/app/config
      readOnly: true
  volumes:
  - name: config-volume
    configMap:
      name: app-config
```

效果：ConfigMap 中每个 key 变成 `/etc/app/config/` 下的一个文件。你的应用直接读文件即可——Python 的 `open('/etc/app/config/DB_HOST').read()`，Node.js 的 `fs.readFileSync('/etc/app/config/DB_HOST')`。

> **哪种更好？** 环境变量简单直接，但修改后需要重启 Pod 才能生效。文件挂载支持热更新（K8s 会定期同步 ConfigMap 的变更到挂载的文件，应用如果做了文件监听就能热加载）。而且文件方式天然避免了环境变量的长度限制和特殊字符转义问题。

**方式三：命令行参数**

```yaml
spec:
  containers:
  - name: app
    image: myapp:latest
    command: ["/app/server"]
    args: ["--db-host=$(DB_HOST)", "--log-level=$(LOG_LEVEL)"]
    envFrom:
    - configMapRef:
        name: app-config
```

### 2.3 ConfigMap 的 immutability（不可变性）

ConfigMap 支持设为 immutable，防止误改：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
immutable: true         # 设为不可变后只能删掉重建
data:
  DB_HOST: postgres-prod
```

Immutability 在 GitOps 工作流中很有用——你通过 ArgoCD/Flux 把 ConfigMap 和 Deployment 一起声明管理，不需要运行时改动。

## 三、Secret：敏感信息的安全存储

Secret 和 ConfigMap 在 API 层面以及使用方式上几乎一样。唯一的区别是：**Secret 是为存储敏感信息（密码、令牌、证书）而专门设计的，K8s 对它有额外的保护措施。**

### 3.1 创建 Secret

```bash
# 方式 1：从字面量创建
kubectl create secret generic db-credentials \
  --from-literal=username=admin \
  --from-literal=password='P@ssw0rd!2024'

# 方式 2：从文件创建
kubectl create secret generic tls-certs \
  --from-file=cert.pem \
  --from-file=key.pem

# 方式 3：创建 TLS 专用 Secret
kubectl create secret tls my-tls \
  --cert=path/to/cert.pem \
  --key=path/to/key.pem

# 方式 4：Docker Registry 认证 Secret
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=myuser \
  --docker-password=mypass
```

**K8s 的 Secret 默认只做 base64 编码，不是加密存储。** `echo 'aGVsbG8=' | base64 -d` 就能解开。这是一个常见误解——以为 Secret 里的数据是加密的。

### 3.2 让 Secret 真正安全

```bash
# 第一步：启用 etcd 静态加密
# 在 API Server 配置中添加 --encryption-provider-config
# 这样所有写入 etcd 的 Secret 数据就是加密的

# 第二步：启用 RBAC 限制谁可以访问 Secret
kubectl create role secret-reader --verb=get --resource=secrets -n production
kubectl create rolebinding secret-reader --role=secret-reader --user=ci-bot -n production

# 第三步（推荐）：使用外部密钥管理工具
# - Sealed Secrets (Bitnami)：对 Secret 二次加密，安全提交到 Git
# - External Secrets Operator：从 AWS Secrets Manager / GCP Secret Manager / Vault 同步
# - Vault Sidecar Injector：HashiCorp Vault 的动态 Secret 注入
```

**生产环境的一个典型做法：** Secret 的原始内容不存 Git，而是用 Sealed Secrets 或 External Secrets Operator 从云上的密钥管理服务同步。这样即使 Git 仓库泄露了，攻击者也拿不到真实的密码。

### 3.3 在 Pod 中使用 Secret

```yaml
spec:
  containers:
  - name: app
    image: myapp:latest
    env:
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: password
    volumeMounts:
    - name: tls
      mountPath: /etc/tls
      readOnly: true
  volumes:
  - name: tls
    secret:
      secretName: my-tls
  imagePullSecrets:
  - name: regcred               # 拉私有镜像用的认证
```

## 四、ConfigMap 和 Secret 的实用对比

| 特性 | ConfigMap | Secret |
|------|-----------|--------|
| 存储方式 | 明文（无编码） | Base64 编码 |
| 大小限制 | 1 MiB per object | 1 MiB per object |
| 热更新 | 支持（文件挂载模式） | 支持（文件挂载模式） |
| 环境变量注入 | ✅ | ✅ |
| 文件挂载 | ✅ | ✅ |
| Immutable | ✅ | ✅ |
| 加密存储 | 否 | 否（需额外配置 etcd 加密） |
| 适合存储 | 数据库地址、日志级别 | 密码、密钥、令牌、证书 |

## 五、实战：一个应用同时使用 ConfigMap 和 Secret

以下是一个完整的例子——Web 应用用 ConfigMap 读业务配置，用 Secret 读数据库密码和 TLS 证书：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  DB_HOST: "postgres-svc"
  DB_PORT: "5432"
  DB_NAME: "myapp"
  REDIS_HOST: "redis-svc"
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "100"
---
apiVersion: v1
kind: Secret
metadata:
  name: web-secrets
type: Opaque
stringData:              # stringData 可以用明文，K8s 会自动 base64 编码
  DB_USER: "myapp_user"
  DB_PASSWORD: "MyS3cur3P@ss!"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: app
        image: myapp:latest
        ports:
        - containerPort: 8080
        envFrom:
        - configMapRef:
            name: web-config
        env:
        - name: DB_USER
          valueFrom:
            secretKeyRef:
              name: web-secrets
              key: DB_USER
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: web-secrets
              key: DB_PASSWORD
        volumeMounts:
        - name: config
          mountPath: /etc/app
          readOnly: true
      volumes:
      - name: config
        projected:                  # Projected Volume：合并多个源为一个目录
          sources:
          - configMap:
              name: web-config
          - secret:
              name: web-secrets
              items:
              - key: DB_PASSWORD
                path: db-password   # 只暴露特定 key 为文件
```

> **Projected Volume** 是把多个 ConfigMap / Secret 合并到同一个目录的技术。在上面的例子中，`/etc/app/` 下既有 ConfigMap 的键（`DB_HOST`、`LOG_LEVEL` 等），也有 Secret 的 `db-password` 文件。

下一章我们来看 K8s 里最容易被忽视的基础设施——存储。数据库的 Pod 挂了重启，数据不能丢，PersistentVolume 和 StatefulSet 就是为这个设计的。
