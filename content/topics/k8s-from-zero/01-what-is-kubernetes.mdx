## 一、先别急学 K8s，我们先回到没有它的时代

在理解 Kubernetes 之前，我们需要先回答一个更基础的问题：**Kubernetes 到底在解决什么问题？**

要回答这个问题，先在脑子里过一遍你的项目上线流程。

### 物理机时代（2005 年以前）

```
┌─────────────────────────────┐
│   一台物理服务器              │
│   ┌───────┐ ┌──────────┐   │
│   │ Nginx │ │ Node.js  │   │
│   │ MySQL │ │ Redis    │   │
│   └───────┘ └──────────┘   │
│                             │
│   问题：                     │
│   · Node.js 内存泄漏 → OOM   │
│     → MySQL 也被杀掉了        │
│   · 升级 Node.js 版本        │
│     → 依赖冲突 → 全部重装     │
│   · 买了一台新机器            │
│     → 花半天重配一遍环境      │
└─────────────────────────────┘
```

那时候，一台物理机上跑好几个服务。一个服务出问题（比如内存泄漏导致 OOM），系统会把同机器上的其他服务也杀掉。环境配置也很痛苦——每台机器的依赖版本、系统库、配置文件稍有不同，代码在这台机器上能跑，换一台就各种报错。"在我机器上能跑"是那个时代最常听到的开场白。

### 虚拟机时代（2005–2014）

VMware、VirtualBox、KVM 带来的虚拟机解决了"环境隔离"的问题：每个应用跑在自己的虚拟机里，有自己的操作系统，互相不干扰。

```
┌────────────────────────────────────┐
│  物理服务器 1                       │
│  ┌──────────┐ ┌──────────┐        │
│  │ VM1: Nginx│ │ VM2: Java│        │
│  │ 4核 8G   │ │ 4核 8G   │        │
│  │ 实际用量  │  │ 实际用量   │        │
│  │ 10% CPU  │  │ 15% CPU  │        │
│  └──────────┘ └──────────┘        │
│                                     │
│  问题：每个 VM 要运行完整操作系统       │
│        → 内核占用 ~1GB 内存           │
│        → 启动需要 30-60 秒            │
│        → CPU/内存利用率很低            │
└────────────────────────────────────┘
```

虚拟机解决了隔离问题，但引入了一个新的浪费：每台虚拟机都要跑一个完整的操作系统。一个操作系统内核本身占大约 1GB 内存，启动要几十秒。三台虚拟机就是 3GB 被操作系统本身吃掉——这些本来是业务能用的资源。

### 容器时代（2013 年起）

Docker 的出现改变了这一切。容器和虚拟机的核心区别用一张图就能说明白：

```
虚拟机架构：                    容器架构：

┌──────────────────┐          ┌──────────────────┐
│ App A │ App B    │          │ App A │ App B    │
│ Bins/libs│Bins/libs│        │ Bins/libs│Bins/libs│
│ Guest OS│Guest OS │          │        │         │
├─────────┴─────────┤          ├────────┴─────────┤
│   Hypervisor      │          │  Container Engine │
├───────────────────┤          ├───────────────────┤
│   Host OS         │          │   Host OS         │
├───────────────────┤          ├───────────────────┤
│   物理硬件          │          │   物理硬件          │
└──────────────────┘          └──────────────────┘

每个 VM 有自己的 OS 内核          所有容器共享一个 OS 内核
启动 30-60 秒                    启动 < 1 秒
每 VM ~1GB 浪费                  几乎没有额外内存开销
```

容器之所以"轻"，是因为它不做硬件虚拟化。它用的是 Linux 内核自带的隔离机制——**namespace** 负责"看不见"（每个容器有自己独立的进程、网络、文件系统视图），**cgroup** 负责"用多少"（限制每个容器的 CPU、内存、磁盘 I/O 上限）。

> **一句话总结：** 虚拟机隔离的是硬件，容器隔离的是进程。前者需要虚拟出一整个操作系统，后者只需要借用宿主机的内核。

### 新问题：谁来管理成百上千个容器？

容器本身很轻，但生产环境中你会有成百上千个容器。新问题随之而来：

- 这 200 个容器分布在哪几台机器上？谁来做分配决策？
- 如果某台机器挂了，上面的容器要自动迁移到其他机器——谁来做？
- 流量突然涨了 10 倍，要自动扩容——谁来执行？
- 滚动升级容器的镜像版本，新版本有问题要快速回滚——谁来做？
- 服务 A 需要调用服务 B，但 B 的 IP 地址在每次重启后都会变——谁来跟踪？

这些问题就是**容器编排（Container Orchestration）**要解决的问题。而 Kubernetes，就是目前地球上最流行的容器编排平台。

## 二、Kubernetes 的设计哲学：声明式而非命令式

理解 K8s，最重要的不是记命令，而是理解一种思维方式的转变：**从"我要做什么"变成"我想要什么状态"**。

这两种方式分别叫**命令式（Imperative）**和**声明式（Declarative）**：

```
命令式（你告诉系统每一步怎么做）：
  $ docker run -d --name web nginx:1.25
  $ docker run -d --name web2 nginx:1.25
  $ docker run -d --name web3 nginx:1.25
  → 你手动启动了 3 个容器，如果某个挂了你要手动重启

声明式（你告诉系统你想要的最终状态）：
  apiVersion: apps/v1
  kind: Deployment
  spec:
    replicas: 3
    template:
      spec:
        containers:
        - name: web
          image: nginx:1.25
  → 你告诉 K8s："我希望任何时候都有 3 个 nginx:1.25 的副本在运行"
  → 至于怎么做到、在哪台机器上跑、挂了怎么补——那是 K8s 的事
```

声明式系统的底层靠的是**控制循环（Control Loop）**，也叫**调谐（Reconcile）**：

```
┌──────────────────────────────────────────────────┐
│                                                   │
│   期望状态（Desired State）      实际状态（Actual State）
│   ┌──────────────┐              ┌──────────────┐  │
│   │ replicas: 3  │              │ 跑了 2 个     │  │
│   └──────────────┘              └──────────────┘  │
│          │                              │         │
│          └────────── 对比 ←─────────────┘         │
│                       │                           │
│                   不一致！                          │
│                       │                           │
│                  ┌────▼────┐                      │
│                  │ 启动第 3  │                      │
│                  │ 个副本    │                      │
│                  └─────────┘                      │
│                                                   │
│  这个"观察 → 对比 → 修正"的循环，K8s 内部每秒都在跑   │
└──────────────────────────────────────────────────┘
```

这个设计带来了一个极具价值的属性：**自愈能力（Self-Healing）**。你不需要写监控脚本、告警规则、自动恢复程序。你只需要声明"我要 3 个副本"，K8s 的控制器会持续监控实际状态，一旦发现不够就自动补上。某个 Pod 挂了、某台 Node 宕机了——你甚至可能察觉不到。

## 三、K8s 集群的组成：Control Plane 和 Node

一个 K8s 集群由两类节点组成：

```
┌─────────────────────────────────────────────────┐
│               Control Plane（控制面）              │
│                                                  │
│  etcd ←──→ API Server ←──→ Scheduler            │
│  (数据存储)  (统一入口)       (调度器)              │
│                ↕                                  │
│           Controller Manager                    │
│           (控制循环引擎)                          │
│                ↕                                  │
│           Cloud Controller Manager               │
│           (云平台对接，可选)                       │
└──────────────┬──────────────────────────────────┘
               │
               │ (kubelet 上报状态，API Server 下发指令)
               │
┌──────────────▼──────────────────────────────────┐
│                 Node（工作节点）                    │
│                                                   │
│  kubelet ←→ Container Runtime (containerd/docker) │
│  (节点代理)  (真正跑容器的东西)                     │
│                                                   │
│  kube-proxy                                      │
│  (网络规则管理，负责 Service 的负载均衡)            │
└──────────────────────────────────────────────────┘
```

各组件的职责可以用一个快递公司的类比来理解：

| K8s 组件 | 职责 | 快递公司类比 |
|----------|------|------------|
| **etcd** | 存储集群所有数据（配置、状态） | 总部的中央数据库 |
| **API Server** | 所有操作的统一入口 | 前台，任何人要办事都只能通过他 |
| **Scheduler** | 决定 Pod 在哪个 Node 上运行 | 调度员，分派包裹到最合适的仓库 |
| **Controller Manager** | 运行各种控制器，维持期望状态 | 仓库管理员，每天对账，少了就补 |
| **kubelet** | 每个 Node 上的代理，执行指令 | 每个仓库的收货员，接收总部命令 |
| **kube-proxy** | 维护网络规则，实现 Service 负载均衡 | 每个仓库的快递员，负责送货上门 |

> 一个快速记忆的方式：**Control Plane 负责"想"——集群应该是什么样的，Node 负责"做"——把容器实际跑起来。**

## 四、理解 K8s 的最小单元：Pod

在 K8s 里，你从来不直接操作容器。K8s 操作的最小单元是 **Pod**。

Pod 是一个逻辑概念：**一个 Pod 可以包含一个或多个容器，这些容器共享同一个网络命名空间（共享 IP 和端口空间）和同一个存储卷（Volume）**。大多数情况下一个 Pod 只跑一个主容器，但有些场景需要"伴生容器（Sidecar Container）"——比如主容器跑应用，伴生容器负责收集日志或配置热更新。

```
Pod 的内部结构：

┌──────────────────────────────────────┐
│ Pod: web-app-6d4f8b9c7-xyz          │
│ IP: 10.244.1.5                       │
│                                      │
│  ┌─────────────────┐  ┌───────────┐ │
│  │ Container: nginx │  │ Sidecar:  │ │
│  │ Port: 80         │  │ log-shipper│ │
│  │                  │  │            │ │
│  │ 共享 localhost ←─┼──┤ 同 Pod 内   │ │
│  │                  │  │ 容器可以通过 │ │
│  │                  │  │ localhost   │ │
│  │                  │  │ 互相通信    │ │
│  └─────────────────┘  └───────────┘ │
│                                      │
│  共享 Volume: /var/log (两个容器都能访问) │
└──────────────────────────────────────┘
```

**Pod 的生命周期是临时的。** Pod 会被创建、销毁、重新调度到其他节点。Pod 的 IP 地址在每次重启后都会改变。这就是为什么 K8s 需要 Service——一个稳定的访问入口，下章会详细讲。
