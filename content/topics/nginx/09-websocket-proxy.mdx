## WebSocket 和普通 HTTP 有什么不同？

普通的 HTTP 请求是"请求-响应"模式：客户端发请求，服务器返回响应，连接结束（或 keepalive 复用一小会儿）。

WebSocket 完全不同：客户端发起一个**升级（Upgrade）请求**，服务器同意后，TCP 连接**切换协议**，从 HTTP 变成 WebSocket。之后这个连接一直保持，双方可以随时互发消息。这就像打电话：你拨号（发起 HTTP），对方接听（同意升级），然后你们一直通话（WebSocket）。

## 最简单的 WebSocket 代理

```nginx
location /ws/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

关键的三行：

| 指令 | 为什么必须设 |
|------|-------------|
| `proxy_http_version 1.1` | WebSocket 需要 HTTP/1.1，而 Nginx 默认用 HTTP/1.0 代理请求 |
| `proxy_set_header Upgrade $http_upgrade` | 把客户端请求中的 Upgrade 头传给后端 |
| `proxy_set_header Connection "upgrade"` | 告诉后端"这是一个协议升级请求" |

### 发生了什么？

1. 客户端发来一个带特殊头的 HTTP 请求
2. Nginx 把这些头转发给后端
3. 后端返回 `101 Switching Protocols` 状态码
4. Nginx 看到 `101`，知道协议切换发生了，于是保持 TCP 连接透传
5. 之后 Nginx 对这个连接不再做 HTTP 解析，直接做**双向 TCP 隧道**

## 完整配置

```nginx
location /ws/ {
    proxy_pass http://127.0.0.1:8080/;

    # HTTP 版本
    proxy_http_version 1.1;

    # WebSocket 必须的头
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";

    # 常规代理头
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # 关键：WebSocket 连接的超时
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

**`proxy_read_timeout` 这里是 1 小时**。为什么设这么长？WebSocket 连接可能在很长时间内没有数据传输（比如用户只是开着页面但没操作）。如果超时太短，Nginx 会切断这个空闲连接。

## 理解超时：两个层面的超时

WebSocket 场景下有两个独立的超时需要关注：

### 1. Nginx 代理层超时

```nginx
proxy_read_timeout 3600s;   # Nginx 等后端数据的最大时间
proxy_send_timeout 3600s;   # Nginx 等客户端接收的最大时间
```

如果 3600 秒内这条连接上没有任何数据传输，Nginx 会关闭它。

### 2. 应用层心跳

即使 Nginx 超时设得再长，你也应该在**应用层实现心跳（Ping/Pong）机制**。WebSocket 协议自带 ping/pong 帧：

- 客户端或服务器发 ping
- 对方必须回 pong
- 如果连续几次 ping 都没收到 pong，说明连接可能已经死掉了

大多数 WebSocket 库会自动处理 ping/pong。注意应用层的心跳间隔要小于 Nginx 的 `proxy_read_timeout`，比如 Nginx 超时 3600s，心跳间隔设 60s。

## WebSocket 负载均衡

如果你的 WebSocket 服务有多个实例，需要解决一个特殊问题：**同一个客户端的 WebSocket 连接必须一直打到同一台后端**。因为 WebSocket 是有状态的——连接建立后，后端持有这个客户端的上下文。

用 `ip_hash` 是最简单的方案：

```nginx
upstream ws_backend {
    ip_hash;
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
}

server {
    location /ws/ {
        proxy_pass http://ws_backend/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
    }
}
```

`ip_hash` 保证同一个客户端 IP 始终路由到同一台后端。

### ip_hash 的问题

如果客户端 IP 变了（比如用户从 WiFi 切换到 4G），连接会打到另一台后端，之前的 session 丢失。更严重的是，大量用户可能共享同一个出口 IP（公司 NAT），导致负载倾斜。

**更好的方案**是用 **sticky cookie**（需要 Nginx Plus），或者**把 session 外置到 Redis**。应用层不要在内存里存 WebSocket 上下文，而是存到 Redis 中，这样任何后端实例都能处理任何客户端。

## 调试 WebSocket 代理问题

WebSocket 代理最常见的三个问题：

### 问题 1：连接立即断开

```bash
# 看 Nginx error log
tail -f /var/log/nginx/error.log
```

原因通常是：
- `proxy_read_timeout` 太短（默认 60s）
- 忘记设 `proxy_http_version 1.1`（默认 1.0 不支持 Upgrade）
- 后端没有正确处理 WebSocket 握手

### 问题 2：浏览器报 502 Bad Gateway

说明后端拒绝了连接或根本连不上。检查：
- 后端是否在运行？
- proxy_pass 的地址和端口正确吗？
- 防火墙有没有拦截？

### 问题 3：消息延迟很大

```nginx
proxy_buffering off;  # 关闭缓冲，实时转发
```

默认 `proxy_buffering on`，Nginx 会等后端响应收完再发给客户端。WebSocket 场景下必须关掉。

## 实战：Socket.IO + Nginx

如果你的应用用的是 Socket.IO（Node.js 最流行的 WebSocket 库），配置略有不同：

```nginx
location /socket.io/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    proxy_read_timeout 86400s;  # 24 小时
    proxy_buffering off;
}
```

Socket.IO 有自己的路径前缀 `/socket.io/`，所以不用匹配所有 `/ws/` 路径。

## 小结

这一章我们学到了：

1. WebSocket 协议升级过程：HTTP → `101 Switching Protocols` → 双向通信
2. 代理 WebSocket 的三个关键指令：`http_version 1.1`、`Upgrade` 头、`Connection` 头
3. `proxy_read_timeout` 要设得足够长（至少数小时）
4. 负载均衡 WebSocket 要用 `ip_hash` 或外置 session
5. 调试技巧：看 error log、关 buffering、检查超时
