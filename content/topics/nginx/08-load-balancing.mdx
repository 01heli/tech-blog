## 从单机到集群

你部署了一个 Node.js 应用，在 `127.0.0.1:3000` 上运行。一开始没问题，但随着用户增多，单进程开始吃力。你启动了第二个实例在 `3001` 端口，第三个在 `3002` 端口。现在的问题是：**谁来把用户请求均匀地分配到这三个实例上？**

答案：Nginx 的 `upstream` 模块。

## upstream：定义一组后端服务器

```nginx
upstream backend {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend;
        include snippets/proxy-params.conf;
    }
}
```

这就是最基本的负载均衡配置。Nginx 默认使用**轮询（Round Robin）**——三个后端轮流接收请求。

## 调度算法（Load Balancing Methods）

`upstream` 支持多种调度策略：

### 1. 轮询 Round Robin（默认）

```nginx
upstream backend {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
}
```

最简单公平：请求 1 → 3000，请求 2 → 3001，请求 3 → 3002，请求 4 → 3000 ... 循环往复。

### 2. 加权轮询 Weighted Round Robin

```nginx
upstream backend {
    server 127.0.0.1:3000 weight=3;
    server 127.0.0.1:3001 weight=1;
    server 127.0.0.1:3002 weight=1;
}
```

3000 这台服务器配置更高（4 核 8G），可以处理更多请求，所以给 `weight=3`。每 5 个请求中，3 个发给 3000，各 1 个发给 3001 和 3002。

### 3. IP 哈希 IP Hash

```nginx
upstream backend {
    ip_hash;
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
}
```

同一客户端 IP 的请求始终路由到同一台后端。这解决了**session 共享**的问题：用户的登录状态存在后端内存里，需要让同一个用户每次打到同一台机器。这种需求叫 **session sticky**（会话保持）。

**ip_hash 的局限**：如果有很多用户来自同一个公司出口 IP（NAT 场景），所有用户都会打到同一台后端，负载不均衡。

### 4. 最少连接 Least Connections

```nginx
upstream backend {
    least_conn;
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
}
```

请求发给当前活跃连接数最少的服务器。适合请求处理时间差异大的场景（有的请求 10ms 返回，有的 10s 返回）。

### 5. Random

```nginx
upstream backend {
    random two;
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
}
```

随机选两台（`two`），然后从中选连接数最少的一台。这是**分布式场景下表现最优**的算法——没有全局锁，高度可预测。

### 怎么选？

| 场景 | 推荐算法 |
|------|----------|
| 无状态、处理时间均匀 | 加权轮询 |
| 需要会话保持 | ip_hash 或 sticky cookie |
| 处理时间差异大 | least_conn |
| 高并发分布式 | random |
| 测试/开发 | 默认轮询 |

## 健康检查

Nginx 默认有**被动健康检查**：如果一台后端服务器连续失败太多次，Nginx 会把它标记为 `down`，不再发请求给它。隔一段时间后再试试看它恢复了没有。

```nginx
upstream backend {
    server 127.0.0.1:3000 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:3001 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:3002 max_fails=3 fail_timeout=30s backward;
}
```

- **`max_fails=3`**：在 `fail_timeout` 时间内失败 3 次就标记为不可用
- **`fail_timeout=30s`**：30 秒后重新尝试
- **`backup`**：备用服务器，只有在所有主服务器都挂了才启用
- **`down`**：手动标记为不可用，做维护时用

```nginx
upstream backend {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001 down;   # 维护中，暂时下掉
    server 127.0.0.1:3002;
}
```

> **Nginx Plus** 提供主动健康检查（定期发 `/health` 请求验证）。免费版只有被动检查，但大多数场景下已经够用。

## 连接池：keepalive

每个后端连接都有 TCP 三次握手和四次挥手的开销。Nginx 可以在与后端的连接上启用 keepalive 复用：

```nginx
upstream backend {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    keepalive 32;   # 每个 worker 维持 32 个空闲连接
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;             # 必须用 HTTP/1.1
        proxy_set_header Connection "";      # 清除 close 头
    }
}
```

**关键点**：`keepalive` 的值不是"最多 32 个连接"，而是"最多保留 32 个**空闲**连接"。如果并发需求超过 32，Nginx 会创建新连接，用完后回收到池里。

这个值一般设多大？等于后端能承受的峰值 QPS / worker 数量。比如后端一个实例能处理 500 QPS，你有 4 个 worker，那 `keepalive 128` 差不多。

## 完整示例：生产级负载均衡

```nginx
upstream backend_app {
    least_conn;
    server 10.0.1.10:3000 weight=3 max_fails=2 fail_timeout=30s;
    server 10.0.1.11:3000 weight=3 max_fails=2 fail_timeout=30s;
    server 10.0.1.12:3000 weight=1 max_fails=2 fail_timeout=30s;
    server 10.0.1.13:3000 backup;

    keepalive 64;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    location / {
        proxy_pass http://backend_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        include snippets/proxy-params.conf;

        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;

        # 失败时重试下一个后端
        proxy_next_upstream error timeout invalid_header http_500 http_502 http_503;
        proxy_next_upstream_tries 2;  # 最多重试 1 次
    }
}
```

这个配置的特点：
- `least_conn` 调度，适应不同请求耗时
- 两台主力 (10, 11) 权重高，一台低配 (12) 权重低
- 第 4 台是备用的 (`backup`)
- `keepalive 64` 复用后端连接
- `proxy_next_upstream` 定义了哪些情况应该重试下一个后端

## 小结

这一章我们学到了：

1. `upstream` 定义后端服务器池
2. 五种调度算法：轮询、加权轮询、IP 哈希、最少连接、随机
3. 被动健康检查 + `backup`/`down` 标记
4. `keepalive` 连接池复用
5. `proxy_next_upstream` 失败重试

负载均衡是 Nginx 的核心优势之一。下一章我们处理 WebSocket——它和普通 HTTP 代理有些不同。
