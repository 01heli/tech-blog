## 一、从 docker commit 到 Dockerfile

你可以在一个基础镜像上手动改东西，然后 `docker commit` 保存为新镜像：

```bash
docker run -it alpine sh
apk add python3
exit
docker commit <container-id> my-python:manual

# 这样也能创建镜像，但它是"黑箱"——没人知道这个镜像里装了什么。
# 下次要改，你还得从头来一遍。
```

**Dockerfile 把构建过程写成了代码——可阅读、可版本控制、可重复。** 它解决了三个问题：构建过程透明化（谁都可以看到镜像里有什么）、自动化（CI/CD 一条命令构建）、可优化（利用缓存加速构建）。

## 二、你的第一个 Dockerfile

创建一个目录，放两个文件：

```
my-app/
├── Dockerfile
└── app.py
```

```python
# app.py —— 一个最简单的 Flask 应用
from flask import Flask
app = Flask(__name__)

@app.route('/')
def hello():
    return 'Hello from Docker!'

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

```dockerfile
# Dockerfile —— 构建蓝图
FROM python:3.12-slim                  # 1. 从哪个基础镜像开始
WORKDIR /app                            # 2. 设置工作目录
COPY app.py .                           # 3. 把应用代码拷贝进去
RUN pip install flask                   # 4. 安装依赖
EXPOSE 5000                             # 5. 声明容器会监听 5000 端口（文档性质）
CMD ["python", "app.py"]               # 6. 容器启动时执行的命令
```

```bash
# 构建镜像
docker build -t my-app:v1 .

# 输出中你会看到：
# Step 1/6 : FROM python:3.12-slim     ← 拉取/使用基础镜像
# Step 2/6 : WORKDIR /app              ← 设置工作目录
# Step 3/6 : COPY app.py .             ← 拷贝文件
# Step 4/6 : RUN pip install flask     ← 安装依赖（这一步最慢）
# Step 5/6 : EXPOSE 5000
# Step 6/6 : CMD ["python", "app.py"]
# Successfully tagged my-app:v1

# 运行
docker run -d -p 5000:5000 --name my-app my-app:v1

# 验证
curl localhost:5000
# → Hello from Docker!
```

## 三、Dockerfile 核心指令详解

### 3.1 FROM：一切从这里开始

```dockerfile
# 指定基础镜像（必须的，且必须是第一条指令）
FROM python:3.12-slim

# 多阶段构建中可以多次出现
FROM nginx:alpine AS runtime

# 从零开始构建（scratch 是一个空镜像，没有 Shell，没有任何系统文件）
FROM scratch
COPY --from=builder /app/binary /binary
CMD ["/binary"]
```

### 3.2 COPY vs ADD

```dockerfile
# COPY：从构建上下文（build context，即 docker build 的目录）复制文件到镜像
COPY app.py /app/
COPY --chown=1000:1000 app.py /app/   # 指定文件所有者
COPY . /app/                           # 复制整个目录

# ADD：比 COPY 多了两个功能（用到的时候再用，平时用 COPY）
ADD archive.tar.gz /app/               # 自动解压 tar 文件
ADD https://example.com/file /app/     # 可从 URL 下载（不推荐，无法缓存）
```

> **原则：用 COPY 而不用 ADD。** 只在需要自动解压 tar 文件时才用 ADD。COPY 行为更透明，更容易预期。

### 3.3 RUN：在构建时执行命令

```dockerfile
# 每条 RUN 创建一个新的镜像层
RUN pip install flask

# 多个命令合并为一条 RUN（减少层数，减小镜像体积）
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc curl && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*

# Shell 形式（通过 /bin/sh -c 执行）
RUN pip install flask

# Exec 形式（不经过 Shell，更安全，但不支持变量展开）
RUN ["pip", "install", "flask"]
```

**为什么要把多条命令合在一起？** Docker 的镜像由一层一层叠加而成。每条 `RUN` 创建一层，即使你后续 `rm -rf` 了，那个文件仍然存在于之前的层里，最终镜像仍然包含它的体积。合在一起写，该层结束时这些临时文件就不存在了。

### 3.4 CMD vs ENTRYPOINT

这是 Dockerfile 里最容易弄混的两个指令。

```dockerfile
# CMD：容器启动时默认执行的命令（可以被 docker run 后面的命令覆盖）
CMD ["python", "app.py"]
# docker run my-app → 执行 python app.py
# docker run my-app bash → 执行 bash（覆盖了 CMD）

# ENTRYPOINT：容器的入口（不被 docker run 后面的命令覆盖，后面的当作参数）
ENTRYPOINT ["python", "app.py"]
CMD ["--port", "5000"]
# docker run my-app → 执行 python app.py --port 5000
# docker run my-app --port 8080 → 执行 python app.py --port 8080
```

| | Shell 形式 | Exec 形式 | 可被子命令覆盖？ |
|------|-----------|---------|--------------|
| CMD | `CMD python app.py` | `CMD ["python", "app.py"]` | 是 |
| ENTRYPOINT | `ENTRYPOINT python app.py` | `ENTRYPOINT ["python", "app.py"]` | 否 |

> 组合拳：**用 ENTRYPOINT 指定"这个容器就是干这个的"，用 CMD 指定"默认参数"。** `docker run` 后面带的命令会覆盖 CMD 但不会覆盖 ENTRYPOINT——即把命令作为 ENTRYPOINT 的参数。

### 3.5 其他常用指令

```dockerfile
# WORKDIR：设置工作目录（如果目录不存在会自动创建）
WORKDIR /app
# 后续的 RUN / COPY / CMD 都在这个目录下执行
# 最好用绝对路径，不要 cd（cd 只在当前 RUN 中生效，下一条 RUN 又回到 / 了）

# ENV：设置环境变量（构建时 + 运行时都有）
ENV APP_ENV=production \
    APP_PORT=5000

# ARG：构建参数（只在构建时可用，容器运行时不可见）
ARG VERSION=1.0.0
RUN echo "Building version ${VERSION}"

# EXPOSE：声明容器会监听哪些端口（文档性质，不做实际的端口映射）
EXPOSE 5000

# USER：切换运行用户（不要用 root 跑应用）
USER 1000

# VOLUME：声明容器里的目录应该被挂载（也是文档性质，Docker 不会自动创建卷）
VOLUME /var/lib/mysql

# LABEL：给镜像打元数据标签
LABEL maintainer="team@example.com"
LABEL version="1.0.0"
LABEL description="My Flask App"
```

## 四、镜像的分层结构：为什么构建能缓存

这是理解 Docker 构建速度的核心概念：

```
┌─────────────────────────────────────┐
│   Layer 6: 可写层 (容器运行时)       │  ← 容器启动时添加
├─────────────────────────────────────┤
│   Layer 5: CMD ["python","app.py"]  │  ← 每条指令是一层
├─────────────────────────────────────┤
│   Layer 4: EXPOSE 5000              │
├─────────────────────────────────────┤
│   Layer 3: RUN pip install flask    │  ← 这一层包含了下载的包
├─────────────────────────────────────┤
│   Layer 2: COPY app.py .            │  ← 这一层有你的代码
├─────────────────────────────────────┤
│   Layer 1: FROM python:3.12-slim    │  ← 基础镜像（包含 OS + Python）
└─────────────────────────────────────┘
```

**构建缓存的工作原理：**

```
第一次构建：
  Step 1: FROM python:3.12-slim        ← 从仓库拉取，缓存
  Step 2: WORKDIR /app                 ← 创建层，缓存
  Step 3: COPY app.py .                ← 创建层，缓存
  Step 4: RUN pip install flask        ← 下载安装，创建层，缓存
  Step 5: CMD ["python", "app.py"]     ← 创建层，缓存

你改了 app.py，第二次构建：
  Step 1: FROM python:3.12-slim        ← 命中缓存 ✓
  Step 2: WORKDIR /app                 ← 命中缓存 ✓
  Step 3: COPY app.py .                ← 文件变了，缓存失效 ✗
  Step 4: RUN pip install flask        ← 上一层变了，缓存失效 ✗
  Step 5: CMD ["python", "app.py"]     ← 即使内容没变，上层失效它也失效 ✗
```

> **关键优化原则：把不经常变的东西放前面，经常变的东西放最后。** 尤其是——**先 `COPY requirements.txt` 再 `RUN pip install`，最后 `COPY .` 拷贝源代码。** 这样改了代码不会导致依赖重装：

```dockerfile
# 好的顺序
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .          # 依赖文件很少变
RUN pip install -r requirements.txt   # 这层会被缓存！
COPY . .                         # 代码经常变，放最后
CMD ["python", "app.py"]
```

## 五、多阶段构建：把镜像做小

### 5.1 问题

一个 Go 应用，编译需要 Go SDK（几百 MB），但运行只需要一个几十 MB 的二进制文件。传统做法需要两个 Dockerfile（一个构建，一个运行），很麻烦。

### 5.2 多阶段构建

```dockerfile
# 阶段 1：构建（编译环境，几百 MB）
FROM golang:1.22 AS builder
WORKDIR /build
COPY . .
RUN go build -o ./bin/app ./cmd/app

# 阶段 2：运行（最精简环境）
FROM alpine:3.19
COPY --from=builder /build/bin/app /app      # 只从 builder 阶段拿编译产物
CMD ["/app"]
```

**最终镜像大小：Alpine + 一个二进制文件 = 约 20MB。** 如果用单个 Dockerfile 从 `golang:1.22` 构建，镜像会接近 1GB。

### 5.3 前端应用的例子

```dockerfile
# 阶段 1：构建静态文件
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .
RUN npm run build       # 生成 dist/ 目录

# 阶段 2：用 Nginx 提供静态文件服务
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
# 不需要 Node.js，不需要 node_modules，镜像只有几十 MB
```

## 六、构建命令进阶

```bash
# 基本构建
docker build -t my-app:v1 .

# 指定 Dockerfile 路径
docker build -t my-app:v1 -f Dockerfile.prod .

# 指定构建参数
docker build -t my-app:v1 --build-arg VERSION=2.0.0 .

# 不使用缓存（完全重新构建）
docker build --no-cache -t my-app:v1 .

# 给镜像打多个标签
docker build -t my-app:v1 -t my-app:latest -t registry.example.com/my-app:v1 .

# 推送镜像到远程仓库
docker push registry.example.com/my-app:v1

# 从远程仓库拉取
docker pull registry.example.com/my-app:v1
```

## 七、镜像大小优化清单

| 优化手段 | 效果 | 说明 |
|---------|------|------|
| 用 alpine/slim 基础镜像 | 从 900MB → 100MB | 用 `python:3.12-alpine` 而不是 `python:3.12` |
| 合并 RUN 命令 | 减少层数 | `apt-get update && apt-get install && rm -rf /var/lib/apt/lists/*` 写在一起 |
| 多阶段构建 | 从 1GB → 20MB | 编译环境和运行环境分离 |
| .dockerignore | 排除不必要的文件 | 像 .gitignore 一样，排除 node_modules/ .git/ *.md |
| 先拷依赖，后拷代码 | 加速构建 | COPY requirements.txt → RUN pip install → COPY . |
| 清理包管理器缓存 | 减小体积 | `apt-get clean` / `apk cache clean` |
| 不要安装调试工具 | 减小体积 | 不要在生产镜像里装 vim/curl/netcat |
