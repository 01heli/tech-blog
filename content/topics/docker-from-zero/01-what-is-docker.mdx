## 一、"在我机器上能跑啊"

如果你做过两年以上的软件开发，一定遇到过这个场景：

```
周五下午 5:30，测试说："登录功能报 500 错误。"

你本地一跑——正常。
你："在我机器上能跑啊。"

测试："那为什么测试环境不行？"

你 SSH 到测试服务器，查了半小时：
  · Python 版本：你本地 3.11，测试环境 3.9（之前用到了一个 3.10 才有的语法）
  · 系统库：你本地 glibc 2.31，测试环境 2.17（某个 cryptography 包需要 2.28+）
  · 环境变量：你本地配置了 DATABASE_URL，测试环境的 /etc/environment 里没写
  · Nginx 配置：你本地没用 Nginx，测试环境有 Nginx 反向代理，传丢了某个 Header

最终——你在测试服务器上手动了两个多小时才修好。下周一晨会：
"我们能不能把代码和运行环境一起打包发布？"
```

**这就是 Docker 要解决的问题。** 把应用及其所有依赖（操作系统库、运行时、配置文件……起跑需要的全部东西）打包成一个标准化的镜像。这个镜像在开发的 Mac 上跑、在测试的 Linux 上跑、在生产服务器上跑——行为完全一致。

## 二、容器 vs 虚拟机：一个关键的区别

在 Docker 之前，解决"环境不一致"的标准方案是虚拟机（VM）。

### 2.1 虚拟机怎么工作

```
┌─────────────────────────────────────────┐
│                物理服务器                  │
│  ┌──────────────────┐ ┌────────────────┐ │
│  │    虚拟机 1        │ │   虚拟机 2      │ │
│  │  ┌──────────────┐ │ │ ┌────────────┐ │ │
│  │  │   App A      │ │ │ │   App B    │ │ │
│  │  ├──────────────┤ │ │ ├────────────┤ │ │
│  │  │  Bin/Libs     │ │ │ │ Bin/Libs   │ │ │
│  │  ├──────────────┤ │ │ ├────────────┤ │ │
│  │  │  Guest OS     │ │ │ │ Guest OS   │ │ │
│  │  │  (Ubuntu)     │ │ │ │ (CentOS)   │ │ │
│  │  └──────────────┘ │ │ └────────────┘ │ │
│  └──────────────────┘ └────────────────┘ │
│  ┌──────────────────────────────────────┐ │
│  │         Hypervisor (VMware/KVM)       │ │
│  ├──────────────────────────────────────┤ │
│  │            Host OS (宿主机)            │ │
│  └──────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

虚拟机在物理硬件之上，通过 Hypervisor 模拟出完整的虚拟硬件（虚拟 CPU、虚拟网卡、虚拟磁盘），然后在上面跑一个完整的操作系统。

**虚拟机解决了环境隔离的问题——但它重。** 每个虚拟机需要独立的操作系统，一个操作系统起步就要几 GB 的磁盘、几百 MB 的内存，启动要几十秒。

### 2.2 Docker 怎么工作

```
┌─────────────────────────────────────────┐
│                物理服务器                  │
│  ┌───────────────┐ ┌───────────────┐     │
│  │   容器 A       │ │   容器 B       │     │
│  │  ┌───────────┐ │ │ ┌───────────┐ │     │
│  │  │   App A   │ │ │ │   App B   │ │     │
│  │  ├───────────┤ │ │ ├───────────┤ │     │
│  │  │ Bin/Libs  │ │ │ │ Bin/Libs  │ │     │
│  │  └───────────┘ │ │ └───────────┘ │     │
│  └───────────────┘ └───────────────┘     │
│  ┌──────────────────────────────────────┐ │
│  │          Docker Engine                │ │
│  ├──────────────────────────────────────┤ │
│  │       Host OS (宿主机，共享内核)        │ │
│  └──────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

Docker 的容器**不需要独立的 Guest OS**。所有容器共享宿主机的操作系统内核，它们只是被"隔离开的用户空间"——每个容器有自己的文件系统、进程空间、网络栈，但内核是同一个。

| 维度 | 虚拟机 | Docker 容器 |
|------|-------|------------|
| 启动速度 | 30 秒 - 2 分钟 | < 1 秒（进程启动） |
| 磁盘占用 | 每个 VM 几个 GB | 每个镜像几百 MB |
| 内存占用 | 每个 VM 几百 MB - 几 GB | 几十 MB |
| 性能损耗 | 5-15%（虚拟化层开销） | < 1%（直接系统调用） |
| 隔离级别 | 操作系统级（强） | 进程级（较强） |
| 内核 | 各自独立 | 共享宿主机内核 |

> **一句话：容器不是轻量级虚拟机，它是带了隔离的进程。** 理解了这句话，就理解了 Docker 的本质。

### 2.3 Docker 的隔离靠什么实现

Docker 不是凭空造出来的——它利用了两个 Linux 内核特性：

- **Namespace（命名空间）**：限制"能看到什么"。PID namespace 让容器只能看到自己的进程，Mount namespace 让容器有自己独立的文件系统视图，Network namespace 让容器有独立的网卡和 IP。
- **Cgroups（控制组）**：限制"能用多少"。限制容器最多能用多少 CPU、多少内存、多少磁盘 I/O。

```
Namespace：你看不到我                    Cgroups：你的份额到这里为止
┌─────────────┐ ┌─────────────┐        ┌─────────────┐ ┌─────────────┐
│   容器 A     │ │   容器 B     │        │   容器 A     │ │   容器 B     │
│ PID: 1,2,3  │ │ PID: 1,2    │        │ CPU ≤ 2 核  │ │ CPU ≤ 1 核  │
│   只能看到    │ │   只能看到   │        │ Mem ≤ 1GB  │ │ Mem ≤ 512MB│
│  自己的进程   │ │  自己的进程   │        └─────────────┘ └─────────────┘
└─────────────┘ └─────────────┘
        ▲               ▲
        └───────┬───────┘
        宿主机内核（Namespace + Cgroups）
```

## 三、镜像、容器、仓库：Docker 的三大核心概念

```
                    docker pull
    ┌──────────────────────────────────────┐
    │              Image Registry          │
    │          (Docker Hub / 私有仓库)       │
    └──────────────────────────────────────┘
          │                          ▲
          │ docker pull              │ docker push
          ▼                          │
    ┌──────────┐  docker run   ┌──────────┐
    │  Image   │ ───────────► │ Container│
    │  (镜像)   │             │  (容器)   │
    │  只读模板  │             │  运行实例  │
    └──────────┘             └──────────┘
                                   │
                              docker commit
                                   │
                                   ▼
                            ┌──────────┐
                            │ 新 Image  │
                            └──────────┘
```

**镜像（Image）**：一个只读的模板，包含运行应用所需的文件系统——代码、运行时、系统工具、系统库。镜像是一层一层叠起来的（层是只读的，共享复用）。

**容器（Container）**：镜像的运行实例。当你 `docker run` 一个镜像时，Docker 在镜像的只读层之上加一个可写层，这个整体就是一个容器。可以启动、停止、删除。同一个镜像可以同时跑很多个容器实例。

**仓库（Registry）**：存放和分发镜像的地方。Docker Hub 是最大的公共仓库（相当于 GitHub 之于 Git）。公司内部通常搭建私有仓库。

> 类比：**镜像 = 程序安装包（exe/msi），容器 = 运行起来的进程，仓库 = 软件下载站。** 编程语言来类比：镜像 = 类（Class），容器 = 实例（Instance）。

## 四、一个完整的"镜像→容器"瞬间

从零到看到 Nginx 欢迎页，只需要一条命令：

```bash
docker run -d -p 8080:80 --name my-nginx nginx:alpine
```

这条命令发生了什么？

```
1. docker run nginx:alpine
   → 检查本地有没有 nginx:alpine 镜像
   → 没有 → 从 Docker Hub 拉取
   → 下载了 6 个镜像层，总共约 40MB（alpine 版很精简）

2. -d（detach，后台运行）
   → Docker 创建一个容器，加载 nginx:alpine 镜像
   → 在只读的镜像层上添加一个薄薄的可写层
   → 分配 IP 地址、创建网络接口

3. -p 8080:80（端口映射）
   → 宿主机的 8080 端口 → 映射到 → 容器的 80 端口

4. --name my-nginx（命名）
   → 容器命名为 my-nginx（不指定的话 Docker 会自动生成一个随机名字如 "admiring_curie"）

5. 浏览器打开 http://localhost:8080
   → 看到 Nginx 欢迎页
```

从下载到运行，总共不到 10 秒（取决于网络）。如果用虚拟机，光装操作系统就要十几分钟。

## 五、Docker 解决了什么问题——不只是"环境一致"

回看 Docker 解决的问题，它其实一次解决了四个层面的矛盾：

```
开发阶段             测试/部署阶段          运维阶段
─────────          ────────────         ────────

"在我机器上能跑"    环境配置繁琐           资源利用率低
      │                │                    │
      ▼                ▼                    ▼
  Docker 镜像      一次构建，到处运行      容器密度远高于VM
  统一了环境        测试/CI/生产同一个镜像    一台机器跑几十个容器

                              │
                              ▼
                    开发、测试、运维的协作方式变了：
                    "你的代码 + Dockerfile"
                    而不是
                    "你的代码 + 一份 20 页的部署说明文档"
```

## 六、Docker 不是什么

为了避免后续章节的过度期望，先明确 Docker 的边界：

1. **Docker 不是虚拟机。** 它共享宿主机内核，Linux 容器只能在 Linux 上运行，Windows 容器只能在 Windows 上运行（跨平台靠虚拟机/子系统中转）。

2. **Docker 不解决分布式问题。** 容器本身不解决"多个容器怎么协作"——那是 Docker Compose、Kubernetes 做的事。

3. **Docker 不是银弹。** 有些应用（如需要特定内核模块、需要直接访问硬件）不适合容器化。数据库在容器里跑也有争议（I/O 性能、数据持久化的考量）。

4. **Docker 不等于容器。** Docker 是容器的一种实现（最早做得好且推广开了的）。今天有 podman、containerd、CRI-O 等其他选择——但学习容器，从 Docker 入门仍然是最好的路径。
