## 一、从一个慢查询说起

假设你刚入职一家电商公司，接手了商品详情页的维护。页面上要展示商品基本信息、库存数量、最新 10 条评价——三个 SQL 查询拼出一个页面，响应时间 150ms。你觉得还行。

然后运营告诉你：双十一要到了，预计流量翻 30 倍。

你把代码拉下来压测。50 个并发，响应时间从 150ms 变成了 3.8 秒。数据库 CPU 飙到 100%，慢查询日志刷屏了——全是商品详情页那三条 SQL。

你开始想：**这些商品信息几百年不变，为什么每次都要去数据库里查一遍？**

这就是 Redis 存在的全部理由。

## 二、计算机里的"时间阶梯"

在讲 Redis 之前，先理解一个底层事实：计算机里，不同存储介质的访问速度差了 N 个数量级。

```
访问延迟阶梯（从上到下，每下一层慢约 1000 倍）：

L1 缓存           █ 0.5 ns      (CPU 片内，KB 级别)
L2 缓存           ██ 7 ns       (CPU 片内/片外，MB 级别)
内存 (RAM)        ███ 100 ns    (Redis 在这里，GB 级别)
SSD (NVMe)        ████████████████████ 100 us   (慢了 1000 倍)
机械硬盘 (HDD)     ████████████████████████████████ 10 ms   (慢了 10 万倍)
网络请求 (内网)    ████████████████████████████████████████ 1-5 ms  (慢了 5 万倍)
```

这个阶梯告诉我们一件事：**把频繁访问的数据从磁盘挪到内存，可以获得 1000-100000 倍的加速。** 这不是优化，这是降维打击。

Redis 就是一个把数据放在内存里的存储系统。它所有的数据都在内存中，读写操作直接操作内存——这就是它快的根本原因。

> Redis 的单机 QPS 轻松达到 10 万+，而 MySQL 单机 QPS 通常在几千到一万。差距不是几倍，是两个数量级。

## 三、Redis 不是另一个 MySQL——它们的定位完全不同

很多初学者会把 Redis 当成"另一个数据库"，这是理解 Redis 时最大的误解。

```
MySQL（关系型数据库）：           Redis（内存数据结构服务器）：
┌──────────────────────┐        ┌──────────────────────┐
│ 永久存储              │        │ 临时/半永久存储         │
│ 存所有数据             │        │ 存热数据               │
│ 磁盘为主，内存为缓存    │        │ 内存为主，磁盘为备份     │
│ SQL 查询语言           │        │ 原子操作命令            │
│ 表格 + 行 + 列         │        │ 数据结构（字符串/列表/集合等）│
│ 适合：持久化、复杂查询   │        │ 适合：缓存、计数、队列、排行榜│
└──────────────────────┘        └──────────────────────┘
```

一句话总结：**MySQL 存的是"全量冷热数据"，Redis 存的是"热数据的加速副本"。** Redis 不替代 MySQL——它站在 MySQL 前面，替它挡住大部分读请求。

## 五、Redis vs Memcached——为什么 Redis 赢了

Redis 不是第一个内存缓存系统。在它之前，Memcached 已经存在了很多年。但今天，Redis 几乎全面取代了 Memcached。为什么？

| 维度 | Memcached | Redis |
|------|-----------|-------|
| 数据类型 | 只支持 String（Key-Value） | String、List、Set、Hash、Sorted Set、Stream 等 |
| 持久化 | 不支持（重启数据全丢） | RDB 快照 + AOF 日志，可持久化到磁盘 |
| 集群 | 客户端分片 | 原生 Cluster 模式，服务端分片 |
| 复制 | 不支持 | 原生主从复制 + Sentinel 哨兵 |
| 线程模型 | 多线程 | 单线程（6.0+ 网络 I/O 多线程） |
| 功能丰富度 | 仅缓存 | 事务、Lua 脚本、Pub/Sub、Stream、Geo |
| 内存管理 | Slab Allocation（容易浪费） | Jemalloc（高效利用） |

**Redis 赢在"不只是缓存"。** Memcached 是一个纯粹的缓存工具——重启后数据全部丢失，只能从头开始重建缓存。Redis 有持久化、有主从、有哨兵——它是你可以在生产环境中依赖的基础设施，而不仅仅是一个加速层。

## 六、Redis 是单线程的——为什么还能这么快？

这是 Redis 最容易被误解的一个事实。Redis 的核心命令处理是单线程的——所有读写命令在一个线程里顺序执行。

```
传统多线程数据库：                    Redis 单线程：

请求1 ──▶ Thread 1 ──▶ 加锁            请求1 ──┐
请求2 ──▶ Thread 2 ──▶ 等锁            请求2 ──┤
请求3 ──▶ Thread 3 ──▶ 等锁            请求3 ──┤──▶ 一个线程顺序处理
请求4 ──▶ Thread 4 ──▶ 等锁            请求4 ──┘  无锁、无上下文切换
     ↑ 大量 CPU 浪费在线程切换和锁竞争上了       ↑ CPU 全部用来处理数据
```

单线程快的原因：

1. **所有数据在内存中**——没有磁盘 I/O，单次操作就是纳秒级，CPU 根本不是瓶颈
2. **没有锁开销**——不需要保护共享数据结构，因为没有并发访问同一数据的问题
3. **没有上下文切换**——不会在线程间频繁切换浪费 CPU 时间
4. **精心设计的数据结构**——Redis 用到了跳跃表、压缩列表、哈希表，每种结构都针对内存操作优化到了极致

> Redis 单线程的真正瓶颈在网络 I/O，所以 Redis 6.0 引入了 I/O 多线程——网络读写用多线程，命令执行仍然单线程。

## 七、Redis 为什么不是银弹

说完了 Redis 有多快，必须诚实地说它不适合什么：

**Redis 不适合的场景：**

1. **大数据量的持久化存储。** 内存比磁盘贵几十倍。如果要存 TB 级的数据，用 MySQL/MongoDB 更合理，Redis 只缓存热点数据。

2. **复杂的关系型查询。** Redis 没有 JOIN，没有 WHERE 子句。它的查询模型是 Key → Value 的直接映射。如果你需要"查询所有 2025 年下单且金额超过 1000 元的用户"，MySQL 更适合。

3. **需要强 ACID 保证的交易数据。** Redis 有事务，但它的"原子性"指的是"命令要么全执行要么全不执行"，不包括回滚。Redis 的事务没有 MySQL 那种 ACID 级别的保证。

4. **内存有限又不想丢数据。** Redis 可以持久化，但它的设计哲学是内存优先——如果内存不够用，你需要 Cluster 分片或者换个方案。

**Redis 最适合的场景：**

- 数据量在 GB 级别（通过 Cluster 可以到 TB）
- 高频访问（QPS > 1000）
- 数据结构操作是瓶颈（排序、去重、交集）
- 可以接受极短暂的数据不一致（最终一致性）
