## 一、缓存不是免费午餐

前面讲的都是 Redis 本身的技术——数据结构、持久化、高可用、集群。但如果缓存的使用方式不对，这些技术等于白搭。

缓存引入了一个核心矛盾：**你和数据库之间多了一层中间件，这层中间件的数据和数据库里的数据可能不一致。** 所有缓存问题，归根结底都是这个矛盾的体现。

四种经典问题：

```
                    缓存问题全景图

    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
    │  穿透    │    │  击穿    │    │  雪崩    │    │ 一致性   │
    │ Penetrate│    │Breakdown│    │Avalanche│    │Consistency│
    └────┬────┘    └────┬────┘    └────┬────┘    └────┬────┘
         │              │              │              │
    查不存在的数据   一个热点 Key    大量 Key 同时    缓存和数据库
    穿过了缓存层     过期了          过期了          对不上了
    打到数据库       瞬间大量请求    数据库压垮      用户看到旧数据
         │          打到数据库      连锁反应           │
         │              │              │              │
         ▼              ▼              ▼              ▼
    布隆过滤器      互斥锁/逻辑过期  随机过期时间    延迟双删/Canal
```

## 二、缓存穿透：查一个不存在的数据

### 2.1 问题

```
恶意用户遍历商品 ID：
  GET /product/9999999
    → 查 Redis (缓存未命中)
    → 查 MySQL (这个 ID 不存在)
    → 返回空，也不写入缓存（ID 不存在，没法缓存）

  × 10000 次/秒（恶意攻击）→ 每次打到 MySQL
  → MySQL CPU 100%
```

攻击者专门查不存在的数据——这些不在缓存里，也不在数据库里。每次都穿透到数据库，缓存形同虚设。

### 2.2 解决方案

**方案一：缓存空值**

```python
def get_product(product_id):
    # 查缓存
    cached = redis.get(f"product:{product_id}")
    if cached == "NULL":       # 标记的"不存在"
        return None
    if cached:
        return json.loads(cached)

    # 查数据库
    product = db.query(product_id)
    if product:
        redis.setex(f"product:{product_id}", 3600, json.dumps(product))
        return product
    else:
        # 不存在也缓存，值设为特殊标记，过期时间短一些
        redis.setex(f"product:{product_id}", 60, "NULL")
        return None
```

这样做的好处是简单直接。缺点是如果恶意用户用大量不重复的 ID 攻击，Redis 里会密密麻麻存满各种 `"NULL"` 值——内存浪费且防御效率低。

**方案二：布隆过滤器（推荐）**

布隆过滤器在逻辑上放在缓存层前面：**先问布隆过滤器"这个 ID 是否存在"，如果它说不存在，那就一定不存在——直接返回，不用查数据库。**

```
请求 → 布隆过滤器 → "不存在" → 直接返回 404（不经过缓存，也不经过数据库）
                  → "可能存在" → 正常走 缓存 → 数据库 流程
```

```python
# 使用 Redis 的布隆过滤器模块（RedisBloom）
# 或者用 pybloom-live / bloom-filter 库

from redisbloom.client import Client
rb = Client()

# 初始化布隆过滤器（预计 1000 万条数据，误判率 0.1%）
rb.bfCreate('products', 0.001, 10000000)

# 添加所有已有的商品 ID（初始化或更新时）
rb.bfAdd('products', 1001)
rb.bfAdd('products', 1002)
# ... 全量导入

# 查询时先过布隆过滤器
def get_product(product_id):
    if not rb.bfExists('products', product_id):
        return None    # 一定不存在，直接返回
    # 可能存在，正常走缓存+数据库流程
    ...
```

布隆过滤器的特性：**说"不存在"一定对，说"可能存在"有概率错（误判率可配置）。** 用它来挡掉"一定不存在的请求"——这正是穿透攻击的特征。

> **关键提醒：** 布隆过滤器里存的是"所有可能的合法 Key"。如果你的数据会新增（如新商品上架），需要把新 ID 也加入布隆过滤器。这个更新通常通过监听 MySQL binlog（Canal）来驱动。

## 三、缓存击穿：一个热 Key 过期了

### 3.1 问题

```
双十一零点，秒杀商品的缓存过期了：

时刻 T-1s: 秒杀商品在 Redis 里，缓存命中，一切正常
时刻 T:    缓存刚好过期
时刻 T+1ms: 10000 个用户同时请求这个秒杀商品
          → 全部缓存未命中
          → 全部打到数据库
          → 数据库执行 10000 次相同的 SQL
          → 数据库 CPU 100%，响应超时，连锁崩溃
```

击穿和穿透的区别：**击穿是查一个热 Key——它存在，但它的缓存刚好过期了。** 就像一道防线上唯一被轰开的缺口，所有兵力从这个缺口涌进去。

### 3.2 解决方案

**方案一：互斥锁（简单可靠）**

```python
def get_product_with_lock(product_id):
    # 先查缓存
    cached = redis.get(f"product:{product_id}")
    if cached:
        return json.loads(cached)

    # 缓存未命中——抢锁
    lock_key = f"lock:product:{product_id}"
    if redis.setnx(lock_key, "1"):
        try:
            redis.expire(lock_key, 10)  # 锁 10 秒过期（防死锁）
            # 再查一次缓存（可能其他线程已经重建好了）
            cached = redis.get(f"product:{product_id}")
            if cached:
                return json.loads(cached)
            # 查数据库
            product = db.query(product_id)
            if product:
                redis.setex(f"product:{product_id}", 3600, json.dumps(product))
            return product
        finally:
            redis.delete(lock_key)
    else:
        # 没抢到锁——等一小会儿，然后重试
        time.sleep(0.05)
        return get_product_with_lock(product_id)  # 递归重试
```

每次只有一个线程去查数据库重建缓存，其他线程等待缓存就绪。缺点是增加了编排复杂度，以及抢锁的线程查库期间其他用户需要等待。

**方案二：逻辑过期（不设 TTL，值里带过期时间）**

```python
def get_product_logical_expire(product_id):
    # 从缓存拿数据（这个 Key 永不设置 Redis 过期时间）
    raw = redis.get(f"product:{product_id}")
    if not raw:
        # 真没有——查库
        product = db.query(product_id)
        redis.set(f"product:{product_id}", json.dumps({
            "data": product,
            "expire_at": time.time() + 3600   # 逻辑过期时间
        }))
        return product

    record = json.loads(raw)
    if time.time() < record["expire_at"]:
        return record["data"]     # 没过期，直接返回

    # 逻辑过期了——抢锁重建缓存
    if redis.setnx(f"lock:product:{product_id}", "1"):
        try:
            redis.expire(f"lock:product:{product_id}", 10)
            product = db.query(product_id)
            redis.set(f"product:{product_id}", json.dumps({
                "data": product,
                "expire_at": time.time() + 3600
            }))
        finally:
            redis.delete(f"lock:product:{product_id}")

    # 抢不到锁——直接返回旧数据（关键！）
    return record["data"]
```

这个方案的精髓：**缓存过期后，宁可先返回旧数据（用户不会察觉几百毫秒的延迟），也不让请求涌向数据库。** 只有一个线程去重建，其他线程继续用旧缓存。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 互斥锁 | 实现简单，一定能拿到最新数据 | 查库期间用户等待 |
| 逻辑过期 | 用户无需等待，体验好 | 数据可能有短暂延迟，实现复杂 |

## 四、缓存雪崩：大量 Key 同时过期

### 4.1 问题

```
场景：零点统一设置促销缓存，过期时间都是 1 小时

  1:00:00 —— 10 万个促销 Key 同时过期
  1:00:01 —— 瞬间 10 万请求打到数据库
  1:00:05 —— 数据库扛不住，开始超时
  1:00:30 —— 应用端因为数据库超时，线程池耗尽
  1:01:00 —— 整个系统不可用
```

和击穿不同的是，雪崩不是"一个"热 Key 过期，而是"一群" Key 同时过期——像雪崩一样，一层压一层，终致整体崩溃。

### 4.2 解决方案

**方案一：过期时间加随机偏移（最简单有效）**

```python
# 不要这样
BASE_TTL = 3600

# 而是这样
BASE_TTL = 3600
random_offset = random.randint(0, 600)   # 0-10 分钟的随机偏移
redis.setex(key, BASE_TTL + random_offset, value)
```

10 万个 Key 的过期时间从"全部在 3600 秒"离散到"3600-4200 秒之间"，数据库的流量被均摊到了 10 分钟的窗口里。

**方案二：多级缓存 + 降级**

```
请求 → 本地缓存（Caffeine）→ Redis → MySQL
                ↓ 降级
          返回旧数据或默认值
```

当 Redis 大面积过期、MySQL 出现压力时，可以降级到本地缓存（虽然数据更旧，但不是空，也不会压垮数据库）——这是**限流降级**的思路。

**方案三：Redis Cluster + 多节点**

如果你的 Redis 本身就是 Cluster 模式，多个 Master 分担了不同的键——即使一个 Master 挂了，也只有 1/N 的缓存失效，不会全量涌向数据库。

## 五、缓存与数据库一致性——最让人头疼的问题

### 5.1 问题本质

```
MySQL 里：product:2025:stock = 99
Redis 里：product:2025:stock = 100 （缓存了旧值）

用户看到库存 100，下单，实际只有 99——超卖了。
```

**缓存的本质是"数据库的一份异步副本"。** 既然是异步的，就一定存在不一致的窗口。你能控制的是：**让这个窗口尽量小，让不一致的影响尽量可控。**

### 5.2 四种更新策略

**策略一：先删缓存，后更新数据库**

```
1. 删除 Redis 缓存
2. 更新 MySQL
```

问题：删除缓存后，更新数据库前，另一个请求读到了旧数据库数据，并把它写入了缓存。结果——缓存里还是旧数据。

```
线程 A（写）          线程 B（读）
  │                    │
  │ 删缓存              │
  │ ─────────────────► │ 查缓存（空）
  │                    │ 查数据库（旧值）
  │                    │ 写缓存（旧值）← 缓存被"污染"了
  │ 更新数据库（新值）    │
  ▼                    ▼
  结果：数据库是新值，缓存是旧值
```

**策略二：先更新数据库，后删缓存（推荐）**

```
1. 更新 MySQL
2. 删除 Redis 缓存
```

这是目前最推荐的策略。问题发生的概率远小于策略一（因为"读请求恰好在新旧之间"的概率远小于"写请求恰好在新旧之间"）。但如果删除缓存失败——缓存里永远留着旧数据。

**策略三：延迟双删**

```
1. 先删缓存
2. 更新数据库
3. 等几百毫秒（让并发读完成）
4. 再删一次缓存
```

这是对策略一的补救。但"等几百毫秒"这个时间不好控制——等短了没效果，等长了用户体验差。

**策略四：订阅 binlog + 异步更新（最可靠）**

```
MySQL binlog → Canal 监听 → 解析变更 → 更新/删除 Redis

  ┌──────────┐    binlog     ┌──────────┐    更新     ┌──────────┐
  │  MySQL   │ ───────────► │  Canal   │ ─────────► │  Redis   │
  └──────────┘              └──────────┘            └──────────┘
```

这是最彻底的方案——**把缓存更新交给专门的同步组件，业务代码不用关心缓存一致性。** 代价是增加了一个 Canal 组件要维护，以及 binlog 到 Redis 之间仍有秒级延迟。

### 5.3 一致性方案总结

| 策略 | 实现难度 | 一致性 | 推荐场景 |
|------|---------|--------|---------|
| 先删缓存后更库 | 低 | 差（易污染） | 不推荐 |
| 先更库后删缓存 | 低 | 较好 | 大多数场景（配合重试机制） |
| 延迟双删 | 中 | 较好 | 并发读写很高的场景 |
| Canal + binlog | 高 | 最好 | 对一致性要求高的核心业务 |

> **实际建议：** 对大多数业务，用"先更新数据库，后删除缓存" + 删除失败重试（MQ 或定时任务兜底）就够了。不要过早追求 Canal 方案——维护 Canal 本身也是成本。只有当你确实遇到了"先更新数据库后删缓存"解决不了的一致性问题时，再引入 Canal。
