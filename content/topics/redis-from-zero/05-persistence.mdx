## 一、内存是光速，但光不会等你

Redis 把所有数据放在内存里——这是它快的原因，也是它脆弱的来源。突然断电或进程崩溃，内存里的数据就没了。

```
Redis 重启 vs MySQL 重启：

MySQL 重启：
  ┌──────┐     ┌────────────────┐     ┌──────┐
  │ 进程  │ ──► │ 从磁盘 ibd 文件  │ ──► │ 进程  │  数据完整
  │ 挂了  │     │ 加载数据到内存    │     │ 恢复  │
  └──────┘     └────────────────┘     └──────┘

Redis 重启（没有持久化）：
  ┌──────┐     ┌──────┐
  │ 进程  │ ──► │ 进程  │  数据全空——内存没了就没了
  │ 挂了  │     │ 恢复  │
  └──────┘     └──────┘
```

Redis 提供了两种持久化机制——**RDB（快照）和 AOF（追加日志）**。它们的思路完全不同，各有各的优缺点。

## 二、RDB：给内存拍一张快照

### 2.1 原理

RDB（Redis DataBase Backup）的做法是：**每隔一段时间，把当前内存里的所有数据写到一个 `.rdb` 文件里。这个文件就是一个时间点的完整数据快照。**

```
时刻 T1:                   时刻 T2:                   时刻 T3:
┌──────────┐             ┌──────────┐             ┌──────────┐
│ Key1=Val1│             │ Key1=Val1│             │ Key1=Val1│
│ Key2=Val2│  ────快照───►│ Key2=Val2│  ────快照───►│ Key2=Val2│
│ Key3=Val3│             │ Key3=Val3│             │ Key3=Val3│
│ Key4=Val4│             │ Key5=Val5│             │ Key6=Val6│
│ Key5=Val5│             │          │             │ Key7=Val7│
└──────────┘             └──────────┘             └──────────┘
     │                        │                        │
     ▼                        ▼                        ▼
 dump.rdb                 dump.rdb                 dump.rdb
 (5个Key)                 (5个Key)                 (5个Key)
```

### 2.2 触发方式

```bash
# 手动触发
SAVE                           # 主线程执行，会阻塞所有命令（生产禁用）
BGSAVE                         # 子进程执行，父进程继续处理请求（推荐）

# 自动触发（redis.conf 配置）
save 900 1                     # 900 秒（15 分钟）内至少 1 次修改 → 触发 BGSAVE
save 300 10                    # 300 秒内至少 10 次修改
save 60 10000                  # 60 秒内至少 10000 次修改
```

### 2.3 BGSAVE 的写时复制（Copy-On-Write）

`BGSAVE` 是 Redis 持久化的核心机制。它通过操作系统的 **fork()** 创建一个子进程，这个子进程拥有父进程内存的完整快照（通过 Copy-On-Write 机制，不是真的复制全量内存）。

```
BGSAVE 执行过程：

1. 父进程 fork() → 子进程
   ┌──────────┐      ┌──────────┐
   │ 父进程     │ fork │ 子进程     │
   │ 继续处理请求 │ ───► │ 把内存数据  │
   │          │      │ 写入 RDB  │
   └──────────┘      └──────────┘
   共享同一份内存页
   （操作系统 Copy-On-Write 机制）

2. 如果父进程在子进程写 RDB 期间要修改一个 Key：
   - 操作系统复制那一页内存给父进程
   - 父进程在新页上修改
   - 子进程仍然看原来的页（保证快照一致性）

3. 子进程写完 RDB 文件 → 退出
   → 用新的 RDB 文件替换旧的
```

> 这意味着 RDB 不会阻塞正常命令处理——代价是这段时间内如果改了很多数据，父进程和子进程各自维护的内存页会增加，内存占用会临时上升。

### 2.4 RDB 的优缺点

| 优点 | 缺点 |
|------|------|
| 文件紧凑（二进制压缩格式），适合备份/迁移 | 两次快照之间的数据可能丢失（如最近 5 分钟的写入） |
| 恢复速度快（直接加载到内存） | BGSAVE fork 时，大量数据可能导致 fork 本身耗时较长 |
| 对性能影响小（子进程异步处理） | 不适合对数据丢失敏感的严苛场景（交易、金融） |

> **适用场景：** 缓存为主的数据，允许丢失几分钟的数据。比如全量缓存、非关键业务数据、定期备份到冷存储的场景。

## 三、AOF：记录每一次修改

### 3.1 原理

AOF（Append Only File）的思路和 RDB 完全不同：**它不拍快照，而是在文件后面追加记录每一条修改命令。**

```
AOF 文件内容（以 RESP 协议格式记录）：

*3                  ← 3 个参数
$3                  ← 第一个参数长度 3
SET
$9
user:age
$2
28

翻译：SET user:age 28 → 这就是一条 AOF 记录
```

Redis 重启时，**逐条重放 AOF 文件中记录的命令**来重建数据。这有点像 MySQL 的 binlog——持续追加，不修改已有的部分。

### 3.2 AOF 的三种刷盘策略

AOF 写文件的时机由 `appendfsync` 控制：

| 策略 | 行为 | 性能 | 安全性 |
|------|------|------|--------|
| `always` | 每条命令都同步写入磁盘 | 最低（几百 QPS） | 最高（最多丢一条） |
| `everysec` | 每秒同步一次（默认，推荐） | 高（接近无持久化） | 高（最多丢 1 秒数据） |
| `no` | 由操作系统决定何时写入 | 最高 | 最低（可能丢几十秒数据） |

```bash
# redis.conf 配置
appendonly yes
appendfsync everysec
```

> **`everysec` 是最佳平衡点：** 性能损失极小（通常 < 5%），最多丢 1 秒的写入。对 99% 的业务来说，丢失 1 秒的数据是可以接受的——除非你在做高频交易。

### 3.3 AOF 重写：别让文件撑爆磁盘

AOF 文件只增不减——如果你把一个计数器 `INCR` 了 10000 次，AOF 里就记录了 10000 条 `INCR` 命令。但实际上只需要一条 `SET counter 10000` 就够了。

AOF 重写（Rewrite）做的就是这件事：**创建一个新的 AOF 文件，只包含恢复当前数据所需的最小命令集。**

```
重写前（AOF 文件）：
SET counter 0
INCR counter           ← 这 10000 条只有最后一条有意义
INCR counter
... (9999 条)
INCR counter
SET user:1 "张三"

重写后（新 AOF 文件）：
SET counter 10000      ← 压缩为一条
SET user:1 "张三"
```

AOF 重写也是通过 BGREWRITEAOF 在子进程中执行的（和 BGSAVE 类似的 fork 机制），不阻塞主进程。

```bash
# 配置自动重写条件
auto-aof-rewrite-percentage 100   # AOF 文件增长到上次重写后的 2 倍
auto-aof-rewrite-min-size 64mb    # AOF 文件至少 64MB 才触发重写
```

### 3.4 AOF 的优缺点

| 优点 | 缺点 |
|------|------|
| 数据安全性高（最多丢 1 秒） | AOF 文件比 RDB 大（文本协议记录命令，不是压缩二进制） |
| 文件可读（文本格式，可以看到具体命令） | 恢复速度比 RDB 慢（逐条重放命令 vs 直接加载数据） |
| 自动重写控制文件大小 | 高写入场景下 AOF 文件可能快速增长 |

## 四、混合持久化：Redis 4.0 后的最佳方案

Redis 4.0 引入了混合持久化：**RDB 文件 + AOF 文件的后半部分。**

```
混合持久化文件结构：

┌────────────────────────────┐
│    RDB 部分（快照）          │  ← 某个时间点的完整数据快照
│    (紧凑二进制)              │
├────────────────────────────┤
│    AOF 部分（增量）          │  ← 快照之后的所有修改命令
│    (RESP 协议文本)           │
└────────────────────────────┘

恢复时：
  先加载 RDB 部分（快速恢复大部分数据）
  → 再重放 AOF 部分（恢复到最新状态）
```

```bash
# 启用混合持久化
aof-use-rdb-preamble yes
```

**混合持久化 = RDB 的恢复速度 + AOF 的数据安全性。** 这是目前 Redis 持久化的最佳实践。

## 五、三种持久化方案全景对比

```
                    数据安全性
                        ▲
                        │
                   always (AOF)     ← 最安全，最慢
                       │
                       │
              everysec (AOF)
                   │
                   │
              混合持久化 ←────────── 最佳平衡点（推荐）
                   │
                   │
              RDB (5分钟)
                   │
                   │
              无持久化 ──────────── 最快，重启全丢
                   │
                   └──────────────────► 性能
```

| 方案 | 数据丢失窗口 | 恢复速度 | 文件大小 | 推荐场景 |
|------|------------|---------|---------|---------|
| 无持久化 | 全部 | 瞬间 | 0 | 纯缓存（数据可从数据库重建） |
| RDB | 几分钟 | 快 | 小 | 缓存为主，备份迁移 |
| AOF (everysec) | 1 秒 | 慢 | 大 | 数据安全要求高 |
| 混合持久化 | 1 秒 | 快 | 中 | **生产环境首选** |

## 六、最佳实践

```bash
# 生产环境推荐配置（redis.conf）：
save 900 1
save 300 10
save 60 10000          # RDB：多个时间窗口触发

appendonly yes          # 启用 AOF
appendfsync everysec    # 每秒刷盘
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-use-rdb-preamble yes  # 混合持久化（Redis 4.0+）
```

> **不要以为开了持久化就万事大吉了。** 持久化文件也需要备份——定期把 RDB/AOF 文件拷贝到离线存储（对象存储、NFS），或者在 Slave 节点上执行 BGSAVE 减少对 Master 的影响。生产环境至少要保留最近 7 天的 RDB 备份。
